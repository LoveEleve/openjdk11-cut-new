## 为什么要分析这些字节码？

解释器是 JVM 的"最终兜底"——**所有 Java 代码最初都通过解释器执行**。理解这些字节码模板等于理解：
- `if/else/for/while/switch` 在 CPU 上到底是什么指令？
- `a[i] = x` 的边界检查开销有多大？
- `getfield` 为什么第一次慢、后面快？（字节码重写机制）
- `checkcast` 失败时的 ClassCastException 从哪来？

## 一、控制流字节码

### 1.1 goto / goto_w — 无条件跳转

`goto` 是最简单的控制流字节码，对应 Java 中 `for`/`while` 循环的回跳和 `break`/`continue` 的前跳。

**athrow** 虽然也是控制流，但它走异常路径（已在 [ch06_exception_handling.md](/data/workspace/openjdk-cut-new/jvm-md/Runtime/ch06_exception_handling.md) 详细分析），此处仅做串联。

#### goto 的本质：调用 branch(false, false)

`goto` 字节码并没有独立的模板函数，而是调用通用的 `branch()` 方法：

> 源码: `templateTable_x86.cpp:2139`

```
branch(is_jsr=false, is_wide=false)
├── 1. 读取分支偏移量 (rdx)
│   ├── 非 wide: movl + bswap + sarl(16) → 有符号 16-bit 偏移
│   └── wide:    movl + bswap            → 有符号 32-bit 偏移
│
├── 2. 调整 BCP (r13 += rdx)
│   └── r13 = 字节码指针，加上偏移量 = 跳转目标
│
├── 3. 后向跳转检测 (rdx < 0?)
│   ├── rdx >= 0: 前向跳转 → 直接 dispatch（跳到 dispatch 标签）
│   └── rdx < 0:  后向跳转 → 需要更新计数器
│
├── 4. 回边计数器 (UseLoopCounter)
│   ├── 获取/创建 MethodCounters
│   ├── TieredCompilation:
│   │   ├── 有 MDO: 递增 MDO backedge_counter + 掩码检查
│   │   └── 无 MDO: 递增 MethodCounters backedge_counter + 掩码检查
│   └── 非 Tiered: 累加 backedge + invocation 计数器
│
├── 5. 计数器溢出处理
│   ├── !TieredCompilation: 检查 profile_limit → 分配 MDO
│   ├── !TieredCompilation: 检查 backedge_limit → 触发 OSR
│   └── TieredCompilation:  掩码溢出 → 直接 OSR
│
└── 6. OSR (UseOnStackReplacement)
    ├── call_VM: InterpreterRuntime::frequency_counter_overflow
    ├── 返回 nmethod? 验证 nmethod 状态
    ├── call_VM: SharedRuntime::OSR_migration_begin（迁移栈帧）
    ├── 弹出解释器帧
    └── jmp nmethod.osr_entry_point（进入编译代码）
```

**关键点：`goto` 不仅仅是跳转！每次后向跳转都会检查回边计数器，可能触发 JIT 编译（OSR）。**

#### 为什么后向跳转才计数？

前向跳转 = `break/continue/if-else 分支`，不代表循环。后向跳转 = 循环回边，是热点代码的标志。

#### OSR（On-Stack Replacement）触发流程

```
for 循环后向跳转
    │
    ▼
backedge_counter++
    │
    ▼ (超过阈值)
frequency_counter_overflow()
    │
    ▼
CompileBroker::compile_method(entry_bci = 循环入口)
    │
    ▼ (编译完成)
OSR nmethod 就绪
    │
    ▼
OSR_migration_begin()  ← 将解释器栈帧数据迁移到 OSR 缓冲区
    │
    ▼
弹出解释器帧 → jmp osr_entry_point  ← 直接跳入编译代码的循环体中间！
```

**PrintCompilation 中 OSR 编译的标志是 `%`：**
```
  1234  %4       4       com.example.Main::hotLoop @ 15 (42 bytes)
       ↑                                          ↑
       OSR标志                                    入口 BCI
```

### 1.2 if_0cmp / if_icmp / if_acmp / if_nullcmp — 条件分支

条件分支字节码的模板结构完全相同，区别只在于比较对象和条件码：

> 源码: `templateTable_x86.cpp:2371-2420`

```
┌──────────────────┬──────────────────────────────────────────────────┐
│ 字节码            │ 生成的汇编 (x86_64)                              │
├──────────────────┼──────────────────────────────────────────────────┤
│ ifeq (x == 0)   │ testl rax, rax;  jne not_taken; branch()        │
│ ifne (x != 0)   │ testl rax, rax;  je  not_taken; branch()        │
│ iflt (x < 0)    │ testl rax, rax;  jge not_taken; branch()        │
│ ifge (x >= 0)   │ testl rax, rax;  jl  not_taken; branch()        │
│ ifgt (x > 0)    │ testl rax, rax;  jle not_taken; branch()        │
│ ifle (x <= 0)   │ testl rax, rax;  jg  not_taken; branch()        │
├──────────────────┼──────────────────────────────────────────────────┤
│ if_icmpeq        │ pop rdx; cmpl rdx, rax; jne not_taken; branch()│
│ if_icmpne        │ pop rdx; cmpl rdx, rax; je  not_taken; branch()│
│ if_icmplt        │ pop rdx; cmpl rdx, rax; jge not_taken; branch()│
│ ...              │ （以此类推）                                     │
├──────────────────┼──────────────────────────────────────────────────┤
│ if_acmpeq        │ pop rdx; cmpoop rdx, rax; jne not_taken; ...   │
│ if_acmpne        │ pop rdx; cmpoop rdx, rax; je  not_taken; ...   │
├──────────────────┼──────────────────────────────────────────────────┤
│ ifnull           │ testptr rax, rax; jne not_taken; branch()       │
│ ifnonnull        │ testptr rax, rax; je  not_taken; branch()       │
└──────────────────┴──────────────────────────────────────────────────┘
```

**设计模式**：条件取反 + `branch()`

所有条件分支都使用**条件取反**的方式：当条件**不满足**时跳到 `not_taken` 标签，满足时顺序执行 `branch()` 完成跳转。

原因：
1. `branch()` 包含大量代码（计数器递增、OSR 检查等），放在顺序路径上减少跳转
2. 循环通常是"跳回去"（taken），`not_taken` 是退出循环，统计上 taken 更频繁

**not_taken 路径：**
```cpp
__ bind(not_taken);
__ profile_not_taken_branch(rax);  // 更新 MDO 中 "未走分支" 计数
```

### 1.3 tableswitch — O(1) 跳转表

Java 的 `switch` 语句如果 case 值稠密（如 `1, 2, 3, 4, 5`），`javac` 编译为 `tableswitch`。

> 源码: `templateTable_x86.cpp:2440`

**字节码格式：**
```
tableswitch
  <0-3 bytes padding>    // 对齐到 4 字节边界
  default_offset: int32  // 默认跳转偏移
  low: int32             // case 最小值
  high: int32            // case 最大值
  offsets[high-low+1]: int32[]  // 跳转偏移表
```

**生成的汇编逻辑（伪代码）：**
```
rax = switch 值
rbx = 对齐到 4 字节的表起始地址

rcx = bswap(low)    // 大小端转换
rdx = bswap(high)

if (rax < rcx) goto default_case
if (rax > rdx) goto default_case

// O(1) 查表
offset = table[rax - low]   // Address(rbx, rax, times_4, 3*BytesPerInt)
profile_switch_case(rax)     // 更新 profiling
rbcp += bswap(offset)        // 调整 BCP
dispatch_only(vtos)          // 分发下一字节码
```

**性能：O(1)**。无论多少个 case，只需要一次数组索引。

### 1.4 lookupswitch → fast_linearswitch / fast_binaryswitch

如果 case 值稀疏（如 `1, 100, 10000`），`javac` 编译为 `lookupswitch`。

**关键优化：HotSpot 在类加载时把 lookupswitch 重写为更高效的内部字节码。**

> 源码: `templateTable_x86.cpp:2475`

```cpp
void TemplateTable::lookupswitch() {
  transition(itos, itos);
  __ stop("lookupswitch bytecode should have been rewritten");
  // 永远不该执行到这里！
}
```

这说明原始的 `lookupswitch` 字节码在类加载后被 Rewriter 重写为：
- `Bytecodes::_fast_linearswitch`（case 数量少）
- `Bytecodes::_fast_binaryswitch`（case 数量多）

#### fast_linearswitch — O(n) 线性搜索

> 源码: `templateTable_x86.cpp:2480`

```
rax = bswap(switch 值)    // 预先转换，避免每次比较都 bswap
rcx = bswap(npairs)       // case 数量

loop:
  if (rax == table[rcx].match) goto found
  rcx--
  if (rcx >= 0) goto loop

// 未找到 → 走 default
default: offset = table[0]

found: offset = table[rcx].offset
rbcp += bswap(offset)
dispatch_only(vtos)
```

**性能：O(n)**，适合 case 少（< 5-6 个）的情况。

#### fast_binaryswitch — O(log n) 二分搜索

> 源码: `templateTable_x86.cpp:2518`

使用 Dijkstra/Feijen 的二分搜索算法：

```
i = 0, j = npairs

while (i + 1 < j):
    h = (i + j) >> 1
    if (key < array[h].match):
        j = h
    else:
        i = h

// 最终 i 是候选位置，再验证一次
if (key == array[i].match):
    offset = array[i].offset  // 命中
else:
    offset = default_offset   // 未命中
```

**性能：O(log n)**，适合 case 多（≥ 6 个）的情况。

**两种实现使用 `cmov` 指令避免分支**：
```asm
cmov32(Assembler::less, j, h);            // j = h if key < array[h]
cmov32(Assembler::greaterEqual, i, h);    // i = h if key >= array[h]
```

`cmov` 是条件移动指令，不会导致分支预测失败，对 switch 这种多路分支非常友好。

### 1.5 控制流字节码总结

| 字节码 | 用途 | 复杂度 | 特殊行为 |
|--------|------|--------|---------|
| `goto` / `goto_w` | 无条件跳转 | O(1) | 后向跳转触发回边计数器+OSR |
| `ifeq/ifne/iflt/...` | 与 0 比较 | O(1) | profile_not_taken_branch |
| `if_icmpeq/...` | 两个 int 比较 | O(1) | 同上 |
| `if_acmpeq/if_acmpne` | 对象引用比较 | O(1) | cmpoop（压缩指针感知） |
| `ifnull/ifnonnull` | null 检查 | O(1) | testptr |
| `tableswitch` | 稠密 switch | O(1) | 跳转表直接索引 |
| `lookupswitch` | 稀疏 switch | — | **被重写！永远不执行** |
| `_fast_linearswitch` | 稀疏 switch (少量 case) | O(n) | bswap 预转换 |
| `_fast_binaryswitch` | 稀疏 switch (大量 case) | O(log n) | cmov 无分支二分 |
| `athrow` | 抛出异常 | — | null_check + jump throw_exception_entry |

## 二、字段操作字节码

### 2.1 整体架构：resolve → cache → access

Java 中 `obj.field` 和 `ClassName.field` 对应 `getfield`/`getstatic` 字节码。字段访问看似简单，但涉及复杂的**解析-缓存-访问**三阶段：

```
首次执行                              后续执行
─────────                            ─────────
getfield #index                      _fast_igetfield (已重写)
    │                                    │
    ▼                                    ▼
resolve_cache_and_index()            直接从 ConstantPoolCache 读取
    │                                偏移量和类型标志
    ▼                                    │
InterpreterRuntime::resolve_get_put  ─→  ▼
    │                                load_field_cp_cache_entry()
    ▼                                    │
SystemDictionary::resolve_or_fail        ▼
    │                                access_load_at(T_INT, field_addr)
    ▼                                    │
写入 ConstantPoolCacheEntry              ▼
    │                                push(itos) → dispatch_next
    ▼
patch_bytecode → _fast_igetfield
```

**为什么需要这么复杂？**

字节码中的 `#index` 是常量池索引，指向一个 `Fieldref` 符号引用（类名+字段名+类型描述符）。第一次访问时需要：
1. 解析类（可能触发类加载）
2. 在类层次中搜索字段（可能在父类）
3. 计算字段在对象中的偏移量
4. 检查访问权限

这些步骤只需要做一次，之后偏移量和类型信息被缓存在 `ConstantPoolCacheEntry` 中。

### 2.2 getfield_or_static 详解

> 源码: `templateTable_x86.cpp:2860-3005`

```cpp
void TemplateTable::getfield_or_static(int byte_no, bool is_static, 
                                        RewriteControl rc) {
  transition(vtos, vtos);

  const Register cache = rcx;
  const Register index = rdx;
  const Register obj   = LP64_ONLY(c_rarg3) NOT_LP64(rcx);
  const Register off   = rbx;      // 字段偏移量
  const Register flags = rax;      // 类型标志

  // ① 解析常量池缓存条目
  resolve_cache_and_index(byte_no, cache, index, sizeof(u2));
  
  // ② JVMTI 字段访问事件
  jvmti_post_field_access(cache, index, is_static, false);
  
  // ③ 加载缓存条目（获取对象指针、偏移量、类型标志）
  load_field_cp_cache_entry(obj, cache, index, off, flags, is_static);

  // ④ 非静态字段：弹出对象引用 + null 检查
  if (!is_static) pop_and_check_object(obj);

  // ⑤ 构建字段地址
  const Address field(obj, off, Address::times_1, 0);  // obj + offset

  // ⑥ 根据类型标志分发到不同的加载路径
  //    flags 的 tos_state 字段指示字段类型
  __ shrl(flags, ConstantPoolCacheEntry::tos_state_shift);
  __ andl(flags, ConstantPoolCacheEntry::tos_state_mask);
```

接下来是一系列 `if-else` 链（用 `cmp + jcc` 实现），按字段类型分发：

```
flags == btos? → access_load_at(T_BYTE)   → push(btos) → patch(_fast_bgetfield)
flags == ztos? → access_load_at(T_BOOLEAN) → push(ztos)
flags == atos? → do_oop_load              → push(atos) → patch(_fast_agetfield)
flags == itos? → access_load_at(T_INT)    → push(itos) → patch(_fast_igetfield)
flags == ctos? → access_load_at(T_CHAR)   → push(ctos) → patch(_fast_cgetfield)
flags == stos? → access_load_at(T_SHORT)  → push(stos) → patch(_fast_sgetfield)
flags == ltos? → access_load_at(T_LONG)   → push(ltos) → patch(_fast_lgetfield)
flags == ftos? → access_load_at(T_FLOAT)  → push(ftos) → patch(_fast_fgetfield)
flags == dtos? → access_load_at(T_DOUBLE) → push(dtos) → patch(_fast_dgetfield)
```

### 2.3 字节码重写（Bytecode Rewriting）

**核心优化**：`getfield` 第一次解析后被就地重写为 `_fast_Xgetfield`，下次直接走快速路径。

```
原始字节码流:   [B4] [00] [03]     // getfield #3
                 ↓ 重写
快速字节码流:   [CC] [00] [03]     // _fast_igetfield #3 (假设是 int)
```

**`_fast_igetfield` 比 `getfield` 快多少？**

| 步骤 | `getfield` | `_fast_igetfield` |
|------|-----------|-------------------|
| resolve_cache_and_index | ✅（带解析检查） | ✅（跳过解析检查） |
| 类型判断 cmp/jcc 链 | ✅（8 次比较） | ❌（直接知道是 int） |
| access_load_at | ✅ | ✅ |
| 估计指令数 | ~50 | ~15 |

**省掉了约 35 条指令！** 对于频繁访问的字段（如循环内 `this.count++`），这个优化非常有价值。

### 2.4 putfield_or_static — 字段写入

> 源码: `templateTable_x86.cpp:3116-3300`

写入比读取多一个步骤：**写屏障**（用于 GC 的引用跟踪）。

```
putfield_or_static()
├── resolve_cache_and_index()       ← 同 getfield
├── jvmti_post_field_mod()          ← JVMTI 字段修改事件
├── load_field_cp_cache_entry()     ← 加载偏移量和类型
├── volatile 标志检查               ← 是否需要内存屏障
├── 按类型分发:
│   ├── btos: pop(btos) → access_store_at(T_BYTE, field)
│   ├── atos: pop(atos) → do_oop_store(field, rax)  ← 引用写入走 G1 写屏障！
│   ├── itos: pop(itos) → access_store_at(T_INT, field)
│   ├── ltos/dtos/ftos: 类似
│   └── patch_bytecode → _fast_Xputfield
└── volatile 字段: lock addl [rsp], 0  ← StoreLoad 屏障
```

**关键点：引用类型（atos）走 `do_oop_store`，内部包含 G1 写屏障！**

已在 [G1-Barrier-Assembly.md](/data/workspace/openjdk-cut-new/jvm-md/Interpreter/G1-Barrier-Assembly.md) 详细分析。

### 2.5 volatile 字段的特殊处理

volatile 字段需要内存屏障保证可见性：

```
getfield (volatile):
  access_load_at(..., MO_RELAXED)
  // x86 TSO 模型下，load 自带 acquire 语义，不需要额外屏障
  // （但 long/double 在 32-bit 需要原子读取）

putfield (volatile):
  access_store_at(...)
  lock addl [rsp], 0    ← x86 的 StoreLoad 屏障
  // lock 前缀刷新 store buffer，保证后续 load 看到最新值
```

### 2.6 getstatic 的特殊之处

`getstatic` 与 `getfield` 共用 `getfield_or_static()`，但 `is_static=true` 时：
1. **不弹出对象引用**（没有 `this`）
2. **对象指针来自 ConstantPoolCacheEntry**（指向类的 mirror 对象的 Klass）
3. **不重写字节码**（`getstatic` 没有快速版本，因为缓存查找本身就够快）

## 三、数组操作字节码

### 3.1 数组访问的通用模式

所有数组访问字节码遵循相同的三步模式：

```
1. index_check(array, index)  — null 检查 + 边界检查
2. 计算元素地址               — base + index * element_size
3. 访问元素                   — load 或 store
```

### 3.2 index_check — null 检查 + 边界检查

> 源码: `templateTable_x86.cpp:742-767`

```
index_check(array, index)
├── pop_ptr(array)                        // 弹出数组引用
├── null_check(array, length_offset)      // 隐式 null 检查
│   └── 如果 array == NULL，读取 length_offset 处触发 SIGSEGV
│       → 被信号处理器转换为 NullPointerException
├── movl2ptr(index, index)                // 符号扩展索引
├── cmpl(index, array->length)            // 无符号比较（一条指令同时检查 < 0 和 >= length）
├── index < length? → skip (正常)
└── index >= length? → 
    ├── mov rbx, index                    // 保存非法索引（用于异常消息）
    ├── mov c_rarg1, array                // 保存数组引用
    └── jump _throw_ArrayIndexOutOfBoundsException_entry
```

**关键优化：`cmpl` 的无符号比较**

Java 数组索引是 `int`（有符号），但 `cmpl` 后用 `jccb(Assembler::below, skip)` 即**无符号小于**跳转。

这是一个经典技巧：当 `index < 0` 时，无符号比较会将其视为很大的正数，自然大于 `length`，因此**一条比较指令同时检查了下界（< 0）和上界（≥ length）**！

### 3.3 iaload — int 数组加载

> 源码: `templateTable_x86.cpp:769`

```cpp
void TemplateTable::iaload() {
  transition(itos, itos);
  // rax: index (从栈顶弹出)
  // rdx: array (将被弹出)
  index_check(rdx, rax);       // null 检查 + 边界检查
  __ access_load_at(T_INT, IN_HEAP | IS_ARRAY, rax,
                    Address(rdx, rax, Address::times_4,
                            arrayOopDesc::base_offset_in_bytes(T_INT)),
                    noreg, noreg);
}
```

**地址计算**：`rdx + rax * 4 + base_offset_in_bytes(T_INT)`

其中：
- `rdx` = 数组对象指针
- `rax` = 索引
- `times_4` = int 元素大小 4 字节
- `base_offset_in_bytes(T_INT)` = 16 字节（64-bit，压缩指针开启时：markWord 8B + klass 4B + length 4B）

**各类型的 scale 和 base offset：**

| 类型 | 字节码 | Scale | Base Offset (64-bit +CompOops) |
|------|--------|-------|-------------------------------|
| byte/boolean | `baload` | times_1 | 16 |
| char | `caload` | times_2 | 16 |
| short | `saload` | times_2 | 16 |
| int | `iaload` | times_4 | 16 |
| float | `faload` | times_4 | 16 |
| long | `laload` | times_8 | 16 |
| double | `daload` | times_8 | 16 |
| ref | `aaload` | times_4 (CompOops) / times_8 | 16 |

### 3.4 aaload — 对象引用数组加载

> 源码: `templateTable_x86.cpp:819`

```cpp
void TemplateTable::aaload() {
  transition(itos, atos);
  index_check(rdx, rax);
  do_oop_load(_masm,
              Address(rdx, rax,
                      UseCompressedOops ? Address::times_4 : Address::times_ptr,
                      arrayOopDesc::base_offset_in_bytes(T_OBJECT)),
              rax, IS_ARRAY);
}
```

**与 iaload 的区别**：
1. **使用 `do_oop_load`** 而不是 `access_load_at`，因为引用类型可能需要 GC 屏障
2. **Scale 取决于 `UseCompressedOops`**：开启压缩指针时 4 字节，否则 8 字节
3. 加载的结果是一个 oop（对象指针），会做 decode_heap_oop

### 3.5 aastore — 对象引用数组存储（最复杂的数组操作）

> 源码: `templateTable_x86.cpp:1114`

aastore 是所有数组操作中最复杂的，因为它需要做**类型检查**（ArrayStoreCheck）：

```
aastore
├── 1. 弹出 value/index/array
│   rax = value, rcx = index, rdx = array
│
├── 2. index_check_without_pop(rdx, rcx)  — 边界检查
│
├── 3. value == null?
│   ├── null → 直接存 null（跳过类型检查）
│   └── 非 null → 类型检查
│
├── 4. 类型检查（gen_subtype_check）
│   ├── rbx = value.klass        // load_klass(rbx, rax)
│   ├── rax = array.klass → element_klass  // ObjArrayKlass::element_klass_offset()
│   └── gen_subtype_check(rbx, ok_is_subtype)
│       ├── 快速路径：直接比较 klass 指针
│       ├── 中速路径：检查 secondary_super_cache
│       └── 慢速路径：遍历 secondary_supers 数组
│
├── 5a. 类型检查失败 →
│   └── jump _throw_ArrayStoreException_entry
│
└── 5b. 类型检查成功 →
    └── do_oop_store(element_address, rax, IS_ARRAY)
        ├── 存储引用
        └── G1 写屏障（post_barrier）
```

**为什么 aastore 需要类型检查而 iastore 不需要？**

Java 数组是协变的：`String[]` 可以赋值给 `Object[]`。但运行时必须确保存入的元素类型兼容：

```java
Object[] arr = new String[10];  // 合法：String[] 是 Object[] 的子类型
arr[0] = new Integer(1);        // 编译通过，但运行时抛 ArrayStoreException！
```

### 3.6 arraylength

> 源码: `templateTable_x86.cpp:4164`

```cpp
void TemplateTable::arraylength() {
  transition(atos, itos);
  __ null_check(rax, arrayOopDesc::length_offset_in_bytes());
  __ movl(rax, Address(rax, arrayOopDesc::length_offset_in_bytes()));
}
```

**极简实现**：
1. null 检查（通过访问 `length_offset` 触发隐式异常）
2. 读取 `array + length_offset` 处的 int 值

`length_offset_in_bytes()` = 12（64-bit + CompressedOops：markWord 8B + klass 4B）

## 四、类型检查字节码

### 4.1 checkcast — 强制类型转换

> 源码: `templateTable_x86.cpp:4170`

Java 的 `(SomeType) obj` 编译为 `checkcast`：

```
checkcast #cp_index
├── 1. obj == null? → 直接通过（null 可以转为任何类型）
│
├── 2. 常量池标签检查
│   ├── tags[index] == JVM_CONSTANT_Class?
│   │   └── 是 → quicked 路径（已解析）
│   └── 否 → 调用 VM: InterpreterRuntime::quicken_io_cc()
│            解析类并写回常量池标签
│
├── 3. 加载超类 Klass 和对象 Klass
│   ├── rax = resolved_klass_at_index(rcx, rbx)  // 目标类 Klass
│   └── rbx = load_klass(rdx)                    // 对象实际 Klass
│
├── 4. gen_subtype_check(rbx, ok_is_subtype)
│   ├── 快速路径 #1: rbx == rax?（完全相同的类）
│   ├── 快速路径 #2: rax == rbx->super()?（直接父类）
│   ├── 中速路径: rax == rbx->secondary_super_cache?
│   └── 慢速路径: 线性遍历 rbx->secondary_supers[]
│
├── 5a. 检查成功 → bind(ok_is_subtype)
│   └── rax = rdx（恢复对象引用，继续执行）
│
└── 5b. 检查失败 →
    ├── push_ptr(rdx)  // 保存对象引用用于异常消息
    └── jump _throw_ClassCastException_entry
```

### 4.2 instanceof — 类型测试

> 源码: `templateTable_x86.cpp:4226`

Java 的 `obj instanceof SomeType` 编译为 `instanceof`：

```
instanceof #cp_index
├── 1. obj == null? → push 0（null 不是任何类型的实例）
│
├── 2-3. 同 checkcast（解析类 + 加载 Klass）
│
├── 4. gen_subtype_check(rdx, ok_is_subtype)
│
├── 5a. 检查成功 → rax = 1
└── 5b. 检查失败 → rax = 0
    // 注意：instanceof 不抛异常！只返回 0/1
```

**checkcast vs instanceof 的关键区别：**

| 特性 | checkcast | instanceof |
|------|-----------|------------|
| null 处理 | 通过（不抛异常） | 返回 0（false） |
| 类型不匹配 | 抛 ClassCastException | 返回 0 |
| 栈效果 | atos → atos（对象不变） | atos → itos（返回 int） |

### 4.3 gen_subtype_check — 子类型检查的三级加速

> 源码: `macroAssembler_x86.cpp`

子类型检查是 JVM 中最频繁的操作之一（每次 checkcast/instanceof/aastore 都要做），所以 HotSpot 设计了三级加速：

```
gen_subtype_check(subklass, superklass)

Level 1: 直接相等检查
    if (subklass == superklass) return true;
    // 1 条 cmp + 1 条 jcc，最快

Level 2: 主超类表快速检查
    // Klass 内部维护一个长度为 8 的 primary_supers[] 数组
    // 包含从 Object 到当前类的直接继承链
    depth = superklass->super_check_offset();  // 预计算的深度偏移
    if (subklass->primary_supers[depth] == superklass) return true;
    // 1 次内存读取 + 1 条 cmp，O(1)
    // 适用于继承深度 ≤ 7 的类（绝大多数 Java 类）

Level 3: 次级超类表搜索
    // 对于接口和深继承（depth > 7），先查 secondary_super_cache
    if (subklass->secondary_super_cache == superklass) return true;
    
    // cache miss → 线性遍历 secondary_supers[] 数组
    for (int i = 0; i < subklass->secondary_supers->length(); i++) {
        if (subklass->secondary_supers[i] == superklass) {
            subklass->secondary_super_cache = superklass;  // 缓存命中结果
            return true;
        }
    }
    return false;
    // O(n)，n = 实现的接口数量
```

**为什么 primary_supers 只有 8 个？**

统计显示 99% 的 Java 类继承深度 ≤ 7（Object=0, Thread=2, ArrayList=4, ...）。用固定大小数组可以做 O(1) 查找。

## 五、字节码模板分派机制回顾

所有字节码模板的最后一步都是"分派下一个字节码"：

```cpp
// 标准分派
__ dispatch_next(state);
  // 1. load_unsigned_byte(rbx, Address(rbcp, step))  // 读取下一字节码
  // 2. addptr(rbcp, step)                            // 推进 BCP
  // 3. dispatch_base(state, table)                   // 从 dispatch_table 跳转
  //    → jmp Address(rscratch1, rbx, Address::times_ptr)

// 仅分派（不推进 BCP，用于 branch/switch 已经调整了 BCP 的情况）
__ dispatch_only(state);
```

**dispatch_table 是一个 256 x 10 的二维数组**（256 个字节码 × 10 种 TosState），每个元素是一个代码地址。分派就是一次 indirect jump。

## 六、面试高频 Q&A

### Q1: for 循环在解释器中是怎么执行的？

**回答**：
for 循环编译为字节码后，循环条件是 `if_icmpge`（或类似条件分支）+ `goto` 回跳。解释器执行时：

1. 条件分支（`if_icmpge`）：弹出两个 int 做 `cmpl` 比较，不满足条件则走 `not_taken`（退出循环）
2. 回跳（`goto`）：读取负偏移量，调整 BCP 向前跳转
3. **关键**：每次 `goto` 回跳都会递增回边计数器（backedge_counter），超过阈值后触发 JIT 编译。如果 `UseOnStackReplacement` 开启（默认开启），还会触发 OSR——在循环还在执行的过程中，从解释器切换到编译后的机器码继续执行。

### Q2: switch-case 在 JVM 中是 O(1) 还是 O(n)？

**回答**：
取决于 case 值的分布：
- **稠密**（如 1,2,3,4,5）→ `javac` 编译为 `tableswitch` → **O(1)** 跳转表直接索引
- **稀疏**（如 1,100,10000）→ `javac` 编译为 `lookupswitch`，HotSpot 类加载时重写为：
  - case 少（< 5-6）→ `_fast_linearswitch` → **O(n)** 线性搜索
  - case 多（≥ 6）→ `_fast_binaryswitch` → **O(log n)** 二分搜索（使用 cmov 无分支指令）

注意：原始 `lookupswitch` 永远不会被解释器执行，会被重写为更快的内部字节码。

### Q3: 数组边界检查 `a[i]` 的开销有多大？

**回答**：
在解释器中，每次数组访问都会执行 `index_check()`：一条 `cmpl`（无符号比较，同时检查 index < 0 和 index >= length）+ 一条 `jccb`（正常跳过异常处理）。总共约 **2-3 条指令**。

在 C2 编译器中，可以通过**范围检查消除**优化掉循环内的边界检查：将循环分裂为 Pre-Main-Post 三段，Main 循环保证索引在安全范围内，完全去掉检查。

### Q4: getfield 为什么要重写字节码？

**回答**：
原始 `getfield` 需要从 ConstantPoolCacheEntry 中读取字段类型标志，然后做一系列 `cmp + jcc`（8-9 次比较）来确定是 int/long/object 等类型，再选择对应的 load 指令。

重写为 `_fast_igetfield` 后，类型已知，直接执行对应的 load 指令，省掉了 ~35 条指令。对于热点代码中的字段访问（如 `this.count`），这个优化非常显著。

重写是**原地修改字节码流**——直接把 `0xB4`(getfield) 改为 `0xCC`(_fast_igetfield) 等。

### Q5: aastore 为什么比 iastore 慢？

**回答**：
`aastore`（对象引用数组存储）比 `iastore`（int 数组存储）多两个步骤：
1. **ArrayStoreCheck**：需要调用 `gen_subtype_check()` 验证存入的对象类型与数组声明的元素类型兼容。因为 Java 数组是协变的（`String[] is-a Object[]`），编译期无法完全保证类型安全。
2. **G1 写屏障**：存入引用后需要执行 pre-barrier + post-barrier，通知 GC 跟踪跨代引用。

而 `iastore` 只需要一条 `movl` 指令（加上边界检查的 2-3 条指令）。

### Q6: instanceof 和 checkcast 在性能上有什么区别？

**回答**：
两者的核心逻辑完全相同——都是 `gen_subtype_check()`。区别在于结果处理：

- `checkcast`：失败时抛 ClassCastException（很少发生，所以异常路径开销不重要）
- `instanceof`：失败时返回 0（更常发生，但也只是设置 rax=0）

性能几乎没有差别。真正的瓶颈在于 `gen_subtype_check()` 的三级查找：
- 继承深度 ≤ 7 的类：O(1)（primary_supers 数组，一次内存读取）
- 接口/深继承：可能需要线性扫描 secondary_supers 数组
