**第 281 行深度分析**：
```cpp
// SignalHandlerMark 的简化实现（在 thread.hpp 中）
class SignalHandlerMark : public StackObj {
  Thread* _thread;
public:
  SignalHandlerMark(Thread* t) : _thread(t) {
    if (_thread) _thread->set_handling_signal(true);
  }
  ~SignalHandlerMark() {
    if (_thread) _thread->set_handling_signal(false);
  }
};
```

**第 365-367 行解析**：

**栈保护区域布局**（从高地址到低地址）：
```
高地址
├─ 已分配的栈空间（正常使用）
├─ Yellow Zone（黄色警戒区，约 32KB）
├─ Reserved Zone（保留区，约 4KB）
├─ Red Zone（红色禁区，约 4KB）
├─ 未映射的内存（访问会 SIGSEGV）
```

|------|------|-------------|
| Yellow Zone | 警告，还可以恢复 | 禁用 Yellow Zone，抛出 StackOverflowError |

## 6. Safepoint Polling 处理（第 432-434 行）

```cpp
432:       if (sig == SIGSEGV && os::is_poll_address((address)info->si_addr)) {
433:         stub = SharedRuntime::get_poll_stub(pc);
434:       }
```

**深度解析**：

**Safepoint Polling 机制**：
```
JVM 需要定期进入 Safepoint（安全点）进行 GC、Deoptimize 等操作。
实现方式：
1. JVM 映射一个特殊的"轮询页"（Polling Page）
2. 正常时该页可读
3. 需要进入 Safepoint 时，JVM mprotect 该页为不可读
4. 线程执行到轮询指令（通常是 test %eax, [polling_page]）时触发 SIGSEGV
5. 信号处理器识别这是 Safepoint 轮询，跳转到 Safepoint 处理代码
```

**为什么用 SIGSEGV 而不是其他机制？**
- **性能**：test 指令非常轻量，只有一个内存访问周期
- **精确性**：信号会立即触发，不会延迟
- **可恢复性**：通过修改 PC，可以无缝进入 Safepoint 处理

**`get_poll_stub(pc)` 返回什么？**
- 一段汇编代码的地址，这段代码会：
  1. 保存寄存器
  2. 调用 `SafepointSynchronize::block()` 阻塞直到 Safepoint 结束
  3. 恢复寄存器
  4. 跳回原代码继续执行

**深度解析**：

**隐式 null check vs 显式 null check**：
```cpp
// 显式 null check（解释器常用）
if (obj == null) throw new NullPointerException();
// 对应汇编：
// test  rdi, rdi
// je    throw_npe

// 隐式 null check（JIT 编译代码常用）
int x = obj.field;  // 直接访问，如果 obj 为 null，触发 SIGSEGV
// 对应汇编：
// mov   eax, [rdi + offset]  // 如果 rdi=0，SIGSEGV
```

**`needs_explicit_null_check` 判断逻辑**：
```cpp
// 如果故障地址在 0-4095 之间（第一页），说明是 null 访问
// 因为 Java 对象不会分配在这个范围，mmap 通常也从高地址开始
bool MacroAssembler::needs_explicit_null_check(intptr_t offset) {
  return offset < 0 || offset >= os::vm_page_size();
}
```

**为什么 JIT 用隐式 null check？**
- **性能**：省去显式比较和分支预测失败的开销
- **代码密度**：少一条指令
- **代价**：null 访问时触发 SIGSEGV，进入内核，开销大。但 null 访问是异常情况，假设很少发生

**`continuation_for_implicit_exception`**：
- 返回一个 stub 地址，该 stub 会：
  1. 找到触发异常的 PC
  2. 确定是哪个字段访问
  3. 创建 NullPointerException
  4. 跳转到异常处理代码

```cpp
615:   sigaddset(&newset, sig);
616:   sigprocmask(SIG_UNBLOCK, &newset, NULL);
617:
618:   VMError::report_and_die(t, sig, pc, info, ucVoid);
```

**第 612-618 行深度解析**：

**为什么 unblock 信号？**
- 信号处理期间，内核会自动阻塞当前信号（防止递归）
- `VMError::report_and_die` 会生成 hs_err_pid.log，这个过程可能很复杂
- 如果在生成日志时又收到信号（如用户按 Ctrl-C），需要能处理
- 所以先 unblock，让 `report_and_die` 有机会处理新信号

**`VMError::report_and_die`**：
- 生成 hs_err_pid.log 文件
- 包含：寄存器状态、栈回溯、线程列表、内存映射、JVM 配置等
- 如果配置了 `CreateCoredumpOnCrash`，触发 core dump
- 最后调用 `os::die()` 终止进程

```cpp
620:   ShouldNotReachHere();
621:   return true; // Mute compiler
```

**第 620-621 行解析**：
- **`ShouldNotReachHere()`**：这是一个 `assert(false, "should not reach here")`。理论上 `report_and_die` 不会返回（它会调用 exit 或 abort）
- **`return true`**：为了让编译器不报错"控制流到达函数末尾却没有 return"。实际上这行永远不会执行

## 10. 面试高频问题总结

### Q1: 为什么 JVM 用 SIGSEGV 实现 NullPointerException？
**答案要点**：
1. 性能：省去显式 null check 的分支预测开销
2. 代码密度：少一条指令
3. 精确性：信号立即触发，没有延迟
4. 可恢复性：通过修改 ucontext->uc_mcontext.gregs[REG_RIP] 实现无缝跳转

### Q2: 信号处理中为什么用 `extern "C"`？
**答案要点**：
1. 禁用 C++ 名称修饰，确保函数名在 C 和汇编中一致
2. 这个函数要被 libjsig（C 代码）调用
3. 也要被 JVM 内部的汇编桩代码调用

### Q3: `ucontext_t` 是什么？如何修改程序执行流？
**答案要点**：
1. `ucontext_t` 是 Linux 保存线程上下文的结构，包含所有寄存器值
2. x86_64 上 PC 在 `uc->uc_mcontext.gregs[REG_RIP]`
3. 信号处理器修改这个值，返回后内核从新的 PC 开始执行
4. 这是实现"从信号恢复并执行其他代码"的关键机制

### Q4: Yellow Zone、Red Zone、Reserved Zone 的区别？
**答案要点**：
1. Yellow Zone（32KB）：警告区，触发 StackOverflowError，可恢复
2. Reserved Zone（4KB）：给 @ReservedStackAccess 方法使用，关键操作的最后机会
3. Red Zone（4KB）：致命区，栈已耗尽，JVM 终止
4. 实现：通过 mprotect 设置保护页，访问时触发 SIGSEGV

### Q5: 为什么 SIGPIPE 和 SIGXFSZ 直接返回 true？
**答案要点**：
1. 这两个信号的默认行为是终止进程
2. 但在 Java 中应该让系统调用返回 -1 并设置 errno
3. 直接返回 true 表示"已处理"，内核继续执行，系统调用返回错误
4. 这是 POSIX 规范的行为，不是 JVM bug
