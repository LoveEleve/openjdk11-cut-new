## 第 1 章: libnet.so 整体架构

### 1.1 一句话总结

libnet.so 是 Java 网络编程(Socket/ServerSocket)的底层原生实现，封装了 POSIX Socket API，将 Linux socket()、bind()、listen()、accept()、connect()、send()、recv() 等系统调用暴露给 Java 层。

### 1.2 核心类关系图

```
Java 层:
java.net.Socket
    └── SocketImpl (抽象类)
            └── PlainSocketImpl (实现类)
                    └── socketCreate() → JNI → socket()
                    └── socketBind()   → JNI → bind()
                    └── socketListen() → JNI → listen()
                    └── socketAccept() → JNI → accept()
                    └── socketConnect()→ JNI → connect()

java.net.SocketInputStream
    └── socketRead0()  → JNI → recv()

java.net.SocketOutputStream
    └── socketWrite0() → JNI → send()

Native 层 (libnet.so):
PlainSocketImpl.c
    ├── Java_java_net_PlainSocketImpl_socketCreate   → socket()
    ├── Java_java_net_PlainSocketImpl_socketBind     → bind()
    ├── Java_java_net_PlainSocketImpl_socketListen   → listen()
    ├── Java_java_net_PlainSocketImpl_socketAccept   → accept()
    ├── Java_java_net_PlainSocketImpl_socketConnect  → connect()
    └── Java_java_net_PlainSocketImpl_socketClose0   → close()

SocketInputStream.c
    └── Java_java_net_SocketInputStream_socketRead0  → recv()

SocketOutputStream.c
    └── Java_java_net_SocketOutputStream_socketWrite0 → send()
```

### 1.3 POSIX Socket API 映射

```
Java Method                    Native Method              POSIX API
─────────────────────────────────────────────────────────────────────────
Socket.<init>()           →   socketCreate()        →   socket()
ServerSocket.bind()       →   socketBind()          →   bind()
ServerSocket.listen()     →   socketListen()        →   listen()
ServerSocket.accept()     →   socketAccept()        →   accept()
Socket.connect()          →   socketConnect()       →   connect()
InputStream.read()        →   socketRead0()         →   recv()
OutputStream.write()      →   socketWrite0()        →   send()
Socket.close()            →   socketClose0()        →   close()
Socket.setOption()        →   socketSetOption0()    →   setsockopt()
Socket.getOption()        →   socketGetOption()     →   getsockopt()
```

**逐行深度解析**:

**Line 73-93: getMarkerFD() - 延迟关闭机制**

**什么是 marker fd?**
- 用于实现 "延迟关闭(deferred close)" 机制
- 解决多线程环境下 socket 关闭的竞态条件

**工作原理**:
```
1. 创建 Unix Domain Socket pair: sv[0], sv[1]
2. shutdown(sv[0]) - 关闭双向通信，使其成为 "无效" fd
3. close(sv[1])   - 关闭另一端
4. 返回 sv[0] 作为 marker fd

延迟关闭时:
  dup2(marker_fd, socket_fd)  // 将 socket_fd 替换为无效的 marker_fd
  // 原 socket_fd 被关闭，但任何正在进行的 IO 操作会立即发现 fd 无效
```

- 使用 dup2() 将 fd 替换为无效的 marker fd
- 正在进行的 IO 操作立即失败
- 避免多线程竞态条件

**方式 2: 立即关闭**
```c

    (*env)->SetIntField(env, fdObj, IO_fd_fdID, -1);
    NET_SocketClose(fd);
```
- 将 FileDescriptor.fd 设为 -1
- 调用 close() 关闭原生 fd

**为什么需要延迟关闭?**
```
场景: 线程 A 正在 read()，线程 B 调用 close()

立即关闭的问题:
  1. 线程 A 可能持有 fd 引用
  2. close() 后，fd 被系统回收
  3. 线程 A 可能错误地操作了其他 socket(如果 fd 被重用)

延迟关闭的解决:
  1. dup2(marker_fd, socket_fd) 将 socket_fd 指向无效 fd
  2. 原 socket 被关闭
  3. 线程 A 的 read() 立即返回错误(EBADF)
  4. 但 fd 数字本身没有被系统回收，安全
```

## 第 6 章: 面试高频问题与深度答案

### Q1: Java Socket 的阻塞/非阻塞模式是如何实现的?

**答案**:
```
实现层级:
1. Java 层: Socket 没有非阻塞 API(只有阻塞模式)
2. JNI 层: 通过 fcntl(fd, F_SETFL, O_NONBLOCK) 动态切换
3. 使用场景:
   - connect() 超时控制: 非阻塞 + poll
   - accept() 超时控制: 非阻塞 + poll
   - 正常 IO: 阻塞模式

代码示例 (socketConnect):
  SET_NONBLOCKING(fd);      // 切换为非阻塞
  connect(fd, ...);         // 立即返回
  poll(..., timeout);       // 等待连接完成
  SET_BLOCKING(fd);         // 恢复阻塞
```

### Q2: Socket 的延迟关闭(deferred close)机制是什么?

**答案**:
```
问题场景:
  线程 A: 阻塞在 read()
  线程 B: 调用 close()

立即关闭的风险:
  1. close() 释放 fd
  2. 系统回收 fd，可能分配给新 socket
  3. 线程 A 从 read() 返回，但操作了错误的 fd

延迟关闭的解决:
  1. 创建 marker fd (无效 fd)
  2. dup2(marker_fd, socket_fd)
  3. 原 socket 关闭，但 fd 数字仍指向无效 fd
  4. 线程 A 的 read() 立即返回 EBADF
  5. fd 不会被系统回收，安全
```

### Q3: 为什么 ServerSocket 默认启用 SO_REUSEADDR?

**答案**:
```
问题场景:
  Server 崩溃后立即重启
  原连接在 TIME_WAIT 状态
  bind() 返回 "Address already in use"

SO_REUSEADDR 作用:
  允许绑定处于 TIME_WAIT 状态的地址
  解决快速重启问题

注意: SO_REUSEADDR 不允许多个进程绑定同一地址
      (需要 SO_REUSEPORT)
```

### Q4: IPv6 双栈支持是如何实现的?

**答案**:
```
实现机制:
1. 创建 AF_INET6 socket
2. 设置 IPV6_V6ONLY = 0 (启用双栈)
3. IPv4 连接以 IPv4-Mapped IPv6 地址呈现

地址格式转换:
  IPv4 127.0.0.1 → IPv6 ::ffff:127.0.0.1

Java 层处理:
  检测到 IPv4-Mapped 地址
  创建 Inet4Address 而非 Inet6Address
  对应用透明
```

### Q5: SocketTimeoutException 是如何实现的?

**答案**:
```
实现机制:
1. 设置 socket 为非阻塞
2. 调用 poll/select 等待可读/可写
3. 超时返回 0，抛出 SocketTimeoutException

代码流程 (Read):
  NET_ReadWithTimeout(timeout):
    while (剩余超时 > 0):
      result = poll(fd, 等待可读, 剩余超时)
      if (result == 0): 抛出 SocketTimeoutException
      n = recv(fd, buf, len, MSG_DONTWAIT)
      if (n >= 0): 返回 n
      if (errno != EAGAIN): 抛出异常
      更新剩余超时时间
```

### Q6: SO_LINGER 选项的作用是什么?

**答案**:
```
控制 close() 行为:

不设置 SO_LINGER (默认):
  close() 立即返回
  内核在后台继续发送数据
  可能丢失未发送的数据

SO_LINGER {on, 0}:
  close() 立即返回
  丢弃未发送的数据
  发送 RST 强制关闭连接

SO_LINGER {on, n}:
  close() 阻塞最多 n 秒
  等待数据发送完成
  超时后强制关闭

使用场景:
  - 优雅关闭: SO_LINGER {on, 30}
  - 强制关闭: SO_LINGER {on, 0}
```

### Q7: 为什么 write() 需要循环调用 send()?

**答案**:
```
原因:
  send() 可能只发送部分数据
  原因包括:
    - 发送缓冲区已满
    - 被信号中断
    - 网络拥塞

标准模式:
  while (剩余数据 > 0):
    n = send(fd, buf + 偏移, 剩余长度, 0)
    if (n < 0): 错误处理
    剩余长度 -= n
    偏移 += n

Java 层保障:
  SocketOutputStream.write() 保证所有数据发送
  或抛出异常
```
