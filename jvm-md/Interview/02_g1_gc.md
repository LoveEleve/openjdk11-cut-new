## Q1: G1 GC 的整体架构是什么？⭐

### 一句话结论
G1 将堆划分为 **等大小的 Region**（默认 1~32MB），Region 动态扮演 Eden/Survivor/Old/Humongous 角色，通过 **选择性回收 (Collection Set)** 实现可控的停顿时间。

### 源码级回答

```
┌─────────────────────── G1 堆布局 (2048 Regions × 4MB = 8GB) ──────────────────┐
│ ┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐ │
│ │E ││E ││S0││O ││O ││H ││H ││H ││F ││E ││O ││O ││S1││F ││O ││E ││F ││O │ │
│ └──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘ │
│  E=Eden  S=Survivor  O=Old  H=Humongous(连续)  F=Free                       │
└──────────────────────────────────────────────────────────────────────────────┘
```

**Region 大小计算 (源码):**
```cpp
// HeapRegion::setup_heap_region_size()
target = MAX(初始堆, 最大堆) / TARGET_REGION_NUMBER(2048)
GrainBytes = 夹在 [1MB, 32MB] 的 2 的幂次
```

**三种 GC 模式:**
| 模式 | CSet 范围 | 触发条件 | STW |
|------|----------|---------|-----|
| Young GC | 所有 Eden + Survivor | Eden 满 | 是 |
| Mixed GC | Young + 部分 Old | 并发标记完成后 | 是 |
| Full GC | 整堆 | Old 空间不足/Evacuation 失败 | 是(最长) |

**核心组件:**
- **G1Policy**: 决策大脑（选哪些 Region 回收、回收多少能满足 pause target）
- **G1RemSet + CardTable**: 跨 Region 引用追踪
- **G1ConcurrentMark**: 并发标记（SATB 算法）
- **G1ConcurrentRefine**: 异步精炼脏卡

> 📖 详细文档: `Universe/D.4.1-G1Policy.md`, `G1-GC/8.6_G1Policy_Decision_Logic.md`

## Q2: Young GC 的完整流程是什么？⭐⭐

### 一句话结论
Young GC = **STW → Root 扫描 → RSet 扫描 → 对象复制(Evacuation) → 引用处理 → 清理 → 恢复**，全程 STW，多线程并行。

### 源码级回答

```
do_collection_pause_at_safepoint()
│
├── 1. STW 进入 (SafepointSynchronize::begin())
│
├── 2. CSet 选择 (G1Policy::finalize_collection_set())
│   └── 所有 Eden Region + Survivor Region
│   └── 根据 pause_target 决定是否加入 Old Region (Mixed GC 时)
│
├── 3. Evacuation 阶段 (并行, GangWorker)
│   ├── 3.1 Root 扫描
│   │   ├── 线程栈 (OopClosure 遍历每帧的 OopMap)
│   │   ├── JNI Handles
│   │   ├── ClassLoaderDataGraph
│   │   └── StringTable / Universe::oops_do
│   │
│   ├── 3.2 RSet 扫描 (G1RemSet::oops_into_collection_set_do)
│   │   └── 遍历 CSet 中每个 Region 的 RSet
│   │   └── 找到所有从 Old→Young 的引用
│   │
│   ├── 3.3 对象复制 (evacuate_object)
│   │   ├── 存活对象 → Survivor Region (age < threshold)
│   │   ├── 存活对象 → Old Region (age >= threshold 或 Survivor 满)
│   │   └── 使用 forwarding pointer (markWord 中) 重定向
│   │
│   └── 3.4 引用处理 (ReferenceProcessor)
│       └── 四种引用类型的清理
│
├── 4. 后处理
│   ├── Redirty logged cards
│   ├── Free CSet (回收 Eden Region)
│   ├── 调整 Young Region 数量
│   └── 更新统计数据 (G1Analytics)
│
└── 5. STW 退出
```

**关键数值 (8GB 堆, 标准配置):**
- Eden Region 数: ~600 个 (5% ~ 60% 堆)
- Survivor Region: 按需扩展
- 并行度: `-XX:ParallelGCThreads=8`
- 目标停顿: `-XX:MaxGCPauseMillis=200`

> 📖 详细文档: `G1-GC/8.3_Young_GC_Complete_Flow.md`, `YoungGC/YoungGC_Full_Process.md`

## Q3: RSet（Remembered Set）是什么？为什么需要它？⭐⭐

### 一句话结论
RSet 记录 **"谁引用了我这个 Region"**，让 Young GC 不需要扫描整个 Old 区，只扫描 RSet 中记录的 card 即可找到所有跨代引用。

### 源码级回答

**问题:** Young GC 只回收 Eden/Survivor，但 Old 区对象可能引用 Young 区对象 → 不扫描 Old 就会漏标。

**解法:** 每个 Region 维护一个 RSet，记录"哪些其他 Region 的哪些 card 有指向我的引用"。

**三层存储模式 (OtherRegionsTable):**
```
┌─────────── 稀疏模式 (SparsePRT) ──────────┐
│ 哈希表: RegionIdx → [card1, card2, ...]     │
│ 适用: 跨 Region 引用 < 4 个 card             │
├─────────── 细粒度模式 (PerRegionTable) ────┤
│ 位图: 每个 card 一个 bit (Region_size/512)   │
│ 适用: 同一个 Region 的多个 card 引用我        │
├─────────── 粗粒度模式 (Coarse Bitmap) ─────┤
│ 全局位图: 每个 Region 一个 bit                │
│ 适用: 太多 Region 引用我 → 标记整个 Region    │
└───────────────────────────────────────────┘
```

**自动升级:** Sparse 满 → 自动升级为 Fine → Fine 满 → 升级为 Coarse

**空间开销:** 默认约占堆的 5%~10%（`-XX:G1MaxRSetEntriesPerRegion` 控制）

> 📖 详细文档: `G1-GC/6_RememberedSet/2_three_storage_modes_detailed.md`

## Q4: G1 的写屏障是怎么工作的？⭐⭐⭐

### 一句话结论
G1 使用 **post-write barrier**（写后屏障），每次引用赋值后将对应 card 标脏并入队到 DirtyCardQueue，由 ConcurrentRefine 线程异步精炼更新 RSet。

### 源码级回答

**写屏障伪代码 (解释器版):**
```
obj.field = new_value;  // 原始赋值

// === post-write barrier ===
card_addr = card_table_base + (obj >> 9);  // 512 字节一个 card
if (*card_addr != dirty_card) {            // 避免重复标脏
    *card_addr = dirty_card;               // 标脏
    enqueue(card_addr);                    // 入队 DirtyCardQueue
}
```

**SATB pre-write barrier (并发标记期间):**
```
// 并发标记期间额外的前置屏障
old_value = obj.field;                     // 读旧值
if (marking_active) {
    satb_enqueue(old_value);               // 旧值入 SATB 队列
}
obj.field = new_value;                     // 赋值
```

**精炼线程 (ConcurrentRefine):**
```
while (true) {
    card = dequeue(DirtyCardQueue);
    region = card_to_region(card);
    // 扫描 card 内的所有对象引用
    for_each_reference_in_card(card) {
        target_region = object_region(ref);
        if (target_region != region) {
            target_region.rset.add(region, card);  // 更新 RSet
        }
    }
}
```

**精炼线程数量 & 三色阈值:**
```
Green → 0 个线程工作（队列短）
Yellow → 逐步激活线程（队列中等）
Red → 所有线程 + 应用线程协助（队列太长）
```

> 📖 详细文档: `G1-GC/8.4_CardTable_and_WriteBarrier_deep_dive.md`, `G1-GC/8.7_G1_Barrier_JIT_Version.md`

## Q5: 并发标记是怎么做的？什么是 SATB？⭐⭐

### 一句话结论
G1 使用 **Snapshot-At-The-Beginning (SATB)** 算法：在并发标记开始时对引用关系做快照，通过 pre-write barrier 捕获所有被覆盖的引用，保证不会漏标。

### 源码级回答

**并发标记 6 阶段:**
```
1. Initial Mark (STW) — 标记 GC Roots 直接可达的对象
   （搭载在 Young GC 上，不额外 STW）

2. Root Region Scan — 扫描 Survivor Region（它们引用的 Old 区对象需要标记）
   （并发，不 STW）

3. Concurrent Mark — 遍历整个引用图，用 _next_mark_bitmap 标记存活对象
   （并发，应用线程继续运行）

4. Remark (STW) — 处理 SATB 队列残留 + 引用处理
   （短暂 STW）

5. Cleanup (STW) — 统计每个 Region 的存活字节，排序回收价值
   （短暂 STW）

6. Concurrent Cleanup — 回收完全空的 Region
```

**SATB 原理:**
```
问题: 并发标记期间应用线程修改引用 → 可能漏标存活对象
解法: 在覆盖引用前，把旧值记录到 SATB buffer

示例:
  A.field = B;  // 并发标记前的快照: A→B
  ... 并发标记中 ...
  A.field = C;  // 应用线程修改! pre-barrier 记录 B 到 SATB buffer
  → 标记完成后处理 SATB buffer → B 被标记为存活 (保守但安全)
```

**IHOP (Initiating Heap Occupancy Percent):**
```
触发并发标记的条件:
Old 区占用 / 堆大小 >= IHOP 阈值

自适应 IHOP (-XX:+G1UseAdaptiveIHOP, 默认开):
  IHOP = old_used + buffer - old_allocation_rate × marking_duration
  → 根据历史数据动态调整，确保标记能在 Old 满之前完成
```

> 📖 详细文档: `G1-GC/8.2_G1_Concurrent_Mark_Complete_Flow.md`, `Universe/F.4-G1IHOPControl.md`

## Q6: Mixed GC 和 Young GC 有什么区别？⭐⭐

### 一句话结论
Mixed GC = Young GC + **部分 Old Region**，触发条件是并发标记完成后 G1Policy 判断 Old 区有可回收的垃圾。

### 源码级回答

**触发条件:**
```cpp
// G1Policy::next_gc_should_be_mixed()
return _collection_set->candidates() != nullptr
    && _collection_set->candidates()->old_candidates_remaining() > 0;
```

**CSet 选择策略 (G1Policy):**
```
1. 固定加入: 所有 Eden + Survivor
2. 可选加入: 按 gc_efficiency (回收字节/回收耗时) 排序的 Old Region
3. 约束:
   - 最多加入 `-XX:G1OldCSetRegionThresholdPercent=10%` 的 Old Region
   - 总停顿不超过 MaxGCPauseMillis
   - 只加入存活比例 < `-XX:G1MixedGCLiveThresholdPercent=85%` 的 Region
```

**Mixed GC 轮次:**
```
并发标记完成后 → 连续若干次 Mixed GC → 直到:
- Old 候选 Region 用完
- 或 Old 区回收比例达到 G1HeapWastePercent(5%)
```

> 📖 详细文档: `G1-GC/8.5_Mixed_GC_Complete_Flow.md`

## Q7: G1 的 Full GC 是怎么回事？什么时候触发？⭐⭐

### 一句话结论
G1 Full GC 是**单线程**的 Mark-Compact（JDK 11），效率极低，通常意味着 GC 调优失败。

### 源码级回答

**触发条件:**
1. **Evacuation Failure**: Young/Mixed GC 时没有足够的 Region 存放存活对象
2. **Humongous 分配失败**: 找不到足够的连续 Region
3. **并发标记跟不上分配速度**: Old 满了但标记还没完成
4. `System.gc()` + `-XX:-ExplicitGCInvokesConcurrent`

**Full GC 四阶段:**
```
Phase 1: Mark — 从 GC Roots 标记所有存活对象
Phase 2: Compute Forward — 计算压缩后的新地址
Phase 3: Adjust Pointers — 调整所有引用指向新地址
Phase 4: Compact — 物理移动对象到新位置
```

**为什么慢:**
- **单线程** (JDK 10+ 改为并行，但 JDK 11 的 Full GC 已支持 `-XX:ParallelGCThreads`)
- 整堆遍历，所有 Region 都参与
- 对象移动 → 所有引用都要更新

**预防措施:**
```
-XX:MaxGCPauseMillis=200      # 合理的暂停目标
-XX:G1ReservePercent=10       # 预留空间防止 Evacuation Failure
-XX:ConcGCThreads=N           # 并发标记线程数
-XX:G1HeapWastePercent=5      # 不要太早停止 Mixed GC
```

> 📖 详细文档: `G1-GC/5_Full_GC_detailed_analysis.md`

## Q8: G1 怎么保证停顿时间可控？⭐⭐⭐

### 一句话结论
G1Policy 基于 **历史 GC 数据的衰减平均** 预测每个 Region 的回收耗时，贪心选择 gc_efficiency 最高的 Region 组成 CSet，直到预测停顿达到 MaxGCPauseMillis。

### 源码级回答

**预测模型 (G1Analytics + TruncatedSeq):**
```
每次 GC 后记录:
  - eden_region_scan_time    (每 Region 扫描耗时)
  - survivor_region_scan_time
  - old_region_scan_time
  - rs_scan_time            (RSet 扫描耗时)
  - object_copy_time        (对象复制耗时)
  ...

预测公式:
  predicted_pause = fixed_cost
    + eden_count × predict(eden_scan_seq)
    + survivor_count × predict(survivor_scan_seq)
    + Σ(old_region_i) × predict(old_scan_seq)
    + ...
```

**衰减平均:**
```
TruncatedSeq: 保留最近 N 个样本
sigma = 0.5 (衰减因子)
predicted = davg + sigma × dsd
→ 新数据权重大，旧数据权重指数衰减
→ 预测值偏保守 (平均值 + 标准差)
```

**CSet 选择算法:**
```cpp
// finalize_old_cset_part()
while (remaining_time > 0 && has_more_candidates) {
    region = next_candidate();  // 按 gc_efficiency 排序
    predicted_time = predict_region_time(region);
    if (predicted_time <= remaining_time) {
        add_to_cset(region);
        remaining_time -= predicted_time;
    }
}
```

**MMU (Minimum Mutator Utilization) 保护:**
```
确保在任意 200ms 窗口内，应用线程至少有一定比例的运行时间
→ 即使 GC 频繁，也不会连续 STW
```

> 📖 详细文档: `G1-GC/8.6_G1Policy_Decision_Logic.md`, `Universe/F.1-G1Predictions.md`, `Universe/F.2-G1Analytics.md`

## Q9: CardTable 是什么？和 RSet 是什么关系？⭐⭐

### 一句话结论
CardTable 是**全局的字节数组**，每 512 字节堆内存对应 1 个 byte（card），用于追踪"哪些区域被修改过"。RSet 是**每个 Region 的精确记录**，由 Refine 线程根据 CardTable 的脏卡精炼而来。

### 源码级回答

```
┌─────── 堆内存 ────────────────────────────────┐
│ card0(512B) │ card1(512B) │ card2(512B) │ ...  │
└─────────────────────────────────────────────────┘
      ↓              ↓              ↓
┌─────── CardTable ──────────────────────────────┐
│   clean    │   dirty    │   clean    │ ...      │
│   (0x00)   │   (0x00)   │   (0x00)   │          │
└─────────────────────────────────────────────────┘

写屏障: obj.field = ref → card_table[obj >> 9] = dirty
精炼:   Refine 线程取脏卡 → 扫描 card 内对象 → 更新目标 Region 的 RSet
```

**CardTable vs RSet 的关系:**
```
CardTable: 全局, 回答 "哪些 card 被修改了" (O(1) 标脏)
    ↓ Refine 线程精炼
RSet: per-Region, 回答 "谁引用了我这个 Region" (GC 时 O(1) 查询)
```

**为什么需要两层?**
- 写屏障要快 → CardTable 只需一次内存写
- GC 扫描要精确 → RSet 记录精确的 Region→card 映射
- 异步精炼解耦: 应用线程只标脏卡，Refine 线程后台更新 RSet

> 📖 详细文档: `G1-GC/8.4_CardTable_and_WriteBarrier_deep_dive.md`, `G1-GC/6_RememberedSet/3_g1cardtable_mechanism.md`

## Q10: JIT 编译后的写屏障和解释器版有什么区别？⭐⭐⭐

### 一句话结论
C1/C2 编译的写屏障会做**更多优化**：条件过滤（young→young 不标脏）、自身 Region 过滤、card 已脏检查，减少不必要的入队操作。

### 源码级回答

**解释器版 (简单):**
```
card = card_table + (field_addr >> 9);
*card = dirty;
enqueue(card);
```

**C2 JIT 版 (优化):**
```
// 1. 空值过滤
if (new_value == null) return;

// 2. 自身 Region 过滤
if (obj XOR new_value) >> RegionSizeShift == 0) return; // 同 Region

// 3. 标脏 + 检查是否已脏
card = card_table + (field_addr >> 9);
if (*card == g1_young_card) return;  // Young Region 不需要
old = *card;
*card = dirty;
if (old == dirty) return;  // 已经脏了，不重复入队

// 4. 入队
dirty_card_queue.enqueue(card);
```

**优化效果:**
- Young→Young 赋值: 直接跳过（同 Region 或 young card 过滤）
- 已脏 card: 不重复入队（减少队列压力）
- null 赋值: 不需要屏障

> 📖 详细文档: `G1-GC/8.7_G1_Barrier_JIT_Version.md`

## Q11: G1 调优你会关注哪些参数？⭐⭐

### 一句话结论
核心 4 个: **MaxGCPauseMillis**(停顿目标), **G1HeapRegionSize**(Region 大小), **InitiatingHeapOccupancyPercent**(IHOP), **G1ReservePercent**(预留空间)。

### 源码级回答

**第一梯队 (必须知道):**
| 参数 | 默认值 | 作用 |
|------|--------|------|
| `-XX:MaxGCPauseMillis` | 200ms | GC 暂停时间目标 |
| `-XX:G1HeapRegionSize` | 自动(1~32MB) | Region 大小 |
| `-XX:InitiatingHeapOccupancyPercent` | 45% | 触发并发标记的阈值 |
| `-XX:G1ReservePercent` | 10% | 预留空间防 Evacuation Failure |

**第二梯队 (进阶调优):**
| 参数 | 默认值 | 作用 |
|------|--------|------|
| `-XX:G1MixedGCLiveThresholdPercent` | 85% | Old Region 存活率阈值 |
| `-XX:G1OldCSetRegionThresholdPercent` | 10% | Mixed GC 每次最多选多少 Old |
| `-XX:G1MixedGCCountTarget` | 8 | Mixed GC 目标轮次 |
| `-XX:G1HeapWastePercent` | 5% | 可容忍的堆浪费比例 |
| `-XX:ConcGCThreads` | ParallelGCThreads/4 | 并发标记线程数 |
| `-XX:ParallelGCThreads` | CPU 核数 | 并行 GC 线程数 |

**调优场景实例:**
```
# 大对象过多 → Region 太小
-XX:G1HeapRegionSize=16m

# 频繁 Full GC → 并发标记太晚
-XX:InitiatingHeapOccupancyPercent=35

# Evacuation Failure → 预留空间不够
-XX:G1ReservePercent=20

# Mixed GC 太慢 → 减少每次回收量
-XX:G1MixedGCCountTarget=16
```

> 📖 详细文档: `G1-GC/7.1~7.7` 调优参数全系列

## Q12: GC 日志怎么看？关键信息在哪？⭐⭐

### 一句话结论
JDK 11 使用 `-Xlog:gc*=info` 统一日志框架，关键看 **Pause Young/Mixed/Full** 的总耗时、各子阶段耗时、堆变化。

### 源码级回答

**推荐日志配置:**
```
-Xlog:gc*=info,gc+phases=debug,gc+heap=debug:gc.log:time,uptime,level,tags
```

**Young GC 日志解读:**
```
[gc,start    ] GC(0) Pause Young (Normal) (G1 Evacuation Pause)
[gc,phases   ] GC(0)   Pre Evacuate Collection Set: 0.1ms    ← 准备阶段
[gc,phases   ] GC(0)   Evacuate Collection Set: 15.2ms       ← 核心! 对象复制
[gc,phases   ] GC(0)     Ext Root Scanning: 1.2ms            ← Root 扫描
[gc,phases   ] GC(0)     Scan RS: 0.5ms                      ← RSet 扫描
[gc,phases   ] GC(0)     Object Copy: 12.3ms                 ← 对象复制
[gc,phases   ] GC(0)   Post Evacuate Collection Set: 1.1ms   ← 后处理

```

**问题诊断模式:**
| 症状 | 看什么 | 可能原因 |
|------|--------|---------|
| STW 长 | Evacuate Collection Set 耗时 | 存活对象多/RSet 大 |
| 频繁 Full GC | 日志中出现 "Pause Full" | IHOP 太高/分配速率太快 |
| Real >> User | Pause 行的 real 时间 | 系统 IO 或 swap |
| User >> Real | Pause 行的 user 时间 | GC 线程数合理 (并行) |

## Q13: G1 和 CMS 的核心区别是什么？⭐

### 一句话结论
G1 是 **Region 化 + 选择性回收 + 压缩**，CMS 是**分代 + 并发标记清除 + 不压缩**。G1 停顿可控，CMS 碎片化。

### 源码级回答

| 对比维度 | G1 | CMS |
|---------|----|----|
| 堆布局 | Region (动态分代) | 固定 Young/Old |
| Old GC 算法 | Evacuation (复制压缩) | Mark-Sweep (不压缩) |
| 碎片化 | 每次 GC 都压缩 | 严重碎片化 → Full GC |
| 停顿控制 | MaxGCPauseMillis 预测模型 | 尽力而为 |
| 写屏障 | CardTable + SATB + RSet | CardTable + Incremental Update |
| 并发标记 | SATB (快照) | Incremental Update (增量更新) |
| Remark 停顿 | 短 (SATB 只处理旧值) | 可能长 (需要重新扫描被修改区域) |
| 大对象 | Humongous Region | 直接分配 Old (可能碎片) |

> 📖 详细文档: 分散在 G1-GC 全系列中

## Q14: 什么是 Evacuation Failure？怎么避免？⭐⭐⭐

### 一句话结论
Evacuation Failure 是 GC 复制存活对象时**没有足够的空闲 Region**，导致部分对象无法移动，被原地"钉住"(pinned)，是 G1 最糟糕的情况，通常触发 Full GC。

### 源码级回答

**触发条件:**
```
Evacuation 过程中:
1. 从 FreeRegionList 申请新 Region → 失败
2. G1ReservePercent 的预留空间也用完
3. → Evacuation Failure!
```

**后果:**
```
1. 未能复制的对象原地不动，Region 标记为 "pinned"
2. 这些对象的引用需要自修复 (self-forwarding)
3. 当前 GC 效果打折 → 下次可能触发 Full GC
4. Full GC 单线程压缩 → 长时间 STW
```

**预防措施:**
```
1. -XX:G1ReservePercent=15~20  # 增加预留空间
2. -XX:MaxGCPauseMillis=300    # 放宽停顿目标 → 每次回收更多
3. -XX:ConcGCThreads=N         # 增加并发标记线程 → 更快完成标记
4. -XX:InitiatingHeapOccupancyPercent=35 # 更早触发并发标记
5. 减少大对象分配 (避免 Humongous 碎片)
```

> 📖 详细文档: `Universe/E.5.2-E.5.3-StealAndEvacFailed.md`
