## 1. 功能定位

### 1.1 一句话概述

**Phase 3 的核心目标**：将 JVM 内部的 JavaThread C++ 对象与操作系统的原生线程（pthread）关联起来，建立完整的线程管理体系。

### 1.2 整体流程位置

```
Threads::create_vm()
├── Phase 1-2: JVM 初始化...
├── ★ Phase 3: 主线程创建与附加
│   ├── 3.1 new JavaThread()              ← 创建 JavaThread 对象
│   ├── 3.2 set_thread_state(_thread_in_vm)
│   ├── 3.3 initialize_thread_current()    ← TLS 绑定（核心）
│   ├── 3.4 record_stack_base_and_size()
│   ├── 3.5 register_thread_stack_with_NMT()
│   ├── 3.6 set_active_handles()
│   ├── 3.7 set_as_starting_thread()       ← 创建 OSThread（核心）
│   ├── 3.8 create_stack_guard_pages()
│   └── 3.9 ObjectMonitor::Initialize()
├── Phase 4: init_globals()
└── ...
```

### 1.3 如果没有 Phase 3 会怎样？

- JVM 无法知道当前运行在哪个线程上
- `Thread::current()` 无法工作，导致整个 JVM 崩溃
- 无法进行安全点检查（因为不知道有哪些 Java 线程）
- 无法进行 GC（因为无法遍历线程栈）

### 2.1 三层结构的关系总结

| 层次 | 对象类型 | 分配位置 | 创建方式 | 主要用途 |
|------|---------|---------|---------|---------|
| Java 层 | java.lang.Thread | Java Heap | `new Thread()` | Java 程序员使用 |
| JVM 层 | JavaThread | Native Heap | `new JavaThread()` | JVM 内部管理 |
| OS 层 | OSThread + pthread | Native Heap + 内核 | `os::create_thread()` | 真正的执行单元 |

### 2.2 为什么需要三层结构？

1. **解耦**: Java 层不需要知道 JVM 实现细节，JVM 层不需要知道 OS 细节
2. **可移植性**: OSThread 封装了平台差异，JavaThread 保持跨平台一致
3. **功能分离**: 
   - Java 层管理业务逻辑（优先级、名称、daemon 等）
   - JVM 层管理运行时状态（安全点、GC 支持等）
   - OS 层管理真正的执行（调度、上下文切换等）

### 4.2 核心字段详解

#### 4.2.1 `_threadObj` - Java 层连接 ⭐⭐⭐⭐

```
字段：_threadObj (oop 类型)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【是什么】
  指向 java.lang.Thread 对象的 oop（ordinary object pointer）

【为什么需要】
  问题：JVM 需要知道这个 C++ 线程对应哪个 Java 层的 Thread 对象
  解决：通过 _threadObj 建立 C++ → Java 的引用

【怎么用】
  读取：当需要获取线程名、优先级、daemon 等 Java 属性时
  写入：create_initial_thread() 创建 java.lang.Thread 后设置
  
【示例代码】
  // 获取线程名
  oop name = java_lang_Thread::name(thread->threadObj());
  
  // 判断是否是 daemon 线程
  bool is_daemon = java_lang_Thread::is_daemon(thread->threadObj());

【特殊值】
  NULL：主线程在 Phase 3 时 _threadObj 为 NULL（尚未创建 Java 对象）
        后续在 Phase 5 create_initial_thread() 时设置

【GC 注意】
  _threadObj 是 oop，GC 时需要扫描
  GC 移动对象后，_threadObj 指针会被自动更新
```

#### 4.2.2 `_thread_state` - 线程状态 ⭐⭐⭐⭐

```
字段：_thread_state (JavaThreadState 枚举)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【是什么】
  表示线程当前正在执行什么类型的代码

【状态定义】
  enum JavaThreadState {
    _thread_uninitialized     =  0,  // 未初始化
    _thread_new               =  2,  // 刚创建
    _thread_new_trans         =  3,  // new → in_native 转换中
    _thread_in_native         =  4,  // 执行 Native 代码
    _thread_in_native_trans   =  5,  // native → vm/java 转换中
    _thread_in_vm             =  6,  // 执行 VM 代码 (HotSpot C++)
    _thread_in_vm_trans       =  7,  // vm → java/native 转换中
    _thread_in_Java           =  8,  // 执行 Java 代码
    _thread_in_Java_trans     =  9,  // java → vm/native 转换中
    _thread_blocked           = 10,  // 阻塞状态
    _thread_blocked_trans     = 11   // blocked → 其他 转换中
  };

【状态转换图】
                    ┌─────────────────┐
                    │  _thread_new    │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
          ┌─────────┤ _thread_in_vm   ├─────────┐
          │         └────────┬────────┘         │
          │                  │                  │
  ┌───────▼───────┐  ┌───────▼───────┐  ┌───────▼───────┐
  │_thread_in_Java│  │_thread_blocked │  │_thread_in_native│
  └───────────────┘  └────────────────┘  └─────────────────┘

【为什么需要 _trans 状态？】
  安全点检查！当线程处于转换状态时：
  - 表示线程正在切换执行环境
  - VMThread 可以安全地停止该线程
  - 如果直接切换，可能在不安全的位置停止

【怎么用】
  // 切换到 VM 状态
  thread->set_thread_state(_thread_in_vm);
  
  // 安全点检查时，检查是否在安全状态
  if (thread->thread_state() == _thread_in_Java) {
    // 需要等待线程到达安全点
  }
```

#### 4.2.3 `_anchor` - Java 栈帧锚点 ⭐⭐⭐

```
字段：_anchor (JavaFrameAnchor 类型)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【是什么】
  记录最后一个 Java 栈帧的位置，用于栈遍历

【结构】
  class JavaFrameAnchor {
    intptr_t* _last_Java_sp;  // 最后 Java 帧的栈指针 (SP)
    address   _last_Java_pc;  // 最后 Java 帧的程序计数器 (PC)
    intptr_t* _last_Java_fp;  // 最后 Java 帧的帧指针 (FP) - 仅某些平台
  };

【为什么需要】
  问题：当线程执行 Native/VM 代码时，如何找到 Java 栈帧？
  解决：在离开 Java 代码时保存锚点，通过锚点可以遍历整个 Java 栈

【使用场景】
  - GC 扫描线程栈时，需要找到所有 Java 栈帧
  - 生成堆栈跟踪（stack trace）
  - 异常处理时展开栈帧
```

### 5.2 _thread_id vs _pthread_id

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    两种线程 ID 的区别                                            │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                   │
│  _thread_id (pid_t / thread_id_t)                                                │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━   │
│  - 获取方式: gettid() 系统调用 (或 syscall(SYS_gettid))                          │
│  - 含义: 内核线程 ID (Light Weight Process ID)                                   │
│  - 用途:                                                                         │
│    * /proc/<pid>/task/<tid> 访问线程信息                                         │
│    * perf/strace 等工具显示                                                      │
│    * futex 等内核接口使用                                                        │
│  - 特点: 在整个系统中唯一                                                        │

## 6. TLS 绑定机制 - Thread::current() 的秘密 ⭐⭐⭐⭐

### 6.1 问题背景

```
核心问题：在 JVM 的任意位置，如何快速获取当前线程的 JavaThread 对象？

场景示例：
  - GC 需要知道当前线程的 TLAB
  - 安全点需要检查当前线程状态
  - JNI 需要获取当前线程的 Handle
  - 异常处理需要访问当前线程的异常状态

难点：
  - 不能每次都遍历线程列表（太慢）
  - 不能用全局变量（多线程不安全）
  - 需要 O(1) 时间复杂度
```

### 6.2 解决方案：Thread Local Storage (TLS)

```

│                        TLS 工作原理                                              │
├─────────────────────────────────────────────────────────────────────────────────┤

### 6.3 源码实现分析

#### 6.3.1 TLS 初始化

```cpp
// 源码位置: src/hotspot/os/posix/threadLocalStorage_posix.cpp

static pthread_key_t _thread_key;   // 全局 TLS key
static bool _initialized = false;

void ThreadLocalStorage::init() {
    assert(!_initialized, "initializing TLS more than once!");
    
    // 创建 TLS key，指定析构函数
    int rslt = pthread_key_create(&_thread_key, restore_thread_pointer);
    assert_status(rslt == 0, rslt, "pthread_key_create");
    
    _initialized = true;
}
```

#### 6.3.2 TLS 绑定（核心！）

```cpp
// 源码位置: src/hotspot/share/runtime/thread.cpp:346-354

void Thread::initialize_thread_current() {
#ifndef USE_LIBRARY_BASED_TLS_ONLY
    // 方式1: 编译器 TLS (__thread 修饰符，更快)
    assert(_thr_current == NULL, "Thread::current already initialized");
    _thr_current = this;  // 将 JavaThread 指针存入编译器 TLS
#endif
    
    // 方式2: 库函数 TLS (pthread_setspecific，兼容性好)
    assert(ThreadLocalStorage::thread() == NULL, "already initialized");
    ThreadLocalStorage::set_thread(this);  // 存入 pthread TLS
    
    assert(Thread::current() == ThreadLocalStorage::thread(), "TLS mismatch!");
}
```

#### 6.3.3 获取当前线程

```cpp
// 源码位置: src/hotspot/share/runtime/thread.hpp:768-782

inline Thread* Thread::current() {
    Thread* current = current_or_null();
    assert(current != NULL, "Thread::current() called on detached thread");
    return current;
}

inline Thread* Thread::current_or_null() {
#ifndef USE_LIBRARY_BASED_TLS_ONLY
    // 优先使用编译器 TLS（更快，单条指令）
    return _thr_current;
#else
    // 使用 pthread TLS
    if (ThreadLocalStorage::is_initialized()) {
        return ThreadLocalStorage::thread();
    }
    return NULL;
#endif
}

// pthread TLS 实现
Thread* ThreadLocalStorage::thread() {
    return (Thread*) pthread_getspecific(_thread_key);
}
```

### 6.4 两种 TLS 实现对比

| 特性 | 编译器 TLS (`__thread`) | 库函数 TLS (`pthread_*`) |
|------|------------------------|-------------------------|
| 声明方式 | `static __thread Thread* _thr_current;` | `pthread_key_create()` |
| 读取方式 | 直接读取（单条指令） | `pthread_getspecific()` |
| 写入方式 | 直接赋值 | `pthread_setspecific()` |
| 性能 | ⭐⭐⭐⭐⭐ 最快 | ⭐⭐⭐ 较慢（函数调用） |
| 兼容性 | 需要编译器支持 | 所有 POSIX 系统 |
| 信号安全 | 是 | 理论上不是，实际上是 |

bool Thread::set_as_starting_thread() {

// 源码位置: src/hotspot/os/linux/os_linux.cpp:1063-1100

bool os::create_main_thread(JavaThread* thread) {
    assert(os::Linux::_main_thread == pthread_self(), 
           "should be called inside main thread");
    return create_attached_thread(thread);
}

bool os::create_attached_thread(JavaThread* thread) {
    // 步骤 1: 创建 OSThread 对象
    OSThread* osthread = new OSThread(NULL, NULL);
    if (osthread == NULL) {
        return false;
    }

    // 步骤 2: 设置线程 ID
    osthread->set_thread_id(os::Linux::gettid());   // 内核线程 ID
    osthread->set_pthread_id(::pthread_self());      // pthread ID

    // 步骤 3: 初始化浮点控制寄存器
    os::Linux::init_thread_fpu_state();

    // 步骤 4: 设置状态为 RUNNABLE
    osthread->set_state(RUNNABLE);

    // 步骤 5: 关联 JavaThread 和 OSThread ★
    thread->set_osthread(osthread);

    // 步骤 6: NUMA 相关（可选）
    if (UseNUMA) {
        int lgrp_id = os::numa_get_group_id();
        if (lgrp_id != -1) {
            thread->set_lgrp_id(lgrp_id);
        }
    }

    return true;
}

## 8. 面试高频问题 ⭐⭐⭐⭐

### Q1: JavaThread 和 java.lang.Thread 是什么关系？

**答案**：
- `JavaThread` 是 JVM 内部的 C++ 对象，分配在 Native Heap
- `java.lang.Thread` 是 Java 层的对象，分配在 Java Heap
- 它们是一一对应的关系
- `JavaThread` 通过 `_threadObj` 字段指向对应的 `java.lang.Thread`
- `java.lang.Thread` 通过 `eetop` 字段（通过 Unsafe）可以获取对应的 `JavaThread`

### Q2: Thread::current() 是如何实现的？为什么能快速获取当前线程？

**答案**：
- 使用 Thread Local Storage (TLS) 机制
- 每个 OS 线程有独立的 TLS 存储空间
- JVM 在 TLS 中存储该线程对应的 JavaThread 指针
- Linux 上通过 `pthread_getspecific()` 获取（或编译器 `__thread`）
- 时间复杂度 O(1)，非常高效

### Q3: OSThread 和 JavaThread 有什么区别？

**答案**：

| 对比项 | JavaThread | OSThread |
|--------|-----------|----------|
| 抽象层次 | JVM 层 | OS 层 |
| 主要职责 | Java 执行状态、安全点、GC 支持 | 线程 ID、中断标志、平台相关信息 |
| 平台相关 | 跨平台一致 | 包含平台特有字段 |
| 继承关系 | Thread → JavaThread | CHeapObj |

### Q4: 为什么需要 _thread_state 的 _trans 中间状态？

**答案**：
- 为了支持安全点机制
- 当线程在 Java ↔ VM ↔ Native 之间切换时，需要经过转换状态
- 转换状态表示线程正在切换，此时可以安全地停止
- 如果没有转换状态，线程可能在不安全的位置被停止

### Q5: 一个 Java 线程在 JVM 内部对应几个对象？

**答案**：
通常对应 3 个对象：
1. `java.lang.Thread` - Java 层对象
2. `JavaThread` - JVM C++ 对象
3. `OSThread` - OS 层 C++ 对象

加上 OS 层的 pthread 实体，共 4 层结构。
