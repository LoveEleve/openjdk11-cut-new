## 为什么要读懂 GC 日志？

GC 日志是 JVM 运行状态的"心电图"——它能告诉你：
- 应用是否存在**内存泄漏**（堆使用量持续增长）
- GC 停顿是否超过 SLA（P99 要求 < 200ms？）
- **哪个阶段最慢**（根扫描？对象复制？引用处理？）
- 是否触发了**不该触发的 Full GC**
- **并发标记**是否正常工作

**不能只看工具**（如 GCViewer/GCEasy），因为：
1. 工具给出的是聚合数据，隐藏了细节
2. 异常情况往往需要逐行分析日志
3. 面试中会直接给你一段日志让你分析

## 一、JDK 11 统一日志框架（Unified Logging）

### 1.1 -Xlog 语法

JDK 9+ 用 `-Xlog` 替代了老版本的 `-XX:+PrintGCDetails` 等参数。

```
-Xlog:<what>:<output>:<decorators>:<output-options>
       ─┬──   ──┬───   ────┬──────  ─────┬─────────
        │       │         │             │
        │       │         │             └─ filecount=5,filesize=1m
        │       │         └─ time,level,tags,uptime,pid,tid
        │       └─ stdout / stderr / file=gc.log
        └─ gc*=info / gc+phases=debug / ...
```

**what** 部分格式：`<tag-set>[=<level>][,<tag-set>[=<level>]...]`

### 1.2 常用组合

| 命令 | 效果 | 等价旧参数 |
|------|------|-----------|
| `-Xlog:gc` | 基本 GC 信息（一行摘要） | `-XX:+PrintGC` |
| `-Xlog:gc*` | GC 所有标签的 info 级别 | `-XX:+PrintGCDetails` |
| `-Xlog:gc*=debug` | GC 所有标签的 debug 级别 | 无直接等价 |
| `-Xlog:gc*=trace` | GC 所有标签的 trace 级别（最详细） | 无直接等价 |
| `-Xlog:gc*=info:file=gc.log:time` | 写入文件，带时间戳 | `-Xloggc:gc.log -XX:+PrintGCDateStamps` |
| `-Xlog:gc+phases=debug` | 只看阶段计时 | 部分等价 `-XX:+PrintGCDetails` |
| `-Xlog:gc+heap=info` | 只看堆变化 | 无 |

### 1.3 日志级别

```
trace → debug → info → warning → error → off
  ↑                                         ↑
最详细（worker 级别每线程数据）          完全关闭
```

> **源码**: `logLevel.hpp` 定义了 `LogLevel::Trace/Debug/Info/Warning/Error` 五个级别

### 1.4 G1 日志标签体系

G1 使用以下标签组合输出日志：

| 标签组合 | 含义 | 级别 |
|---------|------|------|
| `[gc]` | GC 一行摘要（类型+堆变化+耗时） | info |
| `[gc,start]` | GC 开始标记 | info |
| `[gc,task]` | Worker 线程数量 | info |
| `[gc,phases]` | **阶段计时**（最重要！） | info/debug |
| `[gc,phases,task]` | 每个 worker 的阶段计时 | trace |
| `[gc,phases,ref]` | 引用处理详情 | debug |
| `[gc,heap]` | 堆区域变化（Eden/Survivor/Old/Humongous） | info |
| `[gc,heap,exit]` | JVM 退出时的堆摘要 | info |
| `[gc,metaspace]` | Metaspace 变化 | info |
| `[gc,cpu]` | CPU 时间（User/Sys/Real） | info |
| `[gc,marking]` | 并发标记阶段 | info |
| `[gc,age]` | 年龄分布和晋升阈值 | debug |
| `[gc,alloc,region]` | Region 分配/回收详情 | debug |
| `[gc,ergo]` | 自适应策略决策 | debug |
| `[gc,ergo,cset]` | Collection Set 选择决策 | debug |
| `[gc,ergo,ihop]` | IHOP（Initial Heap Occupancy Percent）决策 | debug |
| `[gc,task,stats]` | Worker 线程统计表 | debug |
| `[gc,tlab]` | TLAB 统计 | debug |
| `[gc,refine]` | Refinement 线程统计 | debug |
| `[gc,verify]` | 堆验证信息 | info |

### 1.5 Decorator 装饰器

```
[0.010s]        ← uptime: 从 JVM 启动到现在的秒数（默认开启）
[info]          ← level: 日志级别
[gc,heap]       ← tags: 日志标签
[2024-01-15T10:30:00.123+0800] ← time: ISO 8601 时间戳（需要手动开启）
[pid12345]      ← pid: 进程 ID
[tid0x7f...]    ← tid: 线程 ID
```

**推荐生产环境**：
```
-Xlog:gc*=info:file=gc-%t.log:time,uptime,level,tags:filecount=10,filesize=100m
```

### 逐行解读：

#### 第 1 行：GC 开始


**源码对应**：`g1CollectedHeap.cpp:3605`
```cpp
FormatBuffer<> gc_string("Pause Young ");
if (collector_state()->in_initial_mark_gc()) {
    gc_string.append("(Concurrent Start)");   // 并发标记初始标记
} else if (collector_state()->in_young_only_phase()) {
    if (collector_state()->in_young_gc_before_mixed()) {
        gc_string.append("(Prepare Mixed)");  // 准备 Mixed GC
    } else {
        gc_string.append("(Normal)");          // 普通 Young GC

} else {

}

```

**GC 原因**来自 `GCCause::to_string()`（`gcCause.cpp`）：

| 日志中的原因字符串 | 枚举值 | 含义 |
|-------------------|--------|------|
| `G1 Evacuation Pause` | `_g1_inc_collection_pause` | Eden 满触发 |
| `G1 Humongous Allocation` | `_g1_humongous_allocation` | 大对象分配触发 |
| `System.gc()` | `_java_lang_system_gc` | 代码调用 System.gc() |
| `Allocation Failure` | `_allocation_failure` | 分配失败 |
| `Metadata GC Threshold` | `_metadata_GC_threshold` | Metaspace 阈值触发 |
| `GCLocker Initiated GC` | `_gc_locker` | JNI 临界区释放后触发 |
| `Diagnostic Command` | `_dcmd_gc_run` | jcmd GC.run 触发 |

**Young GC 子类型决策树**：
```
collector_state()->in_initial_mark_gc()?
├── 是 → "(Concurrent Start)"    — 这次 Young GC 同时完成并发标记的初始标记
└── 否 → collector_state()->in_young_only_phase()?
    ├── 是 → in_young_gc_before_mixed()?
    │   ├── 是 → "(Prepare Mixed)"  — 并发标记刚完成，下一次将是 Mixed GC
    │   └── 否 → "(Normal)"         — 最普通的 Young GC
    └── 否 → "(Mixed)"              — 混合回收（Young + 部分 Old）
```

```

                                │              └─ 总 GC 线程数（ParallelGCThreads）
```

```cpp
  out->print(" Min: %4.1lf, Avg: %4.1lf, Max: %4.1lf, Diff: %4.1lf",
             min * MILLIUNITS, avg * MILLIUNITS, max * MILLIUNITS, diff * MILLIUNITS);
```

**关键指标**：如果 `Diff` 很大，说明 Worker 负载不均衡，可能某个 Region 的对象存活率特别高。

**各子阶段含义**：

| 子阶段 | 含义 | 关注点 |
|--------|------|--------|
| **Ext Root Scanning** | 扫描 GC Roots（Thread/JNI/StringTable/CLDG 等） | 线程多则耗时长 |
| **Update RS** | 处理 Dirty Card Queue 更新 RemSet | 如果很大，Refinement 线程跟不上 |
| **Scan RS** | 扫描 RemSet 找跨 Region 引用 | 老年代引用年轻代越多越慢 |
| **Code Root Scanning** | 扫描 nmethod 中的嵌入引用 | JIT 编译代码多则慢 |
| **Object Copy** | **对象疏散（复制到 Survivor/Old）** | **通常是最耗时的！** |
| **Termination** | Worker 等待其他 Worker 完成 | Diff 大→负载不均 |
| **GC Worker Other** | 杂项（= Total - 已知阶段之和） | 通常很小 |
| **GC Worker Total** | 单个 Worker 总耗时 | Diff 小→均衡好 |

**Mixed GC 与 Normal Young GC 的区别**：
1. 类型标记为 `(Mixed)` 而非 `(Normal)`

4. 可能需要多轮 Mixed GC 才能回收完（由 `G1MixedGCCountTarget` 控制，默认 8 轮）

## 五、Full GC 日志

Full GC 是 G1 的"最后手段"，使用 Serial Old GC 算法，STW 非常长。

```
[15.000s][info][gc,start       ] GC(30) Pause Full (Allocation Failure)
[15.000s][info][gc,phases,start] GC(30) Phase 1: Mark live objects
[17.800s][info][gc,phases      ] GC(30) Phase 1: Mark live objects 2800.123ms
[17.800s][info][gc,phases,start] GC(30) Phase 2: Prepare for compaction
[18.700s][info][gc,phases      ] GC(30) Phase 2: Prepare for compaction 900.456ms
[18.700s][info][gc,phases,start] GC(30) Phase 3: Adjust pointers
[20.200s][info][gc,phases      ] GC(30) Phase 3: Adjust pointers 1500.789ms
[20.200s][info][gc,phases,start] GC(30) Phase 4: Compact heap
[21.400s][info][gc,phases      ] GC(30) Phase 4: Compact heap 1200.234ms
[21.400s][info][gc,heap        ] GC(30) Eden regions: 0->0(100)
[21.400s][info][gc,heap        ] GC(30) Survivor regions: 0->0(0)
[21.400s][info][gc,heap        ] GC(30) Old regions: 1800->1500
[21.400s][info][gc,heap        ] GC(30) Humongous regions: 10->5
[21.400s][info][gc             ] GC(30) Pause Full (Allocation Failure) 7200M->6020M(8192M) 6401.602ms
[21.400s][info][gc,cpu         ] GC(30) User=6.40s Sys=0.00s Real=6.40s  ← User ≈ Real → 单线程！
```

**Full GC 四个阶段**：

| 阶段 | 含义 | 算法 |
|------|------|------|
| Phase 1: Mark live objects | 标记所有存活对象 | 深度优先遍历 |
| Phase 2: Prepare for compaction | 计算压缩后的新地址 | 线性遍历 |
| Phase 3: Adjust pointers | 更新所有引用指向新地址 | 遍历所有引用 |
| Phase 4: Compact heap | 实际移动对象到新地址 | 顺序复制 |

**源码对应**：`g1CollectedHeap.cpp:1145`
```cpp
GCTraceTime(Info, gc) tm("Pause Full", NULL, gc_cause(), true);
```

> ⚠️ **Full GC 是单线程的**（`User ≈ Real`），在大堆上可能暂停数秒甚至数十秒！
> 生产环境出现 Full GC 通常意味着：内存泄漏、堆太小、或 Mixed GC 回收不够快。

```
[12.598s][info][gc,heap,exit] Heap
[12.598s][info][gc,heap,exit]  garbage-first heap   total 8388608K, used 4250434K [0x0000000600000000, 0x0000000800000000)
[12.598s][info][gc,heap,exit]   region size 4096K, 299 young (1224704K), 1 survivors (4096K)
[12.598s][info][gc,heap,exit]  Metaspace       used 6498K, capacity 6642K, committed 6784K, reserved 1056768K
[12.598s][info][gc,heap,exit]   class space    used 558K, capacity 620K, committed 640K, reserved 1048576K
```

**逐行解读**：
1. `total 8388608K` = 8GB 堆总大小
2. `used 4250434K` = 约 4.05GB 在使用
3. `[0x0000000600000000, 0x0000000800000000)` = 堆的虚拟地址范围（8GB）

**Metaspace 四个量**：

- `committed` = 已提交的物理内存
- `reserved` = 预留的虚拟内存空间

## 七、常见问题诊断模式

### 7.1 长时间 STW 暂停

**症状**：`Pause Young ... 500ms` 或更长

**排查步骤**：
1. 看 `Evacuate Collection Set` 中哪个子阶段最慢
2. 如果 `Object Copy` 很慢 → Eden 中存活对象太多（可能对象存活率高或 Eden 太大）
3. 如果 `Ext Root Scanning` 很慢 → 线程太多或 StringTable/ClassLoaderData 太大
4. 如果 `Update RS` 很慢 → Refinement 线程跟不上脏卡产生速率
5. 如果 `Reference Processing` 很慢 → 弱引用/虚引用太多

### 7.2 频繁 Full GC

**症状**：反复出现 `Pause Full (Allocation Failure)`

**排查步骤**：
1. 检查老年代是否持续增长（每次 GC 后 Old regions 递增）→ 内存泄漏
2. 检查 Mixed GC 是否有效（`Old regions: X->Y`，Y 应该明显小于 X）
3. 检查 Humongous 分配是否太多（大对象直接进老年代）
4. 考虑增大堆或调整 IHOP

### 7.3 并发标记跟不上

**症状**：`Concurrent Cycle` 总时间很长，或者在并发标记完成前就触发了 Full GC

**排查步骤**：
1. 检查 `InitiatingHeapOccupancyPercent`（IHOP）是否设置合理
2. 检查 `-XX:ConcGCThreads` 是否足够
3. 检查 `Concurrent Mark From Roots` 耗时

### 7.4 User 时间远大于 Real 时间

**症状**：`User=2.00s Sys=0.00s Real=0.05s`

**解释**：这是正常的！GC 使用多线程并行。
- User 是所有 CPU 核心的累计时间
- Real 是实际经过的挂钟时间
- `User / Real ≈ Worker 数量` 说明并行效率好

### 7.5 Real 远大于 User

**症状**：`User=0.01s Sys=0.00s Real=0.50s`

**这不正常！** 可能原因：
1. CPU 资源不足（其他进程抢占）
2. swap 发生（JVM 内存被换出到磁盘）→ 检查 `vmstat` 或 `sar -W`
3. 操作系统的 THP（Transparent Huge Pages）问题

## 九、面试高频 Q&A

### Q1: 如何通过 GC 日志判断是否存在内存泄漏？

**回答**：
观察每次 GC 后的堆使用量（摘要行的 `->XM` 部分）。如果在多次 Full GC 后，堆使用量仍然持续增长并接近最大堆，就是内存泄漏的典型表现。

具体看：
1. Young GC 后的 Old regions 是否持续递增
2. Full GC 后的 `used` 是否无法有效下降
3. Metaspace used 是否持续增长（类加载器泄漏）

### Q2: GC 日志中 "Diff" 值很大说明什么？

**回答**：
`Diff` = Max - Min，表示各 GC Worker 线程之间的负载差异。如果 Diff 很大，说明负载不均衡。可能原因：

1. **Object Copy Diff 大**：某些 Region 存活对象特别多
2. **Ext Root Scanning Diff 大**：某个 Worker 分到了特别大的根集
3. **Termination Diff 大**：有 Worker 很早完成但要等其他 Worker（work stealing 效率低）

优化方向：调整 `-XX:ParallelGCThreads` 或检查对象分布是否严重不均。

### Q3: Young GC 日志中看到 "(Concurrent Start)" 是什么意思？

**回答**：
这意味着此次 Young GC **同时完成了并发标记的初始标记阶段**（搭载 piggyback）。G1 不会专门为初始标记做一次独立的 STW，而是搭载在下一次 Young GC 中完成。

触发条件：堆使用量达到 IHOP 阈值（默认 45%）。初始标记只是在 Young GC 的根扫描阶段额外标记 SATB 快照。

### Q4: 为什么 Full GC 的 `User ≈ Real` 而 Young GC 的 `User >> Real`？

**回答**：
因为 **G1 的 Full GC 是单线程执行的**（JDK 11 中，JDK 12+ 已并行化），所以用户态 CPU 时间等于挂钟时间。而 Young GC 使用多个 Worker 线程并行执行，多个核心的 CPU 时间累加起来大于挂钟时间。

### Q5: 如何判断需要增加 `-XX:ConcGCThreads`？

**回答**：
如果看到以下现象，说明并发标记线程不够：
1. `Concurrent Mark From Roots` 时间很长
2. 并发标记还没完成就触发了 Full GC（日志中 Concurrent Cycle 被中断）
3. `Concurrent Cycle` 总时间 > 预期的 Mixed GC 间隔

默认 `ConcGCThreads` = `ParallelGCThreads / 4`。如果 CPU 资源充足，可以适当增加。

### Q6: JDK 9+ 如何将老版本的 GC 参数转换为 -Xlog？

**回答**：

| 老参数 | 新参数 |
|--------|--------|
| `-XX:+PrintGC` | `-Xlog:gc` |
| `-XX:+PrintGCDetails` | `-Xlog:gc*` |
| `-XX:+PrintGCDateStamps` | `-Xlog:gc*::time` |
| `-XX:+PrintGCTimeStamps` | `-Xlog:gc*::uptime` |
| `-Xloggc:gc.log` | `-Xlog:gc*:file=gc.log` |
| `-XX:+PrintAdaptiveSizePolicy` | `-Xlog:gc+ergo*=debug` |
| `-XX:+PrintReferenceGC` | `-Xlog:gc+ref*=debug` |
| `-XX:+PrintTenuringDistribution` | `-Xlog:gc+age*=trace` |
