# 8.5 Mixed GC 完整流程深度分析

> 标准环境: `-Xms8g -Xmx8g -XX:+UseG1GC`, Region = 4MB, 共 2048 个 Region
> 源码版本: OpenJDK 11 (`/data/workspace/openjdk-cut-new/`)

---

## 1. 解决什么问题？

Young GC 只回收年轻代 Region，老年代 Region 中的垃圾永远得不到回收。如果不处理，老年代最终会被填满，触发代价极大的 Full GC（单线程、全堆压缩）。

Mixed GC 解决的核心问题是：**在可控的暂停时间内，增量回收老年代中垃圾比例高的 Region，避免 Full GC**。

它的设计要点是：
- **增量式**: 不是一次回收所有老年代，而是分多次（默认 8 次），每次挑选一批
- **效率优先**: 优先回收"垃圾多、RSet 小"的 Region（GC 效率最高）
- **暂停时间约束**: 在目标暂停时间内，能收多少收多少

## 3. 触发链路：从并发标记到 Mixed GC

### 3.1 前提：并发标记周期

Mixed GC 的前提是完成一次并发标记周期。并发标记告诉我们每个 Region 有多少存活对象，这是选择回收哪些 Region 的基础。

**并发标记线程主循环** (`g1ConcurrentMarkThread.cpp:247-404`):

```
sleep_before_next_cycle()           ← 等待 Initial Mark 唤醒
    ↓
CLEAR_CLAIMED_MARKS                 ← 清除类加载器标记
    ↓
SCAN_ROOT_REGIONS                   ← 扫描 Survivor Region（根区域）
    ↓
CONCURRENT_MARK (循环)              ← 并发标记
    ├── MARK_FROM_ROOTS             ← 从根对象开始标记
    ├── PRECLEAN                    ← 预清理（可选）
    └── REMARK (STW)                ← 最终标记（处理 SATB 剩余）
    ↓
REBUILD_REMEMBERED_SETS             ← 并发重建 RSet
    ↓
CLEANUP (STW)                       ← ★ 关键: 决定是否进入 Mixed Phase
    ↓
CLEANUP_FOR_NEXT_MARK               ← 为下次标记清理
    ↓
increment_old_marking_cycles_completed(true)
```

### 3.3 record_concurrent_mark_cleanup_end() — 核心决策

**源码**: `g1Policy.cpp:1035-1052`

```cpp
void G1Policy::record_concurrent_mark_cleanup_end() {
  // ① 重建候选老年代 Region 列表（按 GC 效率排序）
  cset_chooser()->rebuild(_g1h->workers(), _g1h->num_regions());

  // ② 判断是否应该启动 Mixed GC
  bool mixed_gc_pending = next_gc_should_be_mixed("request mixed gcs",
                                                   "request young-only gcs");
  if (!mixed_gc_pending) {
    clear_collection_set_candidates();  // 清空候选列表
    abort_time_to_mixed_tracking();     // 中止 Initial Mark → Mixed 的时间追踪
  }

  // ③ 设置状态机
  collector_state()->set_in_young_gc_before_mixed(mixed_gc_pending);
  collector_state()->set_mark_or_rebuild_in_progress(false);

  // ④ 记录时间统计
  _analytics->report_concurrent_mark_cleanup_times_ms(elapsed_time_ms);
}
```

这个函数做了三件事：
1. **重建候选列表**: 并行遍历所有 Region，筛选出可回收的老年代 Region，按 GC 效率排序
2. **决定是否 Mixed**: 如果候选列表不为空且可回收空间超过阈值，就进入 Mixed 阶段
3. **设置状态**: 设置 `_in_young_gc_before_mixed` 标志

### 3.4 next_gc_should_be_mixed() — 判断条件

**源码**: `g1Policy.cpp:1132-1151`

```cpp
bool G1Policy::next_gc_should_be_mixed(const char* true_action_str,
                                       const char* false_action_str) const {
  // 条件 1: 候选列表非空
  if (cset_chooser()->is_empty()) {
    log_debug(gc, ergo)("%s (candidate old regions not available)", false_action_str);
    return false;
  }

  // 条件 2: 可回收空间占堆容量的百分比 > G1HeapWastePercent (默认 5%)
  size_t reclaimable_bytes = cset_chooser()->remaining_reclaimable_bytes();
  double reclaimable_percent = reclaimable_bytes_percent(reclaimable_bytes);
  double threshold = (double) G1HeapWastePercent;
  if (reclaimable_percent <= threshold) {
    log_debug(gc, ergo)("%s ... reclaimable: %zu (%1.2f) threshold: %lu",
                        false_action_str, ...);
    return false;
  }
  log_debug(gc, ergo)("%s ... reclaimable: %zu (%1.2f) threshold: %lu",
                      true_action_str, ...);
  return true;
}
```

**两个条件必须同时满足**:
1. 有候选 Old Region（`!cset_chooser()->is_empty()`）
2. 可回收字节 > 堆容量的 `G1HeapWastePercent`%

在标准 8GB 堆下: 阈值 = 8GB × 5% = **409.6MB**。即只有当老年代中可回收的垃圾总量超过 409.6MB 时才会触发 Mixed GC。

## 4. CollectionSetChooser — 候选 Region 排序选择器

### 4.1 解决什么问题？

并发标记告诉我们每个 Region 的存活字节数。但 Mixed GC 不能回收所有 Old Region（暂停时间约束），必须选择"性价比最高"的。CollectionSetChooser 就是负责排序和管理候选 Region 的组件。

### 4.2 数据结构

**源码**: `collectionSetChooser.hpp:31-158`

### 4.5 GC 效率计算与排序

**HeapRegion::calc_gc_efficiency()** (`heapRegion.cpp:142-154`):

```cpp
void HeapRegion::calc_gc_efficiency() {
  G1Policy* g1p = g1h->g1_policy();
  double region_elapsed_time_ms =
    g1p->predict_region_elapsed_time_ms(this, false /* for_young_gc */);
  _gc_efficiency = (double) reclaimable_bytes() / region_elapsed_time_ms;
}
```

**关键公式**:

```
gc_efficiency = reclaimable_bytes / predicted_elapsed_time_ms
```

其中:
- `reclaimable_bytes = capacity - live_bytes`（可回收字节 = Region 容量 - 存活字节）
- `predicted_elapsed_time_ms` = 预测的 RSet 扫描时间 + 对象复制时间 + 其他时间

**predict_region_elapsed_time_ms()** (`g1Policy.cpp:887-907`):

```cpp
double G1Policy::predict_region_elapsed_time_ms(HeapRegion* hr, bool for_young_gc) const {
  size_t rs_length = hr->rem_set()->occupied();
  size_t card_num = _analytics->predict_card_num(rs_length, for_young_gc);
  size_t bytes_to_copy = predict_bytes_to_copy(hr);

  double region_elapsed_time_ms =
    _analytics->predict_rs_scan_time_ms(card_num, ...) +     // RSet 扫描时间
    _analytics->predict_object_copy_time_ms(bytes_to_copy, ...); // 对象复制时间

  if (hr->is_young()) {
    region_elapsed_time_ms += _analytics->predict_young_other_time_ms(1);
  } else {
    region_elapsed_time_ms += _analytics->predict_non_young_other_time_ms(1);  // Old Region
  }
  return region_elapsed_time_ms;
}
```

**排序规则** (`collectionSetChooser.cpp:41-61`):

```cpp
static int order_regions(HeapRegion* hr1, HeapRegion* hr2) {
  double gc_eff1 = hr1->gc_efficiency();
  double gc_eff2 = hr2->gc_efficiency();
  if (gc_eff1 > gc_eff2) return -1;  // 效率高的排前面
  if (gc_eff1 < gc_eff2) return 1;
  return 0;
}
```

**设计意图**（源码注释 `collectionSetChooser.cpp:32-40`）:

> 尽管我们不再像以前那样依赖 GC 效率做决策，但仍按 GC 效率排序。这使得"存活对象多且 RSet 大"的 Region 排在数组末尾。如果 Mixed GC 因可回收空间低于阈值而提前停止，被跳过的就是这些"效率低"的 Region —— 它们既有大 RSet（扫描耗时）又有大量存活对象（复制耗时）。

**例子**:

| Region | 存活字节 | 可回收字节 | RSet 大小 | 预测时间 | GC 效率 | 排序 |
|--------|---------|-----------|----------|---------|---------|------|
| R100 | 0.5MB | 3.5MB | 50 entries | 0.8ms | 4375 | ① |
| R200 | 1.0MB | 3.0MB | 100 entries | 1.2ms | 2500 | ② |
| R300 | 2.0MB | 2.0MB | 500 entries | 2.5ms | 800 | ③ |
| R400 | 3.0MB | 1.0MB | 2000 entries | 4.0ms | 250 | ④ |

R100 几乎全是垃圾、RSet 很小，效率最高；R400 大部分是存活对象、RSet 很大，效率最低。

## 5. CSet 选择算法 — finalize_old_part()

### 5.1 入口: finalize_collection_set()

**源码**: `g1Policy.cpp:1191-1194`

```cpp
void G1Policy::finalize_collection_set(double target_pause_time_ms,
                                       G1SurvivorRegions* survivor) {
  // ① 先确定 Young 部分，返回剩余时间
  double time_remaining_ms = _collection_set->finalize_young_part(target_pause_time_ms, survivor);
  // ② 把剩余时间给 Old 部分
  _collection_set->finalize_old_part(time_remaining_ms);
}
```

这是一个**时间预算分配**模型：
1. 总预算 = `target_pause_time_ms`（由 `MaxGCPauseMillis` 和 MMU Tracker 决定）
2. 先扣除 Young Region 的预测时间
3. 剩余时间分配给 Old Region

### 5.2 Young 部分: finalize_young_part()

**源码**: `g1CollectionSet.cpp:389-431`

```cpp
double G1CollectionSet::finalize_young_part(double target_pause_time_ms,
                                            G1SurvivorRegions* survivors) {
  // 计算基础开销（不包括 Region 疏散的固定开销）
  size_t pending_cards = _policy->pending_cards();
  double base_time_ms = _policy->predict_base_elapsed_time_ms(pending_cards);
  double time_remaining_ms = MAX2(target_pause_time_ms - base_time_ms, 0.0);

  // 初始化 Region 长度: eden + survivor
  uint eden_region_length = _g1h->eden_regions_count();
  uint survivor_region_length = survivors->length();
  init_region_lengths(eden_region_length, survivor_region_length);

  // 扣除 Young Region 预测时间
  time_remaining_ms = MAX2(time_remaining_ms - _inc_predicted_elapsed_time_ms, 0.0);

  return time_remaining_ms;  // 返回给 Old 部分
}
```

### 5.3 核心: finalize_old_part()

**源码**: `g1CollectionSet.cpp:443-542`

这是 Mixed GC 选择 Old Region 的核心算法。只有 `in_mixed_phase()` 为 true 时才执行。

```cpp
void G1CollectionSet::finalize_old_part(double time_remaining_ms) {
  if (collector_state()->in_mixed_phase()) {
    const uint min_old_cset_length = _policy->calc_min_old_cset_length();
    const uint max_old_cset_length = _policy->calc_max_old_cset_length();
    uint expensive_region_num = 0;
    bool check_time_remaining = _policy->adaptive_young_list_length();

    HeapRegion* hr = cset_chooser()->peek();  // 查看当前效率最高的候选
    while (hr != NULL) {
      // ========== 停止条件 1: 达到最大 Region 数 ==========
      if (old_region_length() >= max_old_cset_length) break;

      // ========== 停止条件 2: 可回收空间不足 ==========
      size_t reclaimable_bytes = cset_chooser()->remaining_reclaimable_bytes();
      double reclaimable_percent = _policy->reclaimable_bytes_percent(reclaimable_bytes);
      if (reclaimable_percent <= (double) G1HeapWastePercent) break;

      // ========== 停止条件 3: 预测时间超出预算 ==========
      double predicted_time_ms = predict_region_elapsed_time_ms(hr);
      if (check_time_remaining) {
        if (predicted_time_ms > time_remaining_ms) {
          if (old_region_length() >= min_old_cset_length) break;  // 已达最小数，可以停
          expensive_region_num += 1;  // 未达最小数，强制加入
        }
      } else {
        // 非自适应模式: 达到最小数就停
        if (old_region_length() >= min_old_cset_length) break;
      }

      // ========== 加入 CSet ==========
      time_remaining_ms = MAX2(time_remaining_ms - predicted_time_ms, 0.0);
      cset_chooser()->pop();          // 从候选列表取出
      _g1h->old_set_remove(hr);       // 从 old_set 移除
      add_old_region(hr);             // 加入 Collection Set
      hr = cset_chooser()->peek();    // 看下一个
    }
  }
  // 最终按 Region index 排序（优化扫描局部性）
  QuickSort::sort(_collection_set_regions, _collection_set_cur_length, compare_region_idx, true);
}
```

### 5.4 四个参数详解

#### calc_min_old_cset_length() — 最小 Old Region 数

**源码**: `g1Policy.cpp:1153-1172`

```cpp
uint G1Policy::calc_min_old_cset_length() const {
  const size_t region_num = (size_t) cset_chooser()->length();  // 候选总数（含已取的）
  const size_t gc_num = (size_t) MAX2(G1MixedGCCountTarget, (uintx) 1);  // 目标次数
  size_t result = region_num / gc_num;                           // 向上取整
  if (result * gc_num < region_num) result += 1;
  return (uint) result;
}
```

**含义**: 确保在 `G1MixedGCCountTarget`（默认 8）次 Mixed GC 内处理完所有候选 Region。

**标准环境计算**:
- 假设候选 Region = 80 个
- 最小数 = ceil(80 / 8) = **10 个/次**
- 即使预测时间超出预算，也必须至少收集 10 个（否则永远做不完）

#### calc_max_old_cset_length() — 最大 Old Region 数

**源码**: `g1Policy.cpp:1174-1189`

```cpp
uint G1Policy::calc_max_old_cset_length() const {
  const size_t region_num = G1CollectedHeap::heap()->num_regions();  // 总 Region 数
  const size_t perc = (size_t) G1OldCSetRegionThresholdPercent;      // 默认 10%
  size_t result = region_num * perc / 100;
  if (100 * result < region_num * perc) result += 1;                 // 向上取整
  return (uint) result;
}
```

**标准环境计算**:
- 总 Region = 2048 个
- 最大数 = ceil(2048 × 10%) = **205 个**
- 防止单次 Mixed GC 加入过多 Old Region 导致暂停时间爆炸

#### G1HeapWastePercent — 可回收阈值

- 默认值: **5%**
- 含义: 当候选 Region 的总可回收空间降到堆容量的 5% 以下时，Mixed GC 停止
- 标准环境: 8GB × 5% = **409.6MB**

#### G1MixedGCLiveThresholdPercent — Region 存活率阈值

- 默认值: **85%**
- 含义: 存活字节超过 Region 容量 85% 的 Region 不参与 Mixed GC
- 标准环境: 4MB × 85% = **3.4MB**（超过此值不回收）

## 6. Mixed GC 执行流程

### 6.1 统一入口: do_collection_pause_at_safepoint()

**源码**: `g1CollectedHeap.cpp:3541-3873`

Young GC 和 Mixed GC 共用同一个入口。核心流程：

```

│
├── 1. note_gc_start()                              // 记录 GC 开始
├── 2. wait_for_root_region_scanning()              // 等待根区域扫描完成
├── 3. decide_on_conc_mark_initiation()             // 决定是否搭载 Initial Mark
├── 4. 确定 GC 类型标签 (Normal/Prepare Mixed/Mixed/Concurrent Start)
│
├── 5. finalize_collection_set()                    // ★ 确定 CSet
│      ├── finalize_young_part()                    // Eden + Survivor
│      └── finalize_old_part()                      // ★ Mixed 阶段: 加入 Old Region
│
├── 6. cleanupHRRS()                                // 清理 RSet
├── 7. register_humongous_regions_with_cset()       // 注册 Humongous Region
├── 8. init_gc_alloc_regions()                      // 初始化 GC 分配区域
│
├── 9. pre_evacuate_collection_set()                // 疏散前准备
├── 10. ★ evacuate_collection_set()                 // 实际疏散（Young + Old Region）
├── 11. post_evacuate_collection_set()              // 后处理
├── 12. free_collection_set()                       // 释放 CSet 中的 Region
├── 13. eagerly_reclaim_humongous_regions()          // 回收 Humongous
│
├── 14. start_new_collection_set()                  // 开始下一个增量 CSet
├── 15. record_collection_pause_end()               // ★ 记录结束，决定是否继续 Mixed
│
└── 16. do_concurrent_mark() (仅 Initial Mark)      // 启动并发标记线程
```

### 6.2 Mixed GC 与 Young GC 的执行差异

Mixed GC 和 Young GC 共用同一套疏散(Evacuation)框架，但有几个关键差异：

| 方面 | Young GC | Mixed GC |
|------|----------|----------|
| **CSet 组成** | Eden + Survivor | Eden + Survivor + **选中的 Old Region** |
| **Young 部分大小** | 自适应计算 | **尽量最小化**（给 Old 留时间） |
| **RSet 扫描范围** | 只扫描 Young Region 的入引用 | 还要扫描 **Old Region 的入引用** |
| **对象存活率** | 通常较低（大多是朝生暮死） | Old Region 存活率较高（最高 85%） |
| **复制开销** | 较小 | **较大**（Old Region 存活对象多） |
| **allMemoryPoolsAffected** | false | **true**（影响老年代内存池） |

### 6.3 年轻代大小调整

**源码**: `g1Policy.cpp:261-324` — `young_list_target_lengths()`

在 Mixed Phase 中，年轻代长度的计算策略有所不同:

```cpp
if (adaptive_young_list_length()) {
  if (collector_state()->in_young_only_phase()) {
    young_list_target_length = calculate_young_list_target_length(...);
  } else {
    // Mixed Phase: 不计算，直接使用 desired_min_length
    // 即: 尽可能减小年轻代，给老年代回收留更多时间预算
  }
}
```

**设计意图**: Mixed Phase 中，年轻代尽量小，这样：
1. 暂停时间预算中 Young 部分占比小
2. 剩余时间更多，能加入更多 Old Region
3. 加速 Mixed 阶段的完成

### 6.4 evacuate_collection_set() — 并行疏散

**源码**: `g1CollectedHeap.cpp:3916-4003` — `G1ParTask::work()`

每个 GC Worker 线程执行:

```

│
├── evacuate_roots(pss, worker_id)           // 扫描 GC Roots
│    ├── Thread Roots                        // 线程栈引用
```

## 7. Mixed GC 结束：继续还是停止？

### 7.1 record_collection_pause_end() 中的决策

**源码**: `g1Policy.cpp:604-669`

```cpp
void G1Policy::record_collection_pause_end(...) {
  bool this_pause_was_young_only = collector_state()->in_young_only_phase();

  if (collector_state()->in_young_gc_before_mixed()) {
    // 场景 1: "Prepare Mixed" 暂停结束
    // 推进到 Mixed Phase
    collector_state()->set_in_young_only_phase(false);
    collector_state()->set_in_young_gc_before_mixed(false);

  } else if (!this_pause_was_young_only) {
    // 场景 2: Mixed GC 暂停结束
    // 决定是否继续
    if (!next_gc_should_be_mixed("continue mixed GCs",
                                 "do not continue mixed GCs")) {
      // 停止 Mixed: 可回收空间不足
      collector_state()->set_in_young_only_phase(true);
      clear_collection_set_candidates();  // 清空候选
      maybe_start_marking();              // 检查是否需要新的并发标记
    }
    // 否则: 继续 Mixed GC（什么都不做，状态保持 in_mixed_phase）
  }
}
```

### 7.2 Mixed GC 停止的三种情况

| 停止原因 | 触发条件 | 日志关键词 |
|---------|---------|-----------|
| 候选列表耗尽 | `cset_chooser()->is_empty()` | "candidate old regions not available" |
| 可回收空间不足 | `reclaimable_percent <= G1HeapWastePercent` | "reclaimable percentage not over threshold" |
| 候选全部被处理完 | 所有候选 Region 已在之前的 Mixed GC 中被回收 | - |

### 7.3 Mixed GC 典型序列（标准环境示例）

假设并发标记后有 80 个候选 Old Region，总可回收空间 640MB:

```
次数  类型            Old Region  剩余候选  剩余可回收  继续?
─────────────────────────────────────────────────────────
#1   Prepare Mixed    0           80        640MB       ── 进入 Mixed Phase
#2   Mixed           10           70        560MB       ✓ (560/8192=6.8% > 5%)
#3   Mixed           10           60        480MB       ✓ (480/8192=5.9% > 5%)
#4   Mixed           10           50        400MB       ✗ (400/8192=4.9% ≤ 5%)
─────────────────────────────────────────────────────────
结果: 3 次 Mixed GC，回收了 30 个 Old Region，剩余 50 个候选被放弃
      回到 Young Only Phase
```

注意: 实际每次的 Old Region 数量不是固定的，取决于预测的暂停时间。

## 8. 与并发标记的互锁机制

### 8.1 about_to_start_mixed_phase() — 防止并发标记重叠

**源码**: `g1Policy.cpp:575-598`

```cpp
bool G1Policy::about_to_start_mixed_phase() const {
  return _g1h->concurrent_mark()->cm_thread()->during_cycle()
      || collector_state()->in_young_gc_before_mixed();
}

bool G1Policy::need_to_start_conc_mark(const char* source, size_t alloc_word_size) {
  if (about_to_start_mixed_phase()) {
    return false;  // 即将进入 Mixed 阶段，不启动新的并发标记
  }
  // 检查堆占用是否超过 IHOP 阈值
  size_t marking_initiating_used_threshold = _ihop_control->get_conc_mark_start_threshold();
  size_t marking_request_bytes = cur_used_bytes + alloc_byte_size;
  if (marking_request_bytes > marking_initiating_used_threshold) {
    return collector_state()->in_young_only_phase()
        && !collector_state()->in_young_gc_before_mixed();
  }
  return false;
}
```

**设计意图**: 确保在以下情况不启动新的并发标记:
1. 正在进行并发标记周期
2. 即将进入 Mixed 阶段（已标记为 `in_young_gc_before_mixed`）

因为 Mixed GC 的 CSet 选择依赖于上一次并发标记的结果。如果在 Mixed 阶段中间启动新的并发标记，会覆盖这些信息。

### 8.2 decide_on_conc_mark_initiation() — 并发标记启动决策

**源码**: `g1Policy.cpp:984-1033`

在每次 GC 暂停开始时调用:

```cpp
void G1Policy::decide_on_conc_mark_initiation() {
  if (collector_state()->initiate_conc_mark_if_possible()) {
    if (!about_to_start_mixed_phase() && collector_state()->in_young_only_phase()) {
      // 正常情况: 启动并发标记
      initiate_conc_mark();
    } else if (is_user_requested_concurrent_full_gc()) {
      // 用户请求 (System.gc()): 强制启动，中断 Mixed 阶段
      collector_state()->set_in_young_only_phase(true);
      collector_state()->set_in_young_gc_before_mixed(false);
      clear_collection_set_candidates();
      initiate_conc_mark();
    } else {
      // 并发标记还在进行中，等下次
      log_debug(gc, ergo)("Do not initiate concurrent cycle (concurrent cycle already in progress)");
    }
  }
}
```

### 8.3 Mixed GC 结束后检查新标记

**源码**: `g1Policy.cpp:662-668`

当 Mixed GC 停止后:

```cpp
collector_state()->set_in_young_only_phase(true);
clear_collection_set_candidates();
maybe_start_marking();  // ★ 检查是否需要启动新的并发标记
```

`maybe_start_marking()` 会检查堆占用是否超过 IHOP 阈值。如果是，就设置 `_initiate_conc_mark_if_possible = true`，在下一次 GC 暂停时搭载 Initial Mark。

```cpp
void G1Policy::record_pause(PauseKind kind, double start, double end) {
  _mmu_tracker->add_pause(start, end);

  switch (kind) {
    case InitialMarkGC:
      _initial_mark_to_mixed.record_initial_mark_end(end);   // 记录起点
```

## 14. 设计哲学总结

### 14.1 为什么 Mixed GC 是增量式的？

如果一次回收所有老年代 Region，暂停时间会很长（可能数百毫秒），违反 G1 的低延迟目标。增量式设计允许在每次暂停中只回收一部分，保持暂停时间可控。

`G1MixedGCCountTarget=8` 意味着"争取在 8 次 Mixed GC 内处理完"，这是一个折衷:
- 太少（如 2 次）: 每次 Old Region 多，暂停长
- 太多（如 20 次）: Mixed 阶段持续太久，老年代垃圾积累

### 14.2 为什么有 G1HeapWastePercent？

"最后一公里"的 Old Region 往往效率最低（存活率高、RSet 大）。继续回收它们的代价可能超过收益。G1HeapWastePercent 允许 G1"容忍"一定比例的浪费，避免为回收小量空间而做高代价的疏散。

### 14.3 为什么排序用 GC 效率而不是可回收字节？

纯按可回收字节排序可能选到"可回收多但 RSet 巨大"的 Region，导致暂停时间爆炸。GC 效率 = 可回收字节 / 预测时间，综合考虑了"收益"和"成本"，是更合理的度量。

### 14.4 先 Young 后 Old 的时间分配

`finalize_young_part()` 必须先执行，因为 Young Region 必须被回收（否则 Eden 满了无法分配）。Old Region 是"可选的"——剩余时间多就多收几个，少就少收几个。这保证了:
- Young GC 的低延迟不被破坏
- Old Region 回收在暂停时间约束内"尽力而为"

### 14.5 Mixed Phase 中年轻代为什么要最小化？

在 `young_list_target_lengths()` 中，Mixed Phase 不执行自适应计算，直接使用 `desired_min_length`。这是因为:
- 年轻代越小，Young 部分占的暂停时间越少
- 剩余时间越多，能加入的 Old Region 越多
- Mixed 阶段越快完成，越早回到正常的 Young Only Phase
