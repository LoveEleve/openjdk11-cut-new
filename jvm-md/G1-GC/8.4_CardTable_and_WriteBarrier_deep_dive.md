# 8.4 Card Table 与 Write Barrier 深度分析

> **标准环境**: `-Xms8g -Xmx8g -XX:+UseG1GC`，Region Size = 4MB，CardsPerRegion = 8192

---

## 1. 总览：Card Table 在 G1 中的角色

Card Table（卡表）是 G1 GC **写屏障（Write Barrier）** 的基础数据结构。它与 RSet 的关系是：

```
卡表（CardTable）：记录 "哪里被修改了"  ← 写屏障直接操作
记忆集（RSet）：记录 "谁引用了我"        ← 精炼线程异步更新

写屏障标脏卡 → 入队 DirtyCardQueue → 精炼线程处理 → 更新 RSet
```

| 维度 | Card Table | RSet |
|------|-----------|------|
| 粒度 | 512 字节（一张卡） | 卡级别（由 Card 索引记录） |
| 数量 | 整个堆共享一个 | 每个 Region 一个 |
| 更新时机 | 写屏障**立即**更新（一条指令） | 精炼线程**异步**更新 |
| 空间开销 | 8GB 堆 → 16MB 卡表 | 可变（Sparse/Fine/Coarse 三层） |

### 3.4 内存布局（8GB 堆）

```
8GB 堆计算:
    堆大小 = 8GB = 8 × 1024 × 1024 × 1024 = 8,589,934,592 字节
    卡数量 = 8GB / 512 = 16,777,216 = 16M 张卡
    卡表大小 = 16M × 1 字节/卡 = 16MB

    每个 4MB Region:
        CardsPerRegion = 4MB / 512B = 8,192 张卡
        卡表中占 8,192 字节 = 8KB
```

```
CardTable 内存布局 (16MB):
┌────────────────────────────────────────────────────────────────┐
│  _byte_map[0]          _byte_map[8191]                        │
│  ├── Region 0 的卡 ──┤                                        │
│                                                                │
│  _byte_map[8192]       _byte_map[16383]                       │
│  ├── Region 1 的卡 ──┤                                        │
│                                                                │
│  ...                                                           │
│                                                                │
│  _byte_map[16M-8193]   _byte_map[16M-1]   _byte_map[16M]     │

│                                             (哨兵位)            │
```

### 3.5 地址映射优化：`byte_for()` 和 `_byte_map_base`

```cpp
// cardTable.hpp:156-165
jbyte* byte_for(const void* p) const {
    return &_byte_map_base[uintptr_t(p) >> card_shift];
}
```

**优化原理**（`g1CardTable.cpp:108-129`）：

```
传统做法（3 步）:
    offset = heap_address - heap_start
    card_index = offset >> 9
    return &_byte_map[card_index]

优化做法（2 步）:
    _byte_map_base = _byte_map - (heap_start >> 9)

    那么：
    &_byte_map_base[addr >> 9]
    = _byte_map_base + (addr >> 9)
    = _byte_map - (heap_start >> 9) + (addr >> 9)
    = _byte_map + (addr - heap_start) >> 9       ← 等价于传统做法

    消除了一次减法运算！
```

**反向映射** `addr_for()`：

```cpp
// cardTable.hpp:187-199
HeapWord* addr_for(const jbyte* p) const {
    size_t delta = pointer_delta(p, _byte_map_base, sizeof(jbyte));
    HeapWord* result = (HeapWord*) (delta << card_shift);
    return result;
}
```

## 4. G1CardTable 初始化

```cpp
// g1CardTable.cpp:74-138
void G1CardTable::initialize(G1RegionToSpaceMapper* mapper) {
    // 1. 设置监听器：Region commit 时自动清理卡表（设为 clean = -1）
    mapper->set_mapping_changed_listener(&_listener);

    // 2. 卡表大小 = 16MB
    _byte_map_size = mapper->reserved().byte_size();

    // 3. 哨兵索引 = cards_required(1G words) - 1 = (1G/64 + 1) - 1 = 16M
    _guard_index = cards_required(_whole_heap.word_size()) - 1;
    _last_valid_index = _guard_index - 1;  // = 16M - 1

    // 4. 获取堆边界
    HeapWord* low_bound  = _whole_heap.start();
    HeapWord* high_bound = _whole_heap.end();

    // 5. G1 采用单一覆盖区域（整个堆共享一个卡表）
    _cur_covered_regions = 1;
    _covered[0] = _whole_heap;

    // 6. 设置卡表数组指针（指向 mapper 预留的内存）
    _byte_map = (jbyte*) mapper->reserved().start();

    // 7. 计算偏移基地址（优化地址映射）
    _byte_map_base = _byte_map - (uintptr_t(low_bound) >> card_shift);
}
```

## 5. Write Barrier 完整链路

### 5.1 总览

G1 使用 **Pre-Barrier（SATB）** 和 **Post-Barrier（Card Marking）** 两道屏障：

```
引用赋值 obj.field = new_val 的完整流程:

    ┌─────────────────────────────────────────────────┐
    │ 1. Pre-Barrier (SATB)                           │
    │    old_val = load(field)                         │
    │    if (marking_active && old_val != null)        │
    │        enqueue(old_val) → SATBMarkQueue          │
    ├─────────────────────────────────────────────────┤
    │ 2. 实际赋值                                      │
    │    store(field, new_val)                          │
    ├─────────────────────────────────────────────────┤
    │ 3. Post-Barrier (Card Marking)                  │
    │    byte = card_table[field >> 9]                  │
    │    if (*byte != g1_young_card_val)    ← 快路径   │
    │        write_ref_field_post_slow(byte) ← 慢路径  │
    └─────────────────────────────────────────────────┘
```

### 5.2 Pre-Barrier（SATB 前置屏障）

```cpp
// g1BarrierSet.inline.hpp:35-46
template <DecoratorSet decorators, typename T>
inline void G1BarrierSet::write_ref_field_pre(T* field) {
    // 跳过：未初始化的目标（如新分配对象的字段）或 no-keepalive
    if (HasDecorator<decorators, IS_DEST_UNINITIALIZED>::value ||
        HasDecorator<decorators, AS_NO_KEEPALIVE>::value) {
        return;
    }
    // 读取旧值
    T heap_oop = RawAccess<MO_VOLATILE>::oop_load(field);
    if (!CompressedOops::is_null(heap_oop)) {
        // 将旧值入队到 SATB 队列
        enqueue(CompressedOops::decode_not_null(heap_oop));
    }
}
```

```cpp
// g1BarrierSet.cpp:118-130 — enqueue 实现
void G1BarrierSet::enqueue(oop pre_val) {
    if (!_satb_mark_queue_set.is_active()) return;  // 非标记周期不记录
    Thread* thr = Thread::current();
    if (thr->is_Java_thread()) {
        // Java 线程：使用线程本地 SATB 队列（无锁）
        G1ThreadLocalData::satb_mark_queue(thr).enqueue(pre_val);
    } else {
        // 非 Java 线程：使用共享队列（需加锁）
        MutexLockerEx x(Shared_SATB_Q_lock, Mutex::_no_safepoint_check_flag);
        _satb_mark_queue_set.shared_satb_queue()->enqueue(pre_val);
    }
}
```

### 5.3 Post-Barrier 快路径（inline）

```cpp
// g1BarrierSet.inline.hpp:48-55
template <DecoratorSet decorators, typename T>
inline void G1BarrierSet::write_ref_field_post(T* field, oop new_val) {
    volatile jbyte* byte = _card_table->byte_for(field);
    if (*byte != G1CardTable::g1_young_card_val()) {
        // 非年轻代卡 → 走慢路径
        write_ref_field_post_slow(byte);
    }
    // 年轻代卡 → 直接返回（年轻代整体会被扫描，无需记录）
}
```

**快路径过滤的意义**：

```
为什么跳过年轻代卡？
    1. 年轻代 Region 在每次 GC 暂停时都会被完整扫描
    2. 因此无需通过 RSet 记录指向年轻代的引用
    3. 也无需记录年轻代内部的引用（因为整个年轻代都会扫描）
    4. 卡值 = 32 表示该卡属于年轻代 Region

    这是一个非常高效的过滤：
    - 新分配对象大多在年轻代
    - 大量引用修改发生在年轻代内
    - 一次字节比较就能跳过，开销极小
```

### 5.4 Post-Barrier 慢路径

```cpp
// g1BarrierSet.cpp:156-171
void G1BarrierSet::write_ref_field_post_slow(volatile jbyte* byte) {
    // 断言：不应该是年轻代卡（快路径已过滤）
    assert(*byte != G1CardTable::g1_young_card_val(), "slow path invoked without filtering");

    // 1. StoreLoad 内存屏障
    //    确保前面的 store（引用赋值）对所有线程可见
    //    然后才读取卡表状态
    OrderAccess::storeload();

    // 2. 检查是否已经为脏（避免重复入队）
    if (*byte != G1CardTable::dirty_card_val()) {
        // 3. 标脏卡：将卡值设为 0 (dirty)
        *byte = G1CardTable::dirty_card_val();

        // 4. 入队到 DirtyCardQueue
        Thread* thr = Thread::current();
        if (thr->is_Java_thread()) {
            // Java 线程：使用线程本地脏卡队列（无锁）
            G1ThreadLocalData::dirty_card_queue(thr).enqueue(byte);
        } else {
            // 非 Java 线程：使用共享队列（需加锁）
            MutexLockerEx x(Shared_DirtyCardQ_lock, Mutex::_no_safepoint_check_flag);
            _dirty_card_queue_set.shared_dirty_card_queue()->enqueue(byte);
        }
    }
}
```

**StoreLoad 屏障的必要性**：

```
时序问题：
    线程 A（应用线程）           线程 B（精炼线程）
    ─────────────────          ─────────────────
    obj.field = new_val  (1)
    *card = dirty        (2)
                                读取 *card == dirty  (3)
                                *card = clean        (4)
                                扫描 card 区域       (5)

    如果没有 StoreLoad 屏障：
    - (1) 可能被处理器重排到 (2) 之后
    - 线程 B 在 (5) 扫描时可能看不到 (1) 的修改
    - 导致跨 Region 引用丢失，RSet 不完整

    有 StoreLoad 屏障：
    - 保证 (1) 在 (2) 之前对所有线程可见
    - 线程 B 扫描时一定能看到最新的引用
```

### 5.5 Post-Barrier 完整调用链

```
应用线程执行 obj.field = new_val

    ↓ Access API (Decorator 框架)

write_ref_field_post(field, new_val)          [g1BarrierSet.inline.hpp:49]
    │
    ├── byte = _card_table->byte_for(field)    [cardTable.hpp:161]
    │       = &_byte_map_base[field >> 9]
    │
    ├── if (*byte != g1_young_card_val)        快路径检查
    │       │
    │       └── YES: 非年轻代卡
    │               │
    │               ↓
    │   write_ref_field_post_slow(byte)         [g1BarrierSet.cpp:156]
    │       │
    │       ├── OrderAccess::storeload()         StoreLoad 内存屏障
    │       │
    │       ├── if (*byte != dirty_card_val)     检查是否已脏
    │       │       │
```

### 6.2 PtrQueue 入队机制

`DirtyCardQueue` 继承自 `PtrQueue`，核心是缓冲区管理：

```cpp
// ptrQueue.hpp:90-93
class PtrQueue {
protected:
    void** _buf;          // 缓冲区数组
    size_t _index;        // 当前写入位置（从高向低生长）
    size_t _capacity_in_bytes;  // 缓冲区容量
    Mutex* _lock;         // 锁（共享队列使用）
    PtrQueueSet* _qset;  // 所属的全局队列集
    bool _active;         // 是否活跃
    bool _permanent;      // 是否永久队列（共享队列 = true）
};
```

**入队实现**（`ptrQueue.cpp:64-74`）：

```cpp
void PtrQueue::enqueue_known_active(void* ptr) {
    // 缓冲区满时处理
    while (_index == 0) {
        handle_zero_index();  // 将满缓冲区提交到全局队列，分配新缓冲区
    }
    // 从高地址向低地址写入
    _index -= _element_size;  // _element_size = sizeof(void*) = 8
    _buf[index()] = ptr;
}
```

**缓冲区布局**：

```
缓冲区 (_buf) - 默认大小由 G1UpdateBufferSize 控制（默认 256）

高地址                                          低地址
┌──────┬──────┬──────┬─────────────────┬──────┬──────┐
│空闲  │空闲  │空闲  │     ← _index    │card2 │card1 │
│slot  │slot  │slot  │                 │ptr   │ptr   │
└──────┴──────┴──────┴─────────────────┴──────┴──────┘
                      ↑                              ↑
                    _index                     capacity-1
                  (当前位置)                   (最先入队)

入队: _index -= 8; _buf[_index/8] = ptr;
满了: _index == 0 → handle_zero_index()
```

### 6.3 缓冲区满时的处理

当 `_index == 0` 时调用 `handle_zero_index()`：

```
handle_zero_index()
    │
    ├── should_enqueue_buffer()  // DirtyCardQueue 总是返回 true
    │       (SATBMarkQueue 会做过滤，可能返回 false)
    │
    ├── YES: 将当前缓冲区包装为 BufferNode
    │   └── qset()->enqueue_complete_buffer(node)
    │       │
    │       ├── 加锁 _cbl_mon
    │       ├── 追加到 _completed_buffers_tail
    │       ├── _n_completed_buffers++
    │       └── notify_if_necessary()  // 唤醒精炼线程（如果超过阈值）
    │
    └── 分配新缓冲区 → _buf = new_buf; _index = capacity;
```

## 7. 并发精炼线程（Concurrent Refinement）

### 7.1 三色区域机制

```
G1ConcurrentRefine 维护三个区域阈值，控制精炼线程的激活/休眠:

完成缓冲区数量
    ▲
    │
    │  ┌─────────────────────────────────┐
Red │  │ 应用线程也参与处理               │  red_zone ≈ 65
Zone│  │ _max_completed_queue = red_zone  │
    │  └─────────────────────────────────┘
    │  ┌─────────────────────────────────┐
Yel-│  │ 逐步激活更多精炼线程             │  yellow_zone ≈ 39
low │  │ 线程 i 的激活阈值:               │
Zone│  │ green + i*(yellow-green)/n_threads│
    │  └─────────────────────────────────┘
    │  ┌─────────────────────────────────┐
Gre-│  │ 主精炼线程工作                   │  green_zone ≈ 13
en  │  │ process_completed_threshold      │
Zone│  └─────────────────────────────────┘
    │  ┌─────────────────────────────────┐
    │  │ 不处理（利用缓存效应延迟处理）    │  0
    │  └─────────────────────────────────┘
    └──────────────────────────────────────►
```

### 7.2 精炼线程运行循环

```cpp
// g1ConcurrentRefineThread.cpp:92-138
void G1ConcurrentRefineThread::run_service() {
    while (!should_terminate()) {
        // 等待被唤醒
        wait_for_completed_buffers();
        if (should_terminate()) break;

        {
            SuspendibleThreadSetJoiner sts_join;  // GC 安全点可挂起

            while (!should_terminate()) {
                if (sts_join.should_yield()) {
                    sts_join.yield();   // GC 暂停时让出
                    continue;
                }
                // 处理一个完成缓冲区
                if (!_cr->do_refinement_step(_worker_id)) {
                    break;  // 缓冲区数量低于去激活阈值
                }
            }
        }

        deactivate();  // 休眠
    }
}
```

**`do_refinement_step()`**（`g1ConcurrentRefine.cpp:438-455`）：

```cpp
bool G1ConcurrentRefine::do_refinement_step(uint worker_id) {
    DirtyCardQueueSet& dcqs = G1BarrierSet::dirty_card_queue_set();
    size_t curr_buffer_num = dcqs.completed_buffers_num();

    // 检查是否需要激活更多线程
    maybe_activate_more_threads(worker_id, curr_buffer_num);

    // 处理下一个缓冲区（如果数量高于去激活阈值）
```

## 8. 热卡缓存（Hot Card Cache）

### 8.1 设计目标

```
问题场景：
    某些内存区域被频繁修改 → 同一张卡反复变脏 → 精炼线程反复处理同一张卡 → 大量重复工作

解决方案：
    1. 统计每张卡的修改次数（G1CardCounts）
    2. 修改次数 >= G1ConcRSHotCardLimit（默认 4）→ "热卡"
    3. 热卡不立即精炼，放入缓存延迟处理
    4. GC 暂停时批量处理，或被新卡驱逐时处理

额外好处：
    热卡被放入缓存后，卡表中该卡仍为 dirty
    → 下次应用线程修改该区域时，快路径检查 *byte != dirty 失败
    → 直接跳过写屏障的后续步骤
    → 显著减少写屏障开销
```

### 8.2 数据结构

### 8.4 热卡插入（环形缓冲区）

```cpp
// g1HotCardCache.cpp:110-132
jbyte* G1HotCardCache::insert(jbyte* card_ptr) {
    uint count = _card_counts.add_card_count(card_ptr);
    if (!_card_counts.is_hot(count)) {
        // 不是热卡 → 返回给调用者立即精炼
        return card_ptr;
    }

    // 热卡 → 原子递增索引（环形缓冲区）
    size_t index = Atomic::add(1u, &_hot_cache_idx) - 1;
    size_t masked_index = index & (_hot_cache_size - 1);  // 取模（size 是 2 的幂）
    jbyte* current_ptr = _hot_cache[masked_index];

    // CAS 替换旧指针（如果该槽位有旧卡，旧卡被驱逐）
    jbyte* previous_ptr = Atomic::cmpxchg(card_ptr, &_hot_cache[masked_index], current_ptr);
    return (previous_ptr == current_ptr) ? previous_ptr : card_ptr;
    // 返回被驱逐的旧卡（或 NULL），由调用者精炼
}
```

**返回值语义**：

| 返回值 | 含义 |
|--------|------|
| `NULL` | 插入成功，槽位之前为空，无需立即精炼 |
| `card_ptr`（原卡） | 非热卡，直接返回给调用者精炼 |
| 其他指针 | CAS 成功，被驱逐的旧热卡，需要精炼 |
| `card_ptr`（CAS 失败） | CAS 竞争失败，返回当前卡精炼 |

## 9. `refine_card_concurrently()` 详解

这是**脏卡转化为 RSet 更新的核心方法**（`g1RemSet.cpp:702-834`）：

```cpp
void G1RemSet::refine_card_concurrently(jbyte* card_ptr, uint worker_i) {
    // 1. 检查卡是否仍为脏
    if (*card_ptr != G1CardTable::dirty_card_val()) {
        return;  // 已被其他线程处理
    }

    // 2. 计算卡对应的堆地址和 Region
    HeapWord* start = _ct->addr_for(card_ptr);
    HeapRegion* r = _g1h->heap_region_containing(start);

    // 3. 过滤非老年代/非巨型对象 Region
    //    年轻代、空闲 Region 不需要精炼
    if (!r->is_old_or_humongous()) {
        return;
    }

    // 4. 热卡缓存处理
    if (_hot_card_cache->use_cache()) {
        const jbyte* orig_card_ptr = card_ptr;
        card_ptr = _hot_card_cache->insert(card_ptr);
        if (card_ptr == NULL) {
            return;  // 插入缓存成功，无驱逐
        } else if (card_ptr != orig_card_ptr) {
            // 被驱逐的旧卡，重新获取其对应的 Region
            start = _ct->addr_for(card_ptr);
            r = _g1h->heap_region_containing(start);
            if (!r->is_old_or_humongous()) {
                return;  // 旧卡的 Region 可能已被释放
            }
        }
    }

    // 5. 修剪扫描范围到 Region 的 top()
    HeapWord* scan_limit = r->top();
    if (scan_limit <= start) {
        return;  // 空卡（过时的脏卡）
    }

    // 6. ★ 清理卡表: 将卡值设回 clean
    *const_cast<volatile jbyte*>(card_ptr) = G1CardTable::clean_card_val();

    // 7. ★ 内存屏障: 确保清卡在扫描之前
    //    保证: (a) 清卡对其他线程可见 (b) top() 的读取已完成
    OrderAccess::fence();

    // 8. 构造脏区域
    HeapWord* end = start + G1CardTable::card_size_in_words;  // + 64 words = 512B
    MemRegion dirty_region(start, MIN2(scan_limit, end));

    // 9. 遍历脏区域内的对象，找出跨 Region 引用
    G1ConcurrentRefineOopClosure conc_refine_cl(_g1h, worker_i);
    bool card_processed =
        r->oops_on_card_seq_iterate_careful<false>(dirty_region, &conc_refine_cl);

    // 10. 处理失败（遇到不可解析的堆区域）
    if (!card_processed) {
        if (*card_ptr != G1CardTable::dirty_card_val()) {
            *card_ptr = G1CardTable::dirty_card_val();  // 重新标脏
            // 重新入队到共享队列
            MutexLockerEx x(Shared_DirtyCardQ_lock, Mutex::_no_safepoint_check_flag);
            DirtyCardQueue* sdcq =
                G1BarrierSet::dirty_card_queue_set().shared_dirty_card_queue();
            sdcq->enqueue(card_ptr);
        }
    }
}
```

**关键同步点**：

```
为什么先清卡再扫描？

    时序：
        精炼线程                    应用线程
        ──────────                 ──────────
                                   obj.field = X   (a)
                                   *card = dirty   (b)
        *card = clean    (6)
        fence()          (7)
        扫描 card 区域   (9)       obj.field = Y   (c)
                                   *card = dirty   (d)

    如果先扫描再清卡：
        精炼线程扫描时看到 field=X
        然后应用线程写入 field=Y 并标脏
        精炼线程清卡 → Y 的引用永远不会被精炼！

    先清再扫的正确性：
        清卡后，如果应用线程再修改，会重新标脏并入队
        精炼线程扫描看到的是清卡前的快照
        即使有遗漏，下一轮精炼或 GC 暂停时会补上
```

## 10. GC 暂停期间脏卡处理

### 10.1 `refine_card_during_gc()`

```cpp
// g1RemSet.cpp:836-875
bool G1RemSet::refine_card_during_gc(jbyte* card_ptr,
                                     G1ScanObjsDuringUpdateRSClosure* update_rs_cl) {
    // 1. 检查是否仍脏
    if (*card_ptr != G1CardTable::dirty_card_val()) {
        return false;
    }

    // 2. 设置 claimed 标记（防止重复扫描，使用惰性声明，允许良性竞争）
    *card_ptr = G1CardTable::clean_card_val() | G1CardTable::claimed_card_val();
    // = -1 | 2 = ... 实际上是 claimed_card_val (2)

    // 3. 计算卡对应的 Region
    HeapWord* card_start = _ct->addr_for(card_ptr);
    uint card_region_idx = _g1h->addr_to_region(card_start);

    // 4. 标记脏 Region
    _scan_state->add_dirty_region(card_region_idx);

    // 5. 限制扫描范围
    HeapWord* scan_limit = _scan_state->scan_top(card_region_idx);
    if (scan_limit <= card_start) return false;

    // 6. 构造脏区域并扫描
    HeapWord* card_end = card_start + G1CardTable::card_size_in_words;
    MemRegion dirty_region(card_start, MIN2(scan_limit, card_end));

    HeapRegion* card_region = _g1h->region_at(card_region_idx);
    update_rs_cl->set_region(card_region);
    bool card_processed =
        card_region->oops_on_card_seq_iterate_careful<true>(dirty_region, update_rs_cl);
    return true;
}
```

**与并发版本的区别**：

| 方面 | 并发精炼 | GC 暂停期间 |
|------|---------|------------|
| 执行时机 | 应用线程运行时 | 安全点（STW） |
| 卡状态设置 | clean（可能被重新标脏） | claimed（防重复扫描） |
| 内存屏障 | 需要 `OrderAccess::fence()` | 不需要（安全点保证） |
| 热卡缓存 | 使用（插入/驱逐） | 不使用（直接处理） |
| 失败处理 | 重新标脏并入队 | 不会失败（assert） |
| 扫描范围 | `r->top()` | `scan_state->scan_top()` |

### 10.2 GC 暂停的整体脏卡处理流程

```
GC 暂停开始
    │
    ├── 1. concatenate_logs()
    │      合并所有线程本地 DirtyCardQueue → 全局 DirtyCardQueueSet
    │      临时取消 _max_completed_queue 限制
    │
    ├── 2. hot_card_cache->drain()
    │      关闭热卡缓存
    │      多线程并行处理缓存中的所有卡（每线程 32 张）
    │      使用 refine_card_during_gc() 处理
    │
    ├── 3. update_rem_set()
    │      处理剩余的全局脏卡缓冲区
    │      使用 apply_closure_during_gc() + refine_card_during_gc()
    │
    ├── 4. scan_rem_set()
    │      扫描 CSet 中各 Region 的 RSet
    │      根据 RSet 找到所有跨 Region 引用
    │
    └── 5. hot_card_cache->set_use_cache(true)
           重新启用热卡缓存
```

## 16. 关键设计思想总结

### 16.1 分层过滤减少开销

```
写屏障开销层层递减：

Level 0: 年轻代卡检查              → 过滤大量年轻代内引用（一次字节比较）
Level 1: 已脏卡检查                → 避免重复入队（StoreLoad + 一次比较）
Level 2: 线程本地缓冲区            → 批量提交，减少锁竞争
Level 3: 三色区域控制              → 按需激活精炼线程
Level 4: 热卡缓存                  → 延迟处理高频修改的卡
Level 5: Region 类型过滤           → 跳过年轻代/空闲 Region
Level 6: 实际 RSet 更新            → 只有真正跨 Region 的引用才更新
```

### 16.2 并发安全的核心手段

| 手段 | 使用位置 |
|------|---------|
| StoreLoad 屏障 | `write_ref_field_post_slow()` — 保证赋值可见后再标脏 |
| `OrderAccess::fence()` | `refine_card_concurrently()` — 保证清卡在扫描之前 |
| `Atomic::cmpxchg` | 热卡缓存插入 — 无锁并发替换 |
| `Atomic::add` | 热卡缓存索引递增 — 无锁环形缓冲 |
| `MutexLockerEx` | 共享队列入队 — 非 Java 线程使用锁 |
| `SuspendibleThreadSet` | 精炼线程 — GC 暂停时可挂起 |

### 16.3 先清后扫的设计模式

```
并发精炼的核心不变量：

    "如果一张卡覆盖的区域有跨 Region 引用被修改，
     那么该引用最终一定会被记录到目标 Region 的 RSet 中"

实现方式：
    1. 精炼线程先清卡，再扫描
    2. 如果应用线程在清卡后、扫描前又修改了引用
       → 会重新标脏并入队 → 下轮精炼会处理
    3. 即使精炼线程扫描失败
       → 也会重新标脏并入队
    4. GC 暂停时会 drain 所有剩余缓冲区
       → 保证最终一致性
```
