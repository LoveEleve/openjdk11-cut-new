本文是对 **5.1 对象分配字节码深度分析 — new / newarray / anewarray / multianewarray** 的深度源码分析：从数据结构到算法流程，逐层剖析其实现原理，并通过 GDB 验证关键结论。

## 1. 问题引入：解释器侧的"最后一块拼图"

`ch02_object_allocation.md` 已经完整分析了 **C++ 分配链路**（MemAllocator → TLAB → G1 → HeapRegion），但有一个关键问题没有回答：

> **解释器在进入 C++ 慢路径之前，到底做了什么？**

答案是：解释器为 `new` 字节码生成了一段**纯 x86 机器码**，在绝大多数情况下（约 99%）直接在汇编中完成对象分配，**完全不进入 C++**。只有少数情况（类未初始化、TLAB 满、有 finalizer）才会 fall through 到 C++ 慢路径。

这就是本文要补齐的内容：**解释器侧的四个分配字节码的完整汇编模板实现**。

### 四个分配字节码概览

| 字节码 | 操作码 | Java 源码 | 栈变化 | 有快速路径？ |
|--------|--------|-----------|--------|-------------|
| `new` | 0xBB | `new MyClass()` | → objectref | ✅ 纯汇编快速路径 |
| `newarray` | 0xBC | `new int[10]` | count → arrayref | ❌ 全部走 VM |
| `anewarray` | 0xBD | `new Object[10]` | count → arrayref | ❌ 全部走 VM |
| `multianewarray` | 0xC5 | `new int[3][4]` | count1,count2,... → arrayref | ❌ 全部走 VM |

**关键发现**：只有 `new` 有解释器侧的汇编快速路径，三种数组分配全部直接 `call_VM`！这是因为：
- `new` 的对象大小在**编译时已知**（缓存在 `Klass::_layout_helper`），可以在汇编中直接 bump pointer
- 数组的大小是**运行时决定的**（length 在栈上），需要动态计算 `header + length * element_size`，还需要检查 length 合法性，逻辑太复杂不值得在汇编中做

## 2. 字节码模板定义

> 源码：`src/hotspot/share/interpreter/templateTable.cpp:448`

```cpp
def(Bytecodes::_new           , ubcp|____|clvm|____, vtos, atos, _new          ,  _  );
def(Bytecodes::_newarray      , ubcp|____|clvm|____, itos, atos, newarray      ,  _  );
def(Bytecodes::_anewarray     , ubcp|____|clvm|____, itos, atos, anewarray     ,  _  );
def(Bytecodes::_multianewarray, ubcp|____|clvm|____, vtos, atos, multianewarray,  _  );
```

### 解读各字段

| 字节码 | 标志 | 输入 TOS | 输出 TOS | 含义 |
|--------|------|----------|----------|------|
| `new` | `ubcp\|clvm` | `vtos` | `atos` | 需要读取 bcp 操作数；可能调 VM；栈空→对象引用 |
| `newarray` | `ubcp\|clvm` | `itos` | `atos` | 栈顶 int(count)→对象引用 |
| `anewarray` | `ubcp\|clvm` | `itos` | `atos` | 栈顶 int(count)→对象引用 |
| `multianewarray` | `ubcp\|clvm` | `vtos` | `atos` | 多个 count 已在栈上→对象引用 |

**`clvm` 标志**意味着这些字节码"可能调用 VM 运行时"。但 `new` 的快速路径实际上不调 VM，只在慢路径才调。

## 3. TemplateTable::_new() — 解释器核心快速路径

> 源码：`src/hotspot/cpu/x86/templateTable_x86.cpp:3991`

这是整个 JVM 中**性能最关键的字节码之一**。我们逐行分析它生成的每一条 x86 指令。

### 3.1 整体流程骨架

```
TemplateTable::_new()
  │
  ├─ Phase 1: 读取常量池索引 (2 字节)
  │
  ├─ Phase 2: 检查类已解析？
  │    └─ 否 → slow_case_no_pop
  │
  ├─ Phase 3: 加载 InstanceKlass*，push 到栈保存
  │
  ├─ Phase 4: 检查类已完全初始化？
  │    └─ 否 → slow_case
  │
  ├─ Phase 5: 读取 layout_helper (对象字节大小)
  │    └─ 检查 slow_path_bit (有 finalizer?) → slow_case
  │
  ├─ Phase 6: TLAB 分配 (tlab_allocate 汇编宏)
  │    └─ 失败 → slow_case
  │
  ├─ Phase 7: 字段清零 (循环写 0)
  │
  ├─ Phase 8: 初始化对象头 (mark word + klass pointer)
  │
  ├─ Phase 9: DTrace 探针 (如果开启)
  │
  └─ done: 对象引用在 rax 中，作为 atos 返回
```

### 3.2 Phase 1: 读取常量池索引

```cpp
transition(vtos, atos);
__ get_unsigned_2_byte_index_at_bcp(rdx, 1);
```

**生成的汇编**：
```asm
movzwl  rdx, WORD PTR [r13 + 1]    ; r13 = bcp, 读取 bcp+1 处的 2 字节索引
bswap   edx                        ; 大端→小端转换 (class file 是大端)
shrl    edx, 16                    ; 右移 16 位得到实际索引
```

`rdx` 现在存储常量池索引（指向 `CONSTANT_Class_info`）。

### 3.3 Phase 2: 检查类已解析

```cpp
__ get_cpool_and_tags(rcx, rax);
// rcx = 当前方法的 ConstantPool*
// rax = ConstantPool 的 tags 数组

const int tags_offset = Array<u1>::base_offset_in_bytes();
__ cmpb(Address(rax, rdx, Address::times_1, tags_offset), JVM_CONSTANT_Class);
__ jcc(Assembler::notEqual, slow_case_no_pop);
```

**生成的汇编**：
```asm
; 获取 ConstantPool 和 tags
mov     rcx, QWORD PTR [rbp + frame::interpreter_frame_cache_offset]  ; ConstantPoolCache
mov     rcx, QWORD PTR [rcx + ConstantPoolCache::constant_pool_offset()] ; ConstantPool
mov     rax, QWORD PTR [rcx + ConstantPool::tags_offset()]  ; tags Array<u1>*

; 检查 tags[index] == JVM_CONSTANT_Class (= 7)
cmp     BYTE PTR [rax + rdx + 0x10], 0x7   ; 0x10 = Array<u1>::base_offset
jne     slow_case_no_pop                    ; 不是已解析的类 → 慢路径
```

**为什么检查 tag？** 常量池中的 `CONSTANT_Class_info` 在首次使用时会被"解析"（resolved）：tag 从 `JVM_CONSTANT_UnresolvedClass` 变为 `JVM_CONSTANT_Class`，同时存储指向 `InstanceKlass` 的指针。如果 tag 不是 `JVM_CONSTANT_Class`，说明类还没解析过，必须走 C++ 慢路径触发类加载。

### 3.4 Phase 3: 加载 InstanceKlass 并保存

```cpp
__ load_resolved_klass_at_index(rcx, rdx, rcx);
__ push(rcx);  // save the contexts of klass for initializing the header
```

**生成的汇编**：
```asm
; ConstantPool 的 resolved_klasses 数组
mov     rcx, QWORD PTR [rcx + ConstantPool::resolved_klasses_offset()]
; 加载 InstanceKlass* (通过索引)
mov     rcx, QWORD PTR [rcx + rdx*8 + Array<Klass*>::base_offset]

; 保存到 Java 表达式栈（后面初始化头部时需要）
push    rcx
```

此时 `rcx` = `InstanceKlass*`。将其 push 到栈上保存，因为后续的 TLAB 分配会覆盖 `rcx`。

### 3.5 Phase 4: 检查类已完全初始化

```cpp
__ cmpb(Address(rcx, InstanceKlass::init_state_offset()), InstanceKlass::fully_initialized);
__ jcc(Assembler::notEqual, slow_case);
```

**生成的汇编**：
```asm
cmp     BYTE PTR [rcx + InstanceKlass::init_state_offset()], 0x4  ; fully_initialized = 4
jne     slow_case
```

**InstanceKlass 的初始化状态**：

| 值 | 状态 | 含义 |
|----|------|------|
| 0 | `allocated` | 刚分配 |
| 1 | `loaded` | 已加载 |
| 2 | `linked` | 已链接 |
| 3 | `being_initialized` | 正在执行 `<clinit>` |
| 4 | `fully_initialized` | 初始化完成 ✓ |
| 5 | `initialization_error` | 初始化失败 |

只有 `fully_initialized` 才能走快速路径。如果类正在初始化（另一个线程在执行 `<clinit>`），必须走慢路径等待。

### 3.6 Phase 5: 读取对象大小并检查 slow_path_bit

```cpp
__ movl(rdx, Address(rcx, Klass::layout_helper_offset()));
__ testl(rdx, Klass::_lh_instance_slow_path_bit);
__ jcc(Assembler::notZero, slow_case);
```

**生成的汇编**：
```asm
mov     edx, DWORD PTR [rcx + Klass::layout_helper_offset()]  ; layout_helper
test    edx, 0x1                                               ; _lh_instance_slow_path_bit
jnz     slow_case
```

**layout_helper 对于普通实例对象的编码**：

```
对于实例对象 (layout_helper > 0):
  ┌───────────────────────────────────────────┐
  │ 31                                      0 │
  │  [对象大小（字节）]  [slow_path_bit(bit0)] │
  └───────────────────────────────────────────┘

  示例: new Object()
    layout_helper = 0x10 = 16 字节 (mark 8B + klass 4B + padding 4B)
    bit 0 = 0 → 无 slow path

  示例: 有 finalizer 的类
    layout_helper = 0x11 = 16 字节 + slow_path_bit
    bit 0 = 1 → 需要走慢路径注册 Finalizer
```

**`_lh_instance_slow_path_bit` 在什么时候被设置？** 在 `ClassFileParser::layout_and_allocate` 计算布局时，如果类：
1. 覆盖了 `finalize()` 方法（不是 `Object.finalize()`）
2. 对象大小需要特殊对齐

就会设置 bit 0 为 1，迫使走 C++ 慢路径。

此时 `rdx` = 对象大小（字节，已包含对象头），且确认无 slow_path_bit。

### 3.7 Phase 6: TLAB 分配

```cpp
if (UseTLAB) {
    __ tlab_allocate(thread, rax, rdx, 0, rcx, rbx, slow_case);
    if (ZeroTLAB) {
        __ jmp(initialize_header);
    } else {
        __ jmp(initialize_object);
    }
}
```

`tlab_allocate` 是一个**宏汇编函数**，委托给 `BarrierSetAssembler::tlab_allocate()`。下一章详细展开。

传入的参数：
- `thread` = `r15_thread`（LP64 下线程寄存器）
- `rax` = 输出寄存器（分配到的对象地址）
- `rdx` = 对象大小（字节）
- `0` = con_size_in_bytes（常量大小，这里用变量大小所以传 0）
- `rcx`, `rbx` = 临时寄存器
- `slow_case` = 失败标签

### 3.8 Phase 7: 字段清零

```cpp
__ bind(initialize_object);
__ decrement(rdx, sizeof(oopDesc));     // rdx -= 16 (减去对象头大小)
__ jcc(Assembler::zero, initialize_header); // 如果对象只有头部(rdx==0)，跳过清零

__ xorl(rcx, rcx);    // rcx = 0, 用于清零
__ shrl(rdx, LogBytesPerLong); // rdx /= 8, 转为 long 单位

// 循环清零
{ Label loop;
  __ bind(loop);
  __ movptr(Address(rax, rdx, Address::times_8, sizeof(oopDesc) - 1*oopSize), rcx);
  __ decrement(rdx);
  __ jcc(Assembler::notZero, loop);
}
```

**生成的汇编**：
```asm
; rdx = object_size_in_bytes
sub     edx, 16                        ; 减去 oopDesc 头部大小
je      initialize_header              ; 空对象(如Object)跳过

xor     ecx, ecx                      ; rcx = 0
shr     edx, 3                        ; rdx /= 8 (字节→long单位)

loop:
  mov   QWORD PTR [rax + rdx*8 + 16 - 8], rcx   ; 清零一个 long
  dec   rdx
  jnz   loop
```

**为什么从后往前清零？** 因为使用 `rdx` 作为递减计数器。第一次写入的是对象末尾 `[rax + sizeof(oopDesc) + (n-1)*8]`，最后写入的是 `[rax + sizeof(oopDesc)]`。这样可以利用 `dec + jnz` 自然终止循环。

**性能特征**：对于小对象（如 4 个字段 = 32 字节字段区），循环执行 4 次。对于空 Object（0 字段），完全跳过。

### 3.9 Phase 8: 初始化对象头

```cpp
__ bind(initialize_header);
if (UseBiasedLocking) {
    __ pop(rcx);   // 恢复 InstanceKlass*
    __ movptr(rbx, Address(rcx, Klass::prototype_header_offset()));
    __ movptr(Address(rax, oopDesc::mark_offset_in_bytes()), rbx);
} else {
    __ movptr(Address(rax, oopDesc::mark_offset_in_bytes()),
              (intptr_t)markOopDesc::prototype()); // = 0x1
    __ pop(rcx);   // 恢复 InstanceKlass*
}
// 压缩 klass 指针处理
__ xorl(rsi, rsi);
__ store_klass_gap(rax, rsi);  // offset 12 = 0 (4字节 gap)
__ store_klass(rax, rcx);       // offset 8 = 编码后的 klass 指针
```

**生成的汇编（-XX:-UseBiasedLocking 时）**：
```asm
; 设置 mark word = prototype (0x1 = 无锁/无hash/age=0)
mov     QWORD PTR [rax + 0], 0x1

; 恢复 klass 指针
pop     rcx                            ; rcx = InstanceKlass*

; 设置 klass gap（压缩oops模式下 offset 12 的 4 字节间隙）
xor     esi, esi
mov     DWORD PTR [rax + 12], esi      ; gap = 0

; 设置 klass pointer（压缩模式：编码后存入 offset 8）
; encode_klass_not_null: rcx → 编码值
; 假设 base=0, shift=3: encoded = rcx >> 3
shr     rcx, 3
mov     DWORD PTR [rax + 8], ecx       ; 4 字节压缩 klass
```

**生成的汇编（-XX:+UseBiasedLocking 时）**：
```asm
pop     rcx                            ; rcx = InstanceKlass*
; 从 klass 的 prototype_header 获取偏向模式的 mark word
mov     rbx, QWORD PTR [rcx + Klass::prototype_header_offset()]
mov     QWORD PTR [rax + 0], rbx       ; mark word = 偏向锁初始值

xor     esi, esi
mov     DWORD PTR [rax + 12], esi
shr     rcx, 3
mov     DWORD PTR [rax + 8], ecx
```

**对象初始化后的内存布局（-XX:-UseBiasedLocking, UseCompressedOops）**：

```
rax →  ┌──────────────────────────────┐
 +0    │  mark word = 0x0000000000000001│  8 字节 (无锁 prototype)
 +8    │  klass (compressed) = encode(k)│  4 字节 (压缩 klass 指针)
+12    │  klass gap = 0x00000000        │  4 字节 (对齐填充)
+16    │  field1 = 0x0000000000000000   │  已清零
+24    │  field2 = 0x0000000000000000   │  已清零
       │  ...                           │
       └──────────────────────────────┘
```

- `slow_case_no_pop`：在 Phase 2 检查 tag 时触发，此时还没 push

## 4. BarrierSetAssembler::tlab_allocate — TLAB 分配汇编

> 源码：`src/hotspot/cpu/x86/gc/shared/barrierSetAssembler_x86.cpp:219`

这是 `TemplateTable::_new()` 中调用的 `tlab_allocate` 宏展开后的实际汇编生成代码。

### 4.1 完整源码

```cpp
void BarrierSetAssembler::tlab_allocate(MacroAssembler* masm,
                                        Register thread, Register obj,
                                        Register var_size_in_bytes,
                                        int con_size_in_bytes,
                                        Register t1, Register t2,
                                        Label& slow_case) {
  Register end = t2;  // end = rbx

  __ movptr(obj, Address(thread, JavaThread::tlab_top_offset()));    // obj = tlab._top
  if (var_size_in_bytes == noreg) {
    __ lea(end, Address(obj, con_size_in_bytes));                    // end = top + 常量大小
  } else {
    __ lea(end, Address(obj, var_size_in_bytes, Address::times_1));  // end = top + 变量大小
  }
  __ cmpptr(end, Address(thread, JavaThread::tlab_end_offset()));    // end vs tlab._end
  __ jcc(Assembler::above, slow_case);                               // end > _end → 失败

  // update the tlab top pointer
  __ movptr(Address(thread, JavaThread::tlab_top_offset()), end);    // tlab._top = end
}
```

### 4.2 生成的 x86-64 汇编

在 `TemplateTable::_new()` 的上下文中，参数映射为：
- `thread` = `r15`（线程寄存器）
- `obj` = `rax`（输出：对象地址）
- `var_size_in_bytes` = `rdx`（对象大小）
- `end` = `rbx`（临时：new_top）

```asm
; obj = thread->tlab._top
mov     rax, QWORD PTR [r15 + JavaThread::tlab_top_offset()]

; end = obj + size
lea     rbx, [rax + rdx]

; if (end > thread->tlab._end) goto slow_case
cmp     rbx, QWORD PTR [r15 + JavaThread::tlab_end_offset()]
ja      slow_case

; thread->tlab._top = end  (bump the pointer!)
mov     QWORD PTR [r15 + JavaThread::tlab_top_offset()], rbx
```

### 4.3 指令级性能分析

| 指令 | 延迟 | 说明 |
|------|------|------|
| `mov rax, [r15+off]` | ~4 cycle (L1 命中) | 读 TLAB top，线程热数据在 L1 |
| `lea rbx, [rax+rdx]` | 1 cycle | 地址计算，无内存访问 |
| `cmp rbx, [r15+off]` | ~4 cycle (L1 命中) | 读 TLAB end |
| `ja slow_case` | ~1 cycle (预测成功) | 99.9%+ 不跳转 |
| `mov [r15+off], rbx` | ~4 cycle (L1 写入) | 更新 TLAB top |

**总计：约 5-6 条指令，~10-14 个时钟周期**。对比 `malloc()` 的 ~50-200 周期，这快了一个数量级。

**为什么无需 CAS？** TLAB 是**线程私有的**（Thread Local Allocation Buffer），每个线程有自己独立的 `_top` 和 `_end`。不存在竞争，所以简单的 `mov` 就够了。

## 5. BarrierSetAssembler::eden_allocate — Eden 直接分配

> 源码：`barrierSetAssembler_x86.cpp:268`

当 `UseTLAB = false` 时（极少见），解释器退化到 Eden 直接分配路径。这条路径需要 CAS 来处理多线程竞争。

### 5.1 完整汇编

```asm
retry:
  ; obj = *(Universe::heap()->top_addr())   — 全局堆 top 指针
  mov     rax, QWORD PTR [heap_top_addr]

  ; end = obj + size
  lea     end, [rax + rdx]

  ; 溢出检查: end < obj → 地址回绕，对象太大
  cmp     end, rax
  jb      slow_case

  ; 边界检查: end > heap_end → 堆满
  cmp     end, QWORD PTR [heap_end_addr]
  ja      slow_case

  ; CAS: compare-and-swap(top_addr, rax, end)
  ; 如果 *top_addr == rax，则 *top_addr = end，成功
  ; 否则 rax = 当前 *top_addr，失败重试
  lock cmpxchg QWORD PTR [heap_top_addr], end
  jne     retry
```

### 5.2 与 TLAB 分配的对比

| 维度 | TLAB 分配 | Eden 直接分配 |
|------|-----------|--------------|
| 线程安全 | 无需（线程私有） | CAS 循环 |
| 指令数 | 5 条 | 8+ 条 |
| 竞争 | 无 | 高并发时严重 |
| 延迟 | ~10 cycle | ~30-200 cycle (取决于竞争) |
| 使用条件 | `UseTLAB=true`（默认） | `UseTLAB=false` 或 G1 不支持 |

**注意**：在 G1 GC 下，`supports_inline_contig_alloc()` 返回 `false`，因为 G1 的堆不是一个连续空间。所以 G1 + `-XX:-UseTLAB` 的情况下，`eden_allocate` 会直接 `jmp slow_case`，完全走 C++ 路径。

## 6. TemplateTable::_new() 汇编指令完整流程图

将上述所有阶段串联，展示从字节码入口到返回的完整汇编流程：

```
vtos entry (从空栈状态进入):
  push_ptr / push_i / ...        ; 如果前一指令留了值在寄存器，先push到栈
  ↓
_new 汇编模板开始:
  ┌─────────────────────────────────────────────────────────────────────────┐
  │ movzwl rdx, [r13+1]; bswap edx; shr edx,16  ; 读取 2字节 CP 索引     │
  │                                                                        │
  │ mov rcx, [rbp + cp_cache_off]                 ; 获取 ConstantPool     │
  │ mov rcx, [rcx + cp_offset]                                            │
  │ mov rax, [rcx + tags_offset]                  ; 获取 tags 数组        │
  │                                                                        │
  │ cmp BYTE [rax+rdx+0x10], 0x7                  ; tag == Class?         │
  │ jne slow_case_no_pop ──────────────────────────────────► [慢路径]      │
  │                                                                        │
  │ mov rcx, [rcx + resolved_klasses_off]          ; 加载 Klass*          │
  │ mov rcx, [rcx + rdx*8 + base]                                        │
  │ push rcx                                       ; 保存 klass          │
  │                                                                        │
  │ cmp BYTE [rcx + init_state_off], 0x4           ; fully_initialized?  │
  │ jne slow_case ─────────────────────────────────────────► [慢路径]      │
  │                                                                        │
  │ mov edx, [rcx + layout_helper_off]             ; 对象大小(字节)       │
  │ test edx, 0x1                                  ; slow_path_bit?       │
  │ jnz slow_case ─────────────────────────────────────────► [慢路径]      │
  │                                                                        │
  │ ┌─── TLAB bump-the-pointer ────────────────────────────────────────┐  │
  │ │ mov rax, [r15 + tlab_top_off]            ; rax = tlab._top       │  │
  │ │ lea rbx, [rax + rdx]                     ; rbx = top + size      │  │
  │ │ cmp rbx, [r15 + tlab_end_off]            ; rbx > tlab._end?     │  │
  │ │ ja  slow_case ──────────────────────────────────────► [慢路径]    │  │
  │ │ mov [r15 + tlab_top_off], rbx            ; tlab._top = rbx ✓    │  │
  │ └──────────────────────────────────────────────────────────────────┘  │
  │                                                                        │
  │ ; ─── 对象初始化 ───                                                   │
  │ sub edx, 16                                    ; rdx -= oopDesc size │
  │ je  init_header                                ; 空对象？跳过清零      │
  │ xor ecx, ecx                                                          │
  │ shr edx, 3                                     ; 字节→long 单位       │
  │ loop: mov [rax+rdx*8+16-8], rcx               ; 循环清零              │
  │       dec rdx                                                          │
  │       jnz loop                                                         │
  │                                                                        │
  │ init_header:                                                           │
  │ mov QWORD [rax+0], 0x1                         ; mark word = prototype│
  │ pop rcx                                        ; 恢复 klass           │
  │ xor esi, esi                                                           │
  │ mov DWORD [rax+12], esi                        ; klass gap = 0        │
  │ shr rcx, 3                                     ; 编码 klass 指针      │
  │ mov DWORD [rax+8], ecx                         ; 设置 klass           │
  │                                                                        │
  │ jmp done                                                               │
  │                                                                        │
  │ slow_case:                                                             │
  │   pop rcx                                      ; 恢复栈平衡           │
  │ slow_case_no_pop:                                                      │
  │   mov rdi, [rbp + cp_off]                      ; arg1: ConstantPool  │
  │   movzwl rsi, [r13+1]; bswap esi; shr esi,16   ; arg2: index         │
  │   call InterpreterRuntime::_new                                       │
  │                                                                        │
  │ done:                                                                  │
  │   ; rax = 新对象的 oop → 作为 atos 返回                                │
  └─────────────────────────────────────────────────────────────────────────┘
  ↓
dispatch_next(atos):
  inc r13                                    ; bcp += bytecode_length
  movzbl ebx, [r13]                          ; 读取下一字节码
  jmp [r15 + dispatch_table + rbx*8]         ; 跳转执行
```

**总指令数（快速路径成功时）**：约 **25 条 x86 指令**。这就是为什么 Java 对象分配几乎和 C 的栈分配一样快。

## 7. TemplateTable::newarray() — 基本类型数组分配

> 源码：`templateTable_x86.cpp:4144`

### 7.1 Java 层

```java
int[] arr = new int[10];    // → newarray T_INT, count
byte[] buf = new byte[1024]; // → newarray T_BYTE, count
```

### 7.2 字节码格式

```
newarray (0xBC)
  操作数: 1 字节 atype (基本类型编码)
  栈:    ..., count → ..., arrayref

atype 编码:
  T_BOOLEAN = 4, T_CHAR = 5, T_FLOAT = 6, T_DOUBLE = 7
  T_BYTE = 8, T_SHORT = 9, T_INT = 10, T_LONG = 11
```

### 7.3 模板实现

```cpp
void TemplateTable::newarray() {
  transition(itos, atos);
  __ load_unsigned_byte(c_rarg1, at_bcp(1));   // rsi = atype (从字节码读取)
  call_VM(rax, CAST_FROM_FN_PTR(address, InterpreterRuntime::newarray),
          c_rarg1, rax);                        // 调用 VM: newarray(atype, count)
}
```

**生成的汇编**：
```asm
; 此时 eax = count (itos 状态，栈顶 int 在 eax 中)
movzbl  esi, BYTE PTR [r13 + 1]    ; rsi = atype (读取 bcp+1 处的类型编码)
; 参数: rdi=thread, rsi=atype, rdx=count(rax)
mov     edx, eax                    ; rdx = count
call    InterpreterRuntime::newarray
```

**为什么没有快速路径？** 原因：
1. 数组大小是**运行时动态的**：`size = header + length * element_size`，需要动态计算
2. 需要检查 `length >= 0`（`NegativeArraySizeException`）
3. 需要检查 `length <= max_array_length`（防止 OOM）
4. 需要在对象中设置 `_length` 字段（对象头之后的 4 字节）
5. 数组的 header 大小因压缩指针配置而异

这些检查和计算在汇编中实现过于复杂，收益不高（大多数场景数组分配频率远低于对象分配）。

### 7.5 TypeArrayKlass::allocate_common() 细节

> 源码：`typeArrayKlass.cpp:101`

```cpp
typeArrayOop TypeArrayKlass::allocate_common(int length, bool do_zero, TRAPS) {
  if (length >= 0) {
    if (length <= max_length()) {
      size_t size = typeArrayOopDesc::object_size(layout_helper(), length);
      return (typeArrayOop)Universe::heap()->array_allocate(this, (int)size, length,
                                                            do_zero, CHECK_NULL);
    } else {
      report_java_out_of_memory("Requested array size exceeds VM limit");
      THROW_OOP_0(Universe::out_of_memory_error_array_size());
    }
  } else {
    THROW_MSG_0(vmSymbols::java_lang_NegativeArraySizeException(), err_msg("%d", length));
  }
}
```

**三种异常情况**：
1. `length < 0` → `NegativeArraySizeException`
2. `length > max_length()` → `OutOfMemoryError: Requested array size exceeds VM limit`
3. 堆空间不足 → `OutOfMemoryError: Java heap space`

**`max_length()` 的计算**：在 `TypeArrayKlass` 构造时设置：
```cpp
set_max_length(arrayOopDesc::max_array_length(type));
// max_array_length = (max_heap_size - header_size) / element_size
// 对于 int[]: (2^31 - 16) / 4 ≈ 536,870,900
```

> 源码：`templateTable_x86.cpp:4513`

### 9.1 Java 层

```java

Object[][][] cube = new Object[2][3][]; // → multianewarray #CP_index, 2 (最后维度可以为空)
```

### 9.2 字节码格式

```
multianewarray (0xC5)
  操作数: 2 字节 indexbyte1, indexbyte2 (常量池索引)
          1 字节 dimensions (维度数，1-255)
  栈:    ..., count1, count2, ..., countN → ..., arrayref
```

### 9.3 模板实现

```cpp
void TemplateTable::multianewarray() {
  transition(vtos, atos);
  __ load_unsigned_byte(rax, at_bcp(3));  // rax = dimensions (第 3 字节)

  // 计算栈上第一个 count 的地址
  // first_addr = rsp + (ndims - 1) * stackElementSize - wordSize
  __ lea(c_rarg1, Address(rsp, rax, Interpreter::stackElementScale(), -wordSize));

  call_VM(rax, CAST_FROM_FN_PTR(address, InterpreterRuntime::multianewarray), c_rarg1);

  // 清理栈上的维度参数
  __ load_unsigned_byte(rbx, at_bcp(3));
  __ lea(rsp, Address(rsp, rbx, Interpreter::stackElementScale()));
}
```

**生成的汇编**：
```asm
movzbl  eax, BYTE PTR [r13 + 3]     ; eax = dimensions
lea     rsi, [rsp + rax*8 - 8]      ; rsi = &first_size (栈上第一个 count 的地址)

call    InterpreterRuntime::multianewarray

; 清理栈：弹出 dimensions 个参数
movzbl  ebx, BYTE PTR [r13 + 3]
lea     rsp, [rsp + rbx*8]          ; rsp += dimensions * 8
```

### 9.4 InterpreterRuntime::multianewarray() 慢路径


## 10. Klass::layout_helper 编码详解

> 源码：`src/hotspot/share/oops/klass.hpp:348`

`layout_helper` 是一个 32-bit 整数，编码了类的"大小信息"，是 `new` 快速路径的关键。

### 10.1 三种编码模式

```
┌──────────────────────────────────────────────────────────┐
│              layout_helper 编码规则                       │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  (1) 实例对象 (layout_helper > 0):                       │
│      ┌─────────────────────────────────────────┐         │
│      │ 31                                    0 │         │
│      │  [      对象大小（字节）      ] [spb]   │         │
│      └─────────────────────────────────────────┘         │
│      spb = slow_path_bit (bit 0)                         │
│                                                          │
│  (2) 非数组非实例 (layout_helper == 0):                  │
│      _lh_neutral_value = 0                               │
│      用于 InstanceMirrorKlass 等特殊类                    │
│                                                          │
│  (3) 数组 (layout_helper < 0):                           │
│      ┌──┬──────────┬────────────┬────────────┐          │
│      │31│30      24│23        16│15         0│          │
│      │tag│hdr_size │ elem_type │log2_elm_sz │          │
│      └──┴──────────┴────────────┴────────────┘          │
│      tag: 11 = typeArray, 10 = objArray                  │
│      hdr_size: 数组头部大小(字节)                        │
│      elem_type: T_BOOLEAN..T_OBJECT                      │
│      log2_elm_sz: 0(byte),1(short),2(int),3(long)       │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 10.2 位域常量定义

```cpp
static const int _lh_neutral_value           = 0;
static const int _lh_instance_slow_path_bit  = 0x01;
static const int _lh_log2_element_size_shift = 0;    // bits [0..5]
static const int _lh_log2_element_size_mask  = 63;   // BitsPerLong - 1
static const int _lh_element_type_shift      = 8;    // bits [8..15]
static const int _lh_element_type_mask       = 0xFF;
static const int _lh_header_size_shift       = 16;   // bits [16..23]
static const int _lh_header_size_mask        = 0xFF;
static const int _lh_array_tag_shift         = 30;   // bits [30..31]
static const int _lh_array_tag_obj_value     = ~0x01; // = 0xFFFFFFFE >> 30 = -2 (10b)
static const unsigned int _lh_array_tag_type_value = 0xFFFFFFFF; // = -1 (11b)
```

### 10.3 具体示例

| 类型 | layout_helper (十六进制) | 含义 |
|------|--------------------------|------|
| `Object` | `0x00000010` | 16 字节，无 slow_path |
| `有 finalizer 的类` | `0x00000011` | 16 字节 + slow_path_bit |
| `有 3 个 int 字段的类` | `0x00000028` | 40 字节 (16 + 3*8 = 40) |
| `int[]` | `0xC0001002` | typeArray, hdr=16, T_INT=10, log2=2 |
| `byte[]` | `0xC0001000` | typeArray, hdr=16, T_BYTE=8, log2=0 |
| `long[]` | `0xC0001003` | typeArray, hdr=16, T_LONG=11, log2=3 |
| `Object[]` | `0x80001004` | objArray, hdr=16, T_OBJECT=12, log2=2(压缩) |

### 10.4 数组大小计算

从 `layout_helper` 计算数组对象总字节数：

```cpp
static int typeArrayOopDesc::object_size(jint lh, int length) {
  int hdr = Klass::layout_helper_header_size(lh);    // (lh >> 16) & 0xFF
  int l2e = Klass::layout_helper_log2_element_size(lh); // lh & 0x3F
  int size = (hdr + ((size_t)length << l2e) + MinObjAlignmentInBytesMask)
             >> LogMinObjAlignmentInBytes;
  return size;  // HeapWord 单位
}
```

示例：`new int[10]`
```
hdr = 16 字节
l2e = 2 (每元素 4 字节)
size = (16 + 10 * 4 + 7) >> 3 = (16 + 40 + 7) >> 3 = 63 >> 3 = 7 HeapWords = 56 字节

实际布局:
  mark(8) + klass(4) + gap(4) = 16 字节头
  + 10 * 4 = 40 字节数据
  = 56 字节 (已对齐到 8 字节)
```

## 11. InterpreterRuntime::_new() 慢路径完整分析

> 源码：`interpreterRuntime.cpp:217`

当 `TemplateTable::_new()` 的任何快速路径检查失败时，落入 C++ 慢路径。

### 11.1 完整源码

```cpp
IRT_ENTRY(void, InterpreterRuntime::_new(JavaThread* thread, ConstantPool* pool, int index))
  Klass* k = pool->klass_at(index, CHECK);              // ① 解析类
  InstanceKlass* klass = InstanceKlass::cast(k);

  klass->check_valid_for_instantiation(true, CHECK);     // ② 合法性检查
  klass->initialize(CHECK);                               // ③ 触发类初始化

  oop obj = klass->allocate_instance(CHECK);              // ④ 分配对象
  thread->set_vm_result(obj);                             // ⑤ 返回结果
IRT_END
```

### 11.2 五步详解

**① `pool->klass_at(index)`**

如果常量池中这个 index 对应的类还没解析（tag 不是 `JVM_CONSTANT_Class`），会触发完整的类加载链路：

```
pool->klass_at(index)
  └── klass_at_impl(pool, index)
        └── SystemDictionary::resolve_or_fail(name, loader, ...)
              └── SystemDictionary::resolve_instance_class_or_null(...)
                    └── ClassLoader.loadClass() → Java 层双亲委派
```

这就是为什么第一次 `new SomeClass()` 比较慢——需要走完类加载。

**② `check_valid_for_instantiation()`**

```cpp
void InstanceKlass::check_valid_for_instantiation(bool throwError, TRAPS) {
  if (is_interface() || is_abstract()) {
    THROW_MSG(throwError ? vmSymbols::java_lang_InstantiationError()
                         : vmSymbols::java_lang_InstantiationException(),
              external_name());
  }
}
```

不能 `new` 一个接口或抽象类。

**③ `klass->initialize()`**

如果类状态不是 `fully_initialized`，会触发初始化：

```
klass->initialize()
  └── InstanceKlass::initialize_impl()
        ├── 等待其他线程完成初始化（如果 being_initialized 且不是当前线程）
        ├── 初始化父类
        ├── 执行 <clinit>
        └── 标记为 fully_initialized
```

**④ `allocate_instance()`**

进入 `ch02_object_allocation.md` 中详述的 C++ 分配链路：
```
InstanceKlass::allocate_instance()
  └── CollectedHeap::obj_allocate(klass, size)
        └── ObjAllocator::allocate()
              └── MemAllocator::allocate()
                    └── TLAB → G1 → HeapRegion ...
```

**⑤ `set_vm_result(obj)`**

将结果写入线程的 `_vm_result` 字段，`call_VM` 宏在返回后会将其加载到 `rax`。

### 11.3 慢路径触发条件总结

| 条件 | 频率 | 后果 |
|------|------|------|
| 类未解析 | 首次使用 | 触发类加载（可能很慢） |
| 类未初始化 | 首次使用 | 执行 `<clinit>` |
| 有 finalizer | 每次 | 需要注册到 FinalizerThread |
| TLAB 空间不足 | 偶尔 | TLAB refill 或堆分配 |
| 类正在初始化 | 极少 | 等待其他线程完成 `<clinit>` |

## 15. 面试高频问答

### Q1: "new 一个对象在 JVM 底层经历了什么？"

**源码级回答**：

> 解释器为 `new` 字节码生成了一段 x86 汇编快速路径（约 25 条指令）：
> 1. 从字节码读取常量池索引，检查类已解析（tag == `JVM_CONSTANT_Class`）
> 2. 加载 `InstanceKlass*`，检查 `init_state == fully_initialized`
> 3. 读取 `layout_helper`（对象字节大小），检查无 `slow_path_bit`（无 finalizer）
> 4. **TLAB bump-the-pointer**：`new_top = tlab._top + size`，如果 `new_top <= tlab._end` 则设置 `tlab._top = new_top`
> 5. 循环清零字段区域
> 6. 设置 mark word = `0x1`（无锁 prototype），设置压缩 klass 指针
>
> 如果上述任何检查失败，fall through 到 C++ 慢路径 `InterpreterRuntime::_new()`，触发类加载/初始化/MemAllocator 框架。
>
> 整个快速路径约 10 个时钟周期，无锁、无 CAS、无系统调用。源码在 `templateTable_x86.cpp:3991`。

### Q2: "为什么 Java 对象分配几乎和 C 的栈分配一样快？"

> 因为 TLAB 是**线程私有的连续内存块**（Thread Local Allocation Buffer），分配操作简化为一个指针移动（`_top += size`），完全没有多线程竞争。而 C 的 `malloc()` 需要在全局堆上加锁（或使用复杂的 free list），开销比 TLAB bump pointer 高一个数量级。

### Q3: "为什么 newarray/anewarray 没有汇编快速路径，但 new 有？"

> 因为 `new` 的对象大小在**类加载时已确定**（缓存在 `Klass::_layout_helper`），解释器可以直接从 klass 中读取一个整数作为 bump pointer 的增量。
> 
> 数组的大小是**运行时决定的**（`size = header + length * element_size`），还需要检查 length 非负、不超过 `max_array_length`，计算对齐后的总大小——这些在汇编中实现过于复杂，且数组分配频率远低于普通对象分配，投入产出比不高。

### Q4: "layout_helper 是什么？怎么区分实例和数组？"

> `layout_helper` 是 `Klass` 中的一个 32-bit 整数，编码了类的大小信息：
> - **`> 0`**：实例对象，值 = 对象字节大小（低位 bit 0 是 slow_path_bit）
> - **`== 0`**：中性值（InstanceMirrorKlass 等特殊类）
> - **`< 0`**：数组，高 2 位是 tag（11=typeArray, 10=objArray），中间存储 header_size、element_type、log2_element_size
>
> 例如 `new Object()` 的 layout_helper = `0x10` = 16 字节。
> `int[]` 的 layout_helper = `0xC0001002`（负数，tag=11, hdr=16, T_INT, log2=2）。

### Q5: "new 的 slow_path_bit 什么时候被设置？"

> 在类加载的 `ClassFileParser::layout_and_allocate()` 阶段计算对象布局时，如果类覆盖了 `finalize()` 方法（不是 `Object.finalize()`），就会设置 `_lh_instance_slow_path_bit`（bit 0 = 1）。
>
> 这迫使解释器走 C++ 慢路径，在 `InstanceKlass::allocate_instance()` 中调用 `register_finalizer()` 将对象注册到 `FinalizerThread` 队列。
