## 1. 反优化概述

### 1.1 什么是反优化？

JIT 编译器基于**某些假设**生成优化代码，当这些假设失效时需要**回退到解释执行**：

| 触发原因 | 说明 |
|----------|------|
| 类加载 | 新加载的类改变了类层次结构 |
| 乐观假设失败 | 如类型预测错误、null 检查失败 |
| 热点代码调试 | 调试器需要访问帧变量 |
| 异常处理 | 编译代码中发生未预期异常 |
| OSR (On-Stack Replacement) | 循环内从解释切换到编译 |
| JVMTI | 强制弹出帧、提前返回等 |

### 1.2 反优化流程

```
JIT 编译代码执行
        ↓
检测到需要反优化
        ↓
保存当前状态（寄存器、表达式栈）
        ↓
Deoptimization::fetch_unroll_info()
        ↓
Deoptimization::unpack_frames()
        ↓
构建解释器骨架帧 (skeleton frames)
        ↓
跳转到 deopt_entry[tos_state]
        ↓
在解释器中继续执行
```

## 2. deopt_entry 数组结构

### 2.1 数量和布局

```cpp
// templateInterpreter.hpp:98
enum {
    max_bytecode_length = 6,  // wide iinc 是最长的（不含 reexecute 情况）
    number_of_deopt_entries = max_bytecode_length + 1  // = 7
};

static EntryPoint _deopt_entry[number_of_deopt_entries];  // 7 组入口点
static address    _deopt_reexecute_return_entry;          // 特殊: return 重执行
```

### 2.2 为什么需要多组入口？

`_deopt_entry[i]` 中的 `i` 表示当前字节码的**长度**（即 bcp 需要前进的字节数）：

| 索引 | 字节码长度 | 对应字节码示例 |
|------|------------|----------------|
| 0 | 0 | 特殊情况（重执行当前字节码） |
| 1 | 1 | `return`、`pop`、`nop` |
| 2 | 2 | `bipush`、`iload` |
| 3 | 3 | `invokevirtual`、`getfield` |
| 4 | 4 | `wide iload`、`multianewarray` |
| 5 | 5 | `invokeinterface`、`invokedynamic` |
| 6 | 6 | `wide iinc` |

每组内有 **10 种 TosState 入口**（btos/ztos/ctos/stos 共享 itos）：

```cpp
// templateInterpreterGenerator.cpp:244
Interpreter::_deopt_entry[i] = EntryPoint(
    deopt_itos, /* btos */
    deopt_itos, /* ztos */
    deopt_itos, /* ctos */
    deopt_itos, /* stos */
    generate_deopt_entry_for(atos, i),
    deopt_itos, /* itos */
    generate_deopt_entry_for(ltos, i),
    generate_deopt_entry_for(ftos, i),
    generate_deopt_entry_for(dtos, i),
    generate_deopt_entry_for(vtos, i)
);
```

## 3. generate_deopt_entry_for() 实现

位置: `templateInterpreterGenerator_x86.cpp:241`

```cpp
address TemplateInterpreterGenerator::generate_deopt_entry_for(
    TosState state,      // 栈顶状态
    int step,            // bcp 前进步长
    address continuation // 可选: 自定义继续点
) {
    address entry = __ pc();
    
    // 1. 清除 last_sp（防止 GC 扫描无效数据）
    __ movptr(Address(rbp, frame::interpreter_frame_last_sp_offset * wordSize), 
              (int32_t)NULL_WORD);
    
    // 2. 恢复解释器关键寄存器
    __ restore_bcp();     // r13 = bcp
    __ restore_locals();  // r14 = locals pointer
    
    // 3. [JVMCI] 处理 pending_monitorenter
    //    同步方法入口可能需要在反优化后获取锁
#if INCLUDE_JVMCI
    if ((EnableJVMCI || UseAOT) && state == vtos && step == 0) {
        Label L;
        __ cmpb(Address(thread, JavaThread::pending_monitorenter_offset()), 0);
        __ jcc(Assembler::zero, L);
        __ movb(Address(thread, JavaThread::pending_monitorenter_offset()), 0);
        __ get_method(rbx);
        lock_method();  // 获取监视器锁
        __ bind(L);
    }
#endif
    
    // 4. 检查并处理 pending exception
    {
        Label L;
        __ cmpptr(Address(thread, Thread::pending_exception_offset()), 
                  (int32_t)NULL_WORD);
        __ jcc(Assembler::zero, L);  // 无异常则跳过
        __ call_VM(noreg, CAST_FROM_FN_PTR(address,
                   InterpreterRuntime::throw_pending_exception));
        __ should_not_reach_here();
        __ bind(L);
    }
    
    // 5. 分发到下一个字节码（或跳转到自定义继续点）
    if (continuation == NULL) {
        __ dispatch_next(state, step);  // 正常路径
    } else {
        __ jump_to_entry(continuation);  // 特殊路径（如 return 重执行）
    }
    
    return entry;
}
```

### 3.1 关键步骤详解

#### restore_bcp() 和 restore_locals()

```cpp
// x86_64 实现
void InterpreterMacroAssembler::restore_bcp() {
    movptr(r13, Address(rbp, frame::interpreter_frame_bcp_offset * wordSize));
}

void InterpreterMacroAssembler::restore_locals() {
    movptr(r14, Address(rbp, frame::interpreter_frame_locals_offset * wordSize));
}
```

反优化时，`Deoptimization::unpack_frames()` 已经构建好解释器栈帧，
`bcp` 和 `locals` 指针存储在栈帧的固定偏移位置。

#### dispatch_next(state, step)

```cpp
// 伪代码
dispatch_next(state, step):
    r13 += step                              ; bcp 前进 step 字节
    bytecode = LOAD_BYTE(r13)                ; 读取下一字节码
    entry = _normal_table[state][bytecode]   ; 查表获取入口
    JMP entry                                ; 跳转执行
```

## 4. 反优化入口的使用场景

### 4.1 deopt_entry(vtos, 0) - 最常用

**场景**: 重执行当前字节码

```cpp
// vframeArray.cpp:192
// 同步方法序言中反优化
pc = Interpreter::deopt_entry(vtos, 0);

// vframeArray.cpp:276
// uncommon trap 或 reexecute 模式
pc = Interpreter::deopt_entry(vtos, 0);
```

`step = 0` 表示 bcp 不前进，重新执行当前字节码。

### 4.2 deopt_continue_after_entry() - 继续执行

**场景**: 执行完当前字节码，继续执行下一个

```cpp
// abstractInterpreter.cpp:371
return is_top_frame
    ? Interpreter::deopt_entry(as_TosState(type), length)
    : Interpreter::return_entry(as_TosState(type), length, index_size);
```

`length` 是当前字节码的长度，反优化后 bcp 前进到下一字节码。

### 4.3 invoke 后反优化 - 处理返回值

```cpp
// 对于 invokevirtual (长度=3)
case Bytecodes::_invokevirtual: {
    type = Bytecode_invoke(mh, bci).result_type();  // 获取返回类型
    // ...
}

// 使用返回类型确定 TosState
return Interpreter::deopt_entry(as_TosState(type), 3);
```

例如：`invokevirtual` 返回 `int`，则使用 `deopt_entry[itos][3]`，
bcp 前进 3 字节，从 itos 状态继续。

## 6. _deopt_reexecute_return_entry

位置: `templateInterpreterGenerator.cpp:260`

```cpp
address return_continuation = Interpreter::_normal_table.entry(Bytecodes::_return).entry(vtos);
Interpreter::_deopt_reexecute_return_entry = 
    generate_deopt_entry_for(vtos, 0, return_continuation);
```

**用途**: 对象构造期间（`<init>` 方法）的 finalizer 注册。

如果在 `_return_register_finalizer` 字节码处发生反优化，
不能重执行该字节码（会导致 finalizer 双重注册），
而是直接跳转到普通 `return` 的执行点。

## 8. 代码大小统计

**PrintInterpreter 输出**:
```
deoptimization entry points [0x00007f8c9d02da20, 0x00007f8c9d031400] 14816 bytes
```

- **总大小**: 约 14.5KB
- **入口点数量**: 7 (lengths) × 6 (实际生成的 TosState) ≈ 42 个入口
- **平均每个入口**: ~350 bytes

这是解释器中**最大的 Codelet**，因为需要为每个 (length, TosState) 组合生成入口。

---

## 9. 关键点总结

1. **7 组入口点**: 对应字节码长度 0-6
2. **每组 10 种 TosState**: 但 btos/ztos/ctos/stos 共享 itos
3. **step=0 最常用**: 用于重执行当前字节码
4. **异常检查**: 每个入口都检查 pending exception
5. **JVMCI 支持**: vtos/step=0 时可能需要获取监视器锁
6. **_deopt_reexecute_return_entry**: 特殊处理 finalizer 注册
