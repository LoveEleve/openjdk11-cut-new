# Phase 6.5: 异常类预初始化 (Exception Pre-initialization)

> **源码位置**: `src/hotspot/share/runtime/thread.cpp:3855-3863` 和 `src/hotspot/share/memory/universe.cpp:1229-1299`
> **重要程度**: ⭐⭐⭐⭐ (面试高频 + 设计思想)
> **前置知识**: `universe_init()` 已完成，堆已创建

---

## 第 0 部分：核心原理 ⭐

### 0.1 本质是什么？

本文分析 **Phase 6.5: 异常类预初始化 (Exception Pre-initialization)** 的初始化过程：JVM 启动时该组件如何被创建、配置和激活，以及初始化顺序的约束关系。

### 0.2 为什么需要？

JVM 初始化顺序有严格的依赖关系——某些组件必须在其他组件之前初始化。理解初始化顺序有助于排查启动失败问题，也能理解各组件的设计约束。

### 0.3 怎么解决？

追踪初始化函数的调用链，分析每个初始化步骤的前置条件和后置效果，识别关键的初始化顺序约束。

### 0.4 为什么这样设计？

初始化顺序的设计原则：「被依赖的先初始化」。例如内存管理必须在 GC 之前初始化，GC 必须在类加载之前初始化。

## 📋 概述

### 1. 功能定位

异常类预初始化是 JVM 启动阶段的**防御性设计**：

```
┌─────────────────────────────────────────────────────────────────────────┐
│  核心问题：                                                              │
│  当发生 OutOfMemoryError/StackOverflowError 时，                         │
│  如果此时才去加载和实例化异常类，可能因为内存/栈空间不足而失败，          │
│  导致 JVM 无法正常抛出异常，最终崩溃                                     │
├─────────────────────────────────────────────────────────────────────────┤
│  解决方案：                                                              │
│  1. 在 JVM 启动早期就 预加载+预初始化 这些异常类                          │
│  2. 预分配一些异常对象实例，缓存在 Universe 中                           │
│  3. 运行时需要抛出异常时，直接使用预分配的对象，无需再分配内存            │
└─────────────────────────────────────────────────────────────────────────┘
```

### 2. 在整体流程中的位置

  Universe::_virtual_machine_error_instance = InstanceKlass::cast(k)->allocate_instance(CHECK_false);
  Universe::_vm_exception = InstanceKlass::cast(k)->allocate_instance(CHECK_false);
  
  // ==========================================================

  Handle msg = java_lang_String::create_from_str("Java heap space", CHECK_false);
  java_lang_Throwable::set_message(Universe::_out_of_memory_error_java_heap, msg());

  msg = java_lang_String::create_from_str("Metaspace", CHECK_false);

  java_lang_Throwable::set_message(Universe::_out_of_memory_error_realloc_objects, msg());

  msg = java_lang_String::create_from_str("/ by zero", CHECK_false);
  java_lang_Throwable::set_message(Universe::_arithmetic_exception_instance, msg());
  
  // ==========================================================
  // 【Part 6】预分配 OOM 错误数组（带 backtrace）
  // ==========================================================
  int len = (StackTraceInThrowable) ? (int)PreallocatedOutOfMemoryErrorCount : 0;  // 默认 4 个
  Universe::_preallocated_out_of_memory_error_array = oopFactory::new_objArray(ik, len, CHECK_false);
  for (int i = 0; i < len; i++) {
    oop err = ik->allocate_instance(CHECK_false);
    Handle err_h = Handle(THREAD, err);
    java_lang_Throwable::allocate_backtrace(err_h, CHECK_false);  // 预分配 backtrace 空间
    Universe::preallocated_out_of_memory_errors()->obj_at_put(i, err_h());
  }
  Universe::_preallocated_out_of_memory_error_avail_count = (jint)len;
  
  return true;
}

## 🔍 运行时使用：gen_out_of_memory_error()

当需要抛出 OOM 时，JVM 会调用 `gen_out_of_memory_error()` 从预分配数组中获取对象：

```cpp
// 源码位置: src/hotspot/share/memory/universe.cpp:616-651

oop Universe::gen_out_of_memory_error(oop default_err) {
  // 生成一个 OOM 错误：
  // - 如果有可用的预分配错误对象（且 j.l.Throwable 已初始化），
  //   则返回带有 backtrace 的预分配对象，并设置 default_err 的消息
  // - 否则，返回 default_err（无 backtrace）
  
  int next;
  if ((_preallocated_out_of_memory_error_avail_count > 0) &&
      SystemDictionary::Throwable_klass()->is_initialized()) {
    // 原子减少可用计数
    next = (int)Atomic::add(-1, &_preallocated_out_of_memory_error_avail_count);
    assert(next < (int)PreallocatedOutOfMemoryErrorCount, "avail count is corrupt");
  } else {
    next = -1;
  }
  
  if (next < 0) {
    // 所有预分配的错误对象都用完了，返回默认的
    return default_err;
  } else {
    Thread* THREAD = Thread::current();
    Handle default_err_h(THREAD, default_err);
    
    // 从数组中取出对象，并清空槽位（避免数组持续引用）
    Handle exc(THREAD, preallocated_out_of_memory_errors()->obj_at(next));
    assert(exc() != NULL, "slot has been used already");
    preallocated_out_of_memory_errors()->obj_at_put(next, NULL);

    // 使用 default_err 的消息
    oop msg = java_lang_Throwable::message(default_err_h());
    assert(msg != NULL, "no message");
    java_lang_Throwable::set_message(exc(), msg);

    // 填充 backtrace 并返回
    java_lang_Throwable::fill_in_stack_trace_of_preallocated_backtrace(exc);
    return exc();
  }
}
```

## 🔍 运行时使用：StackOverflowError

SOE 的处理特殊在于：**栈已经溢出了，无法再调用 Java 构造函数**，必须使用预初始化的异常对象：

```cpp
// 源码位置: src/hotspot/share/interpreter/interpreterRuntime.cpp:366-379

static Handle get_preinitialized_exception(Klass* k, TRAPS) {
  InstanceKlass* klass = InstanceKlass::cast(k);
  // 断言：这个类必须在 VM 初始化期间就已经初始化
  assert(klass->is_initialized(),
         "this klass should have been initialized during VM initialization");
  
  // 创建实例 - 不调用构造函数！因为可能没有（Java）栈空间
  // (应该断言构造函数为空)
  Handle exception;
  oop exception_oop = klass->allocate_instance(CHECK_(exception));
  exception = Handle(THREAD, exception_oop);
  
  // 填充 backtrace（如果启用）
  if (StackTraceInThrowable) {
    java_lang_Throwable::fill_in_stack_trace(exception);
  }
  return exception;
}

// 解释器抛出 SOE
IRT_ENTRY(void, InterpreterRuntime::throw_StackOverflowError(JavaThread* thread))
  Handle exception = get_preinitialized_exception(
                                 SystemDictionary::StackOverflowError_klass(),
                                 CHECK);
  Atomic::inc(&Exceptions::_stack_overflow_errors);  // 统计计数
  THROW_HANDLE(exception);
IRT_END
```

### SharedRuntime 中的 SOE 处理

```cpp
// 源码位置: src/hotspot/share/runtime/sharedRuntime.cpp:769-786

void SharedRuntime::throw_StackOverflowError_common(JavaThread* thread, bool delayed) {
  // 我们避免使用正常的异常构造，因为它会执行到 Java 的 upcall，
  // 而我们已经没有栈空间了
  Thread* THREAD = thread;
  Klass* k = SystemDictionary::StackOverflowError_klass();
  
  // 直接分配实例，不调用构造函数！
  oop exception_oop = InstanceKlass::cast(k)->allocate_instance(CHECK);
  
  // 如果是延迟的 SOE，设置特殊消息
  if (delayed) {
    java_lang_Throwable::set_message(exception_oop,
                                     Universe::delayed_stack_overflow_error_message());
  }
  
  Handle exception(thread, exception_oop);
  if (StackTraceInThrowable) {
    java_lang_Throwable::fill_in_stack_trace(exception);
  }
  
  Atomic::inc(&Exceptions::_stack_overflow_errors);
  throw_and_post_jvmti_exception(thread, exception);
}
```

## 🎯 设计思想总结

### 1. 为什么要预分配？

```
┌─────────────────────────────────────────────────────────────────────────┐
│  场景1：发生 OutOfMemoryError                                           │
│  ─────────────────────────────────────────────────────────────────────  │
│  问题：堆内存不足 → 无法分配 OOM 对象 → 无法抛出异常 → JVM 崩溃        │
│  解决：在启动时预分配 OOM 对象，需要时直接使用                          │
├─────────────────────────────────────────────────────────────────────────┤
│  场景2：发生 StackOverflowError                                         │
│  ─────────────────────────────────────────────────────────────────────  │
│  问题：栈空间耗尽 → 无法调用构造函数 → 无法创建异常对象 → JVM 崩溃     │
│  解决：预初始化 SOE 类，创建时不调用构造函数（直接 allocate_instance）  │
├─────────────────────────────────────────────────────────────────────────┤
│  场景3：NullPointerException / ArithmeticException                      │
│  ─────────────────────────────────────────────────────────────────────  │
│  原因：这些异常非常频繁，预分配可以减少运行时开销                       │
│  场景：JIT 编译器生成的代码可以直接使用预分配的实例                     │
└─────────────────────────────────────────────────────────────────────────┘
```

### 2. 预分配 vs 预初始化

| 概念 | 含义 | 时机 | 位置 |
|-----|------|-----|------|
| **预分配** (pre-allocate) | 提前分配异常对象实例 | `universe_post_init()` | universe.cpp:1229 |
| **预初始化** (pre-initialize) | 初始化异常类 (执行 `<clinit>`) | `initialize_java_lang_classes()` | thread.cpp:3855 |

**顺序关系**：
```
universe_post_init() → 预分配对象实例（只分配内存，填充消息）
       ↓
initialize_java_lang_classes() → 执行类的 <clinit> 方法（静态初始化块）
```

### 3. 关键 JVM 参数

| 参数 | 默认值 | 含义 |
|------|-------|------|
| `PreallocatedOutOfMemoryErrorCount` | 4 | 预分配带 backtrace 的 OOM 对象数量 |
| `StackTraceInThrowable` | true | 异常是否包含堆栈跟踪 |
| `StackReservedPages` | 1 | 栈保留页数（用于延迟 SOE） |

## 🎤 面试高频问题

### Q1: 为什么 JVM 要预分配 OutOfMemoryError？

**答**：当发生 OOM 时，堆内存已经不足。如果此时才去分配 OOM 对象，可能因为内存不足而无法分配，导致 JVM 无法正常抛出异常。预分配可以保证即使在内存极度紧张的情况下，也能正常抛出 OOM。

### Q2: StackOverflowError 为什么不调用构造函数？

**答**：当发生栈溢出时，栈空间已经耗尽。调用构造函数需要压栈，而此时已经没有栈空间了。因此 JVM 使用 `allocate_instance()` 直接分配对象内存，跳过构造函数调用。SOE 的构造函数本来也是空的。

### Q3: 预分配的 OOM 数组有什么作用？

**答**：
- 数组中的 OOM 对象**带有 backtrace 空间**
- 第一次抛出 OOM 时，可以提供完整的堆栈跟踪
- 当 `gen_out_of_memory_error()` 被调用时，从数组中取出对象，填充当前的堆栈信息
- 默认预分配 4 个（`PreallocatedOutOfMemoryErrorCount`）

### Q4: 6 种 OOM 消息分别对应什么场景？

| 类型 | 消息 | 触发场景 |
|-----|------|---------|
| java_heap | "Java heap space" | 普通对象分配失败 |
| metaspace | "Metaspace" | 类元数据空间不足 |
| class_metaspace | "Compressed class space" | 压缩类指针空间不足 |
| array_size | "Requested array size exceeds VM limit" | 数组长度超过 `Integer.MAX_VALUE - 8` |
| gc_overhead_limit | "GC overhead limit exceeded" | GC 时间超过 98%，回收内存不足 2% |
| realloc_objects | "failed reallocation of scalar replaced objects" | 标量替换的对象重新分配失败 |

### Q5: 为什么 NPE 和 ArithmeticException 也要预分配？

**答**：这两个异常在运行时非常频繁（尤其是 NPE）。JIT 编译器生成的代码可以直接使用预分配的实例，避免每次都分配新对象，提高性能。注释中也写明："a cheap & dirty solution in compiler exception handling"。
