# Phase 6.3: 辅助类初始化 (Auxiliary Classes Initialization)

> **源码位置**: `src/hotspot/share/runtime/thread.cpp:3840-3844`
> **重要程度**: ⭐⭐ (模块系统和 Finalizer 机制基础)
> **前置知识**: 主线程已创建，Thread 类已初始化

---

## 第 0 部分：核心原理 ⭐

### 0.1 本质是什么？

本文分析 **Phase 6.3: 辅助类初始化 (Auxiliary Classes Initialization)** 的初始化过程：JVM 启动时该组件如何被创建、配置和激活，以及初始化顺序的约束关系。

### 0.2 为什么需要？

JVM 初始化顺序有严格的依赖关系——某些组件必须在其他组件之前初始化。理解初始化顺序有助于排查启动失败问题，也能理解各组件的设计约束。

### 0.3 怎么解决？

追踪初始化函数的调用链，分析每个初始化步骤的前置条件和后置效果，识别关键的初始化顺序约束。

### 0.4 为什么这样设计？

初始化顺序的设计原则：「被依赖的先初始化」。例如内存管理必须在 GC 之前初始化，GC 必须在类加载之前初始化。

```cpp

void Threads::initialize_java_lang_classes(JavaThread *main_thread, TRAPS) {
    // ... 前面是 6.1 核心类初始化 和 6.2 主线程创建 ...
    
    // ========== 6.3 辅助类初始化 ==========
    
    // 1. Module 类 - VM 创建此类的对象 (模块系统基础)

    initialize_class(vmSymbols::java_lang_reflect_Method(), CHECK);

    initialize_class(vmSymbols::java_lang_ref_Finalizer(), CHECK);

    // Phase 1 of the system initialization in the library

    // ...
}
```

**源码注释说明**：
- **Module**: "VM creates objects of this class" - VM 会创建模块对象
- **Method**: "VM preresolves methods" - VM 需要预解析反射方法
- **Finalizer**: 代码注释较少，但这是 GC finalize 机制的核心类

```cpp
ModuleEntry* java_lang_Module::module_entry(oop module) {
    ModuleEntry* module_entry = (ModuleEntry*)module->address_field(_module_entry_offset);
    if (module_entry == NULL) {

    return module_entry;
```

### 6.3.3 `java.lang.ref.Finalizer` 类 ⭐⭐⭐ (重点)

#### 作用

`Finalizer` 类是 Java 垃圾回收器中 finalize 机制的核心实现类。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                  java.lang.ref.Finalizer 类                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  核心功能：                                                               │
│  ├── 管理所有需要执行 finalize() 方法的对象                             │
│  ├── 维护一个 Finalizer 对象链表                                        │
│  └── FinalizerThread 负责执行 finalize() 方法                           │
│                                                                          │
│  关键静态方法：                                                           │
│  └── Finalizer.register(Object) - 注册需要 finalize 的对象              │
│                                                                          │
│  工作流程：                                                               │
│  1. 对象分配时，如果类重写了 finalize()，注册到 Finalizer               │
│  2. GC 发现对象不可达时，将其从 Finalizer 链表移到 finalize 队列        │
│  3. FinalizerThread 从队列取出对象，执行其 finalize() 方法              │
│  4. finalize() 执行完成后，对象才能被真正回收                            │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

#### JVM 中的 Finalizer 注册实现

```cpp
// 源码位置: src/hotspot/share/oops/instanceKlass.cpp:1225
instanceOop InstanceKlass::register_finalizer(instanceOop i, TRAPS) {
    if (TraceFinalizerRegistration) {
        tty->print("Registered ");
        i->print_value_on(tty);
        tty->print_cr(" (" INTPTR_FORMAT ") as finalizable", p2i(i));
    }
    
    instanceHandle h_i(THREAD, i);
    JavaValue result(T_VOID);
    JavaCallArguments args(h_i);
    
    // 获取 Finalizer.register(Object) 方法
    methodHandle mh (THREAD, Universe::finalizer_register_method());
    
    // 调用 Java 方法: Finalizer.register(obj)
    JavaCalls::call(&result, mh, &args, CHECK_NULL);
    
    return h_i();
}

// 对象分配时检查是否需要注册 finalizer
instanceOop InstanceKlass::allocate_instance(TRAPS) {
    bool has_finalizer_flag = has_finalizer();  // 检查类是否有 finalizer
    int size = size_helper();
    
    instanceOop i = (instanceOop)Universe::heap()->obj_allocate(this, size, CHECK_NULL);
    
    // 如果 RegisterFinalizersAtInit = false 且类有 finalizer
    // 则在对象分配时注册 (而不是在 Object.<init> 结束时)
    if (has_finalizer_flag && !RegisterFinalizersAtInit) {
        i = register_finalizer(i, CHECK_NULL);
    }
    return i;
}
```

## ⚠️ Finalizer 机制的问题

### 为什么 finalize() 被废弃？

```
┌─────────────────────────────────────────────────────────────────────────┐
│  finalize() 机制的问题 (JDK 9 开始废弃)                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  1. 性能问题：                                                            │
│     ├── 每个 finalizable 对象都需要创建 Finalizer 包装对象              │
│     ├── 对象至少存活两个 GC 周期才能被回收                               │
│     └── FinalizerThread 优先级低，可能跟不上分配速度                    │
│                                                                          │
│  2. 不确定性：                                                            │
│     ├── finalize() 何时执行是不确定的                                   │
│     ├── finalize() 甚至可能永远不执行（JVM 退出时）                     │
│     └── 执行顺序也是不确定的                                             │
│                                                                          │
│  3. 安全问题：                                                            │
│     ├── finalize() 中可以"复活"对象（重新使其可达）                     │
│     ├── 可能导致资源泄漏                                                 │
│     └── finalize() 抛出异常会被忽略                                     │
│                                                                          │
│  4. 资源泄漏风险：                                                        │
│     └── 如果 finalize() 执行慢，可能导致 OOM                            │
│                                                                          │
│  替代方案：                                                               │
│  ├── try-with-resources (AutoCloseable)                                  │
│  ├── java.lang.ref.Cleaner (JDK 9+)                                      │
│  └── PhantomReference + ReferenceQueue                                   │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

## 📊 辅助类初始化顺序的原因

```
┌─────────────────────────────────────────────────────────────────────────┐
│  辅助类初始化顺序分析                                                    │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  1. Module 类先初始化：                                                   │
│     ├── initPhase2 会初始化模块系统 (JPMS)                              │
│     ├── 模块系统需要创建 Module 对象                                     │
│     └── Module 类必须先完成静态初始化                                    │
│                                                                          │
│  2. Method 类其次：                                                       │
│     ├── JVM 需要预解析反射方法                                           │
│     ├── 后续初始化可能涉及反射调用                                       │
│     └── Method 对象的字段偏移量需要提前计算                              │
│                                                                          │
│  3. Finalizer 类最后：                                                    │
│     ├── initPhase1 后会开始分配 Java 对象                               │
│     ├── 对象分配时可能需要注册 finalizer                                │
│     ├── Finalizer 类必须在此之前完成初始化                              │
│     └── FinalizerThread 也在这时启动                                     │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

## 🎯 面试高频问题

### Q1: Finalizer 机制是如何工作的？

1. **注册阶段**：对象分配时，如果类重写了 `finalize()`，调用 `Finalizer.register(obj)` 注册
2. **GC 阶段**：发现对象不可达时，将其移到 finalize 队列，对象暂时"复活"
3. **执行阶段**：FinalizerThread 从队列取出对象，执行 `finalize()` 方法
4. **回收阶段**：下次 GC 时，对象才能被真正回收

### Q2: 为什么 finalize() 被废弃？

- **性能差**：对象至少存活两个 GC 周期
- **不确定**：执行时机和顺序都不确定
- **安全隐患**：可以"复活"对象，可能导致资源泄漏
- **替代方案**：`try-with-resources`、`Cleaner`、`PhantomReference`

### Q3: Module 类在模块系统中的作用？

- 表示一个 Java 模块（如 `java.base`）
- 控制模块之间的依赖关系
- `exports/opens` 机制控制包的访问权限
- JVM 通过 `ModuleEntry` 与 Module 对象关联
