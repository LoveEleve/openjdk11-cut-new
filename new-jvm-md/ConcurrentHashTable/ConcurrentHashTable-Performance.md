# ConcurrentHashTable 性能分析与调优指南

> **文档定位**：CHT 系列文档 3/3 - 性能特性、对比分析与调优建议  
> **分析目标**：理解 CHT 的性能特征，掌握调优方法，对比 JDK ConcurrentHashMap  
> **源码版本**：OpenJDK 11  
> **适用场景**：StringTable、SymbolTable、ThreadIdTable 等 JVM 内部哈希表

---

## 第 0 部分：核心原理 ⭐

### 0.1 本质是什么？

CHT 性能设计的本质是**针对 JVM 内部读多写少场景的极致优化**：用 RCU 换取 Wait-Free 读取（正常路径零锁开销），用渐进式扩容换取无全局停顿（最坏延迟可控），用指针打包状态换取内存紧凑性（Bucket 只有 8 字节）。

### 0.2 为什么需要？

JVM 内部哈希表（StringTable/SymbolTable）的访问模式极端：读:写 通常 > 100:1，且读取在 GC 停顿期间也可能发生。通用的 `ConcurrentHashMap` 虽然线程安全，但：(1) 读取需要 volatile 读 + 内存屏障，不是 Wait-Free；(2) 扩容是全量迁移，可能导致几十毫秒的停顿；(3) 内存开销较大（Segment/CounterCell 等额外结构）。

### 0.3 怎么解决？

**三个核心性能决策**：
- **Wait-Free 读取**：GlobalCounter RCU 机制，读取线程只需写一个线程本地计数器，不需要任何 CAS 或锁
- **渐进式扩容**：按需迁移（只有被访问的 bucket 才迁移），双表共存期间读写不停顿，最坏延迟 = 单桶迁移时间（微秒级）
- **指针打包**：Bucket 状态（UNLOCKED/LOCKED/REDIRECT）存在 `_first` 指针低 2 位，Bucket 只需 8 字节，8 个 Bucket 恰好一个 Cache Line

### 0.4 为什么这样设计？

- **为什么 CHT 不用红黑树（CHM 1.8 在链表长度 > 8 时转红黑树）？** JVM 内部表的 hash 函数质量高（Murmur hash），链表长度通过 `_grow_hint`（默认 4）控制，不会出现 CHM 需要红黑树的场景；红黑树节点更大，内存开销更高
- **为什么 CHT 用头插而不是尾插？** 头插只需修改 bucket 的 `_first` 指针（一次 CAS），尾插需要遍历到链表末尾再修改（两次操作，无法原子化）；头插更快，且 CHT 不需要保证插入顺序
- **为什么 StringTable 默认大小是 60013（质数）？** 质数作为哈希表大小可以减少哈希冲突（避免 hash 值的公因子导致聚集）；CHT 使用 2 的幂次大小（通过 `_log2_size` 控制），StringTable 的 60013 是初始化时向上取整到最近的 2 的幂次

### 1.2 场景假设

CHT 的设计基于以下 JVM 内部使用场景的假设：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        CHT 场景假设                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  1. 读多写少                                                            │
│     - StringTable: 类加载时写入，运行时大量读取                          │

│     - 初始大小合理设置后，扩容次数有限                                   │
```

## 3. 核心性能指标

### 3.1 理论性能边界

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      CHT 理论性能边界                                    │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  操作          最优情况              最坏情况              平均情况      │
│  ─────────────────────────────────────────────────────────────────────  │
│                                                                         │
│  get()        O(1)                  O(grow_hint)       O(1 + α/2)      │
│              （直接命中）            （链表遍历）        （α = 负载因子） │
│                                                                         │
│  insert()     O(1) + CAS            O(n) 重试          O(1) + 低概率重试 │
│              （无冲突）              （高并发冲突）                        │
│                                                                         │
│  remove()     O(1) + 锁获取         O(1) + 锁竞争      O(1) + 低竞争     │
│                                                                         │
│  grow()       O(1) 每 bucket        O(n) 全表迁移      O(k) 渐进完成      │
│              （单桶迁移）                                                   │
│                                                                         │
│  内存开销     O(N × (sizeof(Node)   O(N × 1.5)         O(N × 1.2)       │
│              + sizeof(Bucket)))     （扩容期间双表）     （通常）          │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 4. 性能瓶颈分析

### 4.1 热点识别

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      性能热点分析                                        │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  热点场景 1: Bucket 热点                                                 │
│  ═══════════════════════════                                            │
│  症状：单个 bucket 链表过长（>_grow_hint）                               │
│  原因：hash 分布不均，或特定 key 大量重复                                 │
│  解决：检查 hash 函数，增大表大小                                        │
│                                                                         │
│  热点场景 2: 扩容期间的读放大                                            │
│  ═══════════════════════════                                            │
│  症状：扩容期间 get() 延迟增加                                           │
│  原因：REDIRECT 检查 + 新表访问                                          │
│  解决：预扩容，避免运行时扩容                                            │
│                                                                         │
│  热点场景 3: 写冲突                                                      │
│  ═══════════════════════════                                            │
│  症状：insert() 重试次数过多                                             │
│  原因：多线程同时写入同一 bucket                                         │
│  解决：应用层分散写入，或增大表                                          │
│                                                                         │
│  热点场景 4: GlobalCounter 竞争                                          │
│  ═══════════════════════════                                            │
│  症状：CPU 使用率高但吞吐量低                                            │
│  原因：critical_section_begin/end 竞争激烈                               │
│  解决：减少短生命周期操作，合并访问                                      │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 8. 面试深度问题

### 8.1 高级问题与解答

**Q1: 为什么 CHT 不实现为 Lock-Free 而是 Wait-Free？**

```
深度回答：

1. 定义区别：
   • Lock-Free: 至少一个线程在有限步骤内完成，允许饥饿
   • Wait-Free: 每个线程都在有限步骤内完成，无饥饿

2. CHT 的选择：
   • 场景要求：JVM 内部表要求稳定低延迟
   • 实现可行性：get() 只有链表遍历，天然 Wait-Free
   • 代价评估：使用 RCU 的开销可以接受

3. 实际收益：
   • GC 暂停时间更可控
   • 避免读取线程饿死
   • 适应实时性要求高的场景
```

**Q2: CHT 的渐进式扩容 vs CHM 的协助扩容，各有什么优劣？**

```
对比分析：

┌────────────────┬─────────────────────┬─────────────────────┐
│     特性       │    CHT 渐进式       │    CHM 协助式       │
├────────────────┼─────────────────────┼─────────────────────┤
│ 触发方式       │ 访问触发            │ 统一触发            │
│ 迁移粒度       │ 单桶                │ 多线程批量          │
│ 内存开销       │ 双表长期共存        │ 临时开销            │
│ 代码复杂度     │ 高（REDIRECT逻辑）  │ 中                  │
│ 最坏延迟       │ 低（单桶操作）      │ 高（全表迁移）      │
│ 吞吐量影响     │ 小                  │ 大（迁移期间）      │
│ 适用场景       │ 延迟敏感            │ 吞吐量优先          │
└────────────────┴─────────────────────┴─────────────────────┘
```

**Q3: 如何证明 CHT 的 get() 是 Wait-Free？**

```
证明思路：

1. 步骤有界性：
   get() 的操作序列：
   - GlobalCounter::critical_section_begin()  → 常数时间
   - get_bucket()                            → 常数时间
   - get_node()                              → 最多遍历 grow_hint 个节点
   - GlobalCounter::critical_section_end()   → 常数时间

2. 无循环依赖：
   - 没有 while(true) 重试循环
   - 没有等待其他线程释放资源
   - 链表遍历是线性扫描，有明确终止条件

3. 独立性：
   - 不依赖其他线程的进度
   - 即使其他线程卡住，get() 也能完成

结论：get() 满足 Wait-Free 定义
```

### 8.2 设计思考题

**Q4: 如果要优化 CHT 的 insert() 性能，你会考虑哪些方案？**

```
优化方向：

1. 减少 CAS 失败率：
   • 使用退避指数增长（exponential backoff）
   • 添加线程本地缓存减少冲突

2. 批量插入：
   • 提供 bulk_insert API
   • 减少 GlobalCounter 进出开销

3. 无锁链表：
   • 研究 Harris 无锁链表
   • 权衡复杂度与收益

4. 自适应策略：
   • 检测冲突率，动态切换算法
   • 低冲突用 CAS，高冲突用锁
```

**Q5: CHT 是否适合替换业务代码中的 HashMap？**

```
不建议直接使用，原因：

1. API 限制：
   • CHT 使用模板 + 函数对象，Java 难以直接调用
   • 缺乏通用 Map 接口（get/put/remove 签名不同）

2. 性能特点：
   • CHT 针对读多写少优化
   • 业务代码可能读写均衡，CHM 更合适

3. 维护成本：
   • CHT 是 JVM 内部实现
   • 不保证跨版本 API 兼容

4. 适用边界：
   • 仅在 JNI 代码中可能需要直接使用
   • 通过 Unsafe 调用风险高
```
