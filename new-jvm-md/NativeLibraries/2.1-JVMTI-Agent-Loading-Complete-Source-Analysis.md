**第 2630-2632 行：函数指针类型定义**

| 元素 | 含义 | 分析 |
|------|------|------|
| `extern "C"` | 禁用 C++ 名称修饰 | 确保函数名在动态链接时一致 |
| `JNICALL` | JNI 调用约定 | 在 Windows 上是 `__stdcall`，Linux 上为空 |
| `jint` | 返回类型 | JNI 规范要求返回 `JNI_OK`(0) 或错误码 |
| `JavaVM*` | 第一个参数 | Agent 需要 JVM 接口来调用 JNI/JVMTI 函数 |
| `char*` | 第二个参数 | Agent 选项字符串（如 `"port=5005"`） |
| `void*` | 第三个参数 | 保留参数，目前未使用 |

**为什么用 `extern "C"`？**
```
C++ 编译器会对函数名进行修饰（name mangling）：
  Agent_OnAttach → _Z15Agent_OnAttachP7JavaVMcPv

但 dlsym() 查找的是原始符号名：
  dlsym(handle, "Agent_OnAttach")

extern "C" 确保函数名不被修饰，动态链接才能找到
```

```cpp
class AgentLibrary : public CHeapObj<mtInternal> {
  const char* _name;           // Agent 名称
  const char* _options;        // 选项字符串
  void* _os_lib;               // 动态库句柄
  bool _is_absolute_path;      // 是否为绝对路径
  bool _is_static_lib;         // 是否为静态链接
  bool _valid;                 // 是否有效
  
public:
  AgentLibrary(const char* name, const char* options, 
               bool is_absolute_path, void* os_lib) {
    _name = name;
    _options = options;
    _is_absolute_path = is_absolute_path;
    _os_lib = os_lib;
    _valid = false;  // 初始为无效
    _is_static_lib = false;
  }
  
  void set_os_lib(void* lib) { _os_lib = lib; }
  void set_valid() { _valid = true; }
  void set_static_lib(bool v) { _is_static_lib = v; }
  
  bool valid() { return _valid; }
  bool is_static_lib() { return _is_static_lib; }
  const char* name() { return _name; }
  void* os_lib() { return _os_lib; }
};
```

**为什么用 `CHeapObj<mtInternal>`？**
- JVM 的自定义内存分配机制
- `CHeap` 表示 C 堆（malloc/free）
- `mtInternal` 是内存类型标签（用于 NMT 内存追踪）

**第 2646 行注释**："Initially marked as invalid"
- 防御性编程：先假设失败，成功后标记为 valid
- 避免忘记设置状态导致的错误

**`os::dll_load` 实现**（Linux）：
```cpp
void* os::dll_load(const char* name, char* ebuf, int ebuflen) {
  void* result = dlopen(name, RTLD_LAZY);
  if (result == NULL) {
    // 记录错误信息到 ebuf
    strncpy(ebuf, dlerror(), ebuflen - 1);
    ebuf[ebuflen - 1] = '\0';
  }
  return result;
}
```

**`RTLD_LAZY` 标志**：

**`JvmtiJavaThreadEventTransition`**：
```cpp
class JvmtiJavaThreadEventTransition : public StackObj {
  JavaThread* _thread;
  JavaThreadState _saved_state;
public:
  JvmtiJavaThreadEventTransition(JavaThread* thread) : _thread(thread) {
    _saved_state = thread->thread_state();
    // 将线程状态从 _thread_in_vm 转换为 _thread_in_native
    // 这样 GC 不会等待这个线程
    ThreadStateTransition::transition_from_vm(thread, _thread_in_native);
  }
  ~JvmtiJavaThreadEventTransition() {
    // 恢复原始状态
    ThreadStateTransition::transition_to_vm(thread, _saved_state);
  }
};
```

**为什么要状态转换？**
```
JVM 线程状态：
- _thread_in_vm：执行 JVM 内部代码，GC 需要等待
- _thread_in_native：执行 Native 代码，GC 不需要等待

Agent_OnAttach 是 Native 函数，应该标记为 _thread_in_native
这样 GC 可以并行执行，不阻塞在 Agent 代码上
```

## 第 3 部分：事件控制机制

### 3.1 事件位定义（第 56-80 行）

```cpp
56: static const jlong  SINGLE_STEP_BIT = (((jlong)1) << (JVMTI_EVENT_SINGLE_STEP - TOTAL_MIN_EVENT_TYPE_VAL));
```

**第 56 行：事件位定义**

**位图设计**：
```cpp
// JVMTI 事件编号（部分）
enum {
  JVMTI_EVENT_SINGLE_STEP = 1,
  JVMTI_EVENT_BREAKPOINT = 2,
  JVMTI_EVENT_FRAME_POP = 3,
  // ... 共 50+ 个事件
  JVMTI_EVENT_VM_DEATH = 99
};

// 位图计算
SINGLE_STEP_BIT = 1 << (1 - 1) = 1 << 0 = 0x0001
BREAKPOINT_BIT  = 1 << (2 - 1) = 1 << 1 = 0x0002
FRAME_POP_BIT   = 1 << (3 - 1) = 1 << 2 = 0x0004

// 使用 64 位 jlong 可以存储 64 个事件的开关状态
```

**为什么用位图而不是数组？**
```
位图优势：
1. 空间效率：64 个事件只需 8 字节
2. 快速检查：(enabled_bits & SINGLE_STEP_BIT) != 0
3. 批量操作：enabled_bits |= MONITOR_BITS（启用多个事件）

数组劣势：
1. 需要 50+ 字节的布尔数组
2. 检查需要数组访问，可能缓存未命中
```

### 3.2 事件启用检查（简化）

```cpp
bool JvmtiEventEnabled::is_enabled(jvmtiEvent event_type) {
  jlong mask = bit_for(event_type);
  return (_enabled_bits & mask) != 0;
}
```

## 第 4 部分：面试高频问题

### Q1: 为什么 Agent_OnAttach 需要 `extern "C"`？
**答案**：
1. C++ 编译器会对函数名进行修饰（name mangling）
2. `dlsym()` 查找的是原始符号名
3. `extern "C"` 确保函数名不被修饰，动态链接才能找到

### Q2: `RTLD_LAZY` 和 `RTLD_NOW` 的区别？
**答案**：
- `RTLD_LAZY`：延迟绑定，调用时才解析符号，加载快
- `RTLD_NOW`：立即绑定，加载时解析所有符号，加载慢但能早发现问题
- JVM 用 `RTLD_LAZY` 加快启动速度

### Q3: 为什么需要 `JvmtiJavaThreadEventTransition`？
**答案**：
1. Agent 代码是 Native 代码，应该标记为 `_thread_in_native`
2. 这样 GC 不需要等待 Agent 线程
3. 实现并行 GC，减少停顿时间

### Q4: `HAS_PENDING_EXCEPTION` 为什么需要清除？
**答案**：
1. Agent 可能调用 JNI 函数抛出异常
2. 如果不清除，异常会传播到 JVM 内部
3. 可能导致 JVM 崩溃或不可预期行为

### Q5: 静态链接 Agent 和动态加载 Agent 的区别？
**答案**：

| 特性 | 静态链接 | 动态加载 |
|------|----------|----------|
| 编译方式 | 编译进 JVM 可执行文件 | 独立的 .so/.dll 文件 |
| 加载时机 | JVM 启动时 | 运行时通过 `jcmd` |
| 卸载方式 | 不能卸载 | 可以 `dlclose` |
| 使用场景 | 嵌入式系统 | 通用场景 |
