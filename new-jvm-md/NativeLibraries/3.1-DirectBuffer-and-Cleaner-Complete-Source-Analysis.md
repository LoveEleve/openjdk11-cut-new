**`address` 字段**（在父类 `Buffer.java` 中定义）：
```java

```
- **为什么用 `long` 而不是指针？** Java 没有指针类型，用 `long` 存储 64 位地址
- **为什么移到父类？** JNI 函数 `GetDirectBufferAddress` 需要快速访问，放在父类避免虚方法调用开销

**`att` 字段**（第 61 行）：
```
场景：创建 ByteBuffer 的视图

ByteBuffer buf = ByteBuffer.allocateDirect(1024);  // 原始 Buffer
ByteBuffer view = buf.slice();                      // 视图

问题：
- view 的 address = buf.address + position
- 如果 buf 被 GC，Cleaner 会释放内存
- view 还在使用，但内存已被释放！

解决方案：
- view.att = buf  ← 保持对原始 Buffer 的引用
- GC 不会回收 buf，直到 view 也被回收
```

### 1.5 Cleaner 字段（第 96-98 行）

```java
96:     private final Cleaner cleaner;
97:
98:     public Cleaner cleaner() { return cleaner; }
```

**作用**：
- `Cleaner` 是堆外内存的"守护者"
- 当 DirectByteBuffer 被 GC 回收时，Cleaner 自动释放堆外内存
- 解决了"Java 对象很小，但引用大量堆外内存"的 GC 问题

**为什么用 Cleaner 而不是 finalize()？**
```
finalize() 的问题：
1. 性能差：需要 JNI upcall 到 JVM
2. 延迟高：Finalizer 线程单线程处理
3. 顺序问题：finalize 顺序不确定，可能访问已释放的资源

Cleaner 的优势：
1. 轻量：PhantomReference，不阻止 GC
2. 快速：ReferenceHandler 线程直接调用
3. 安全：PhantomReference 保证对象已不可达
```

**第 114 行**：`super(-1, 0, cap, cap)`
```java

Buffer(int mark, int pos, int lim, int cap) {
    this.mark = mark;    // -1 表示未设置 mark
    this.position = pos; // 0，从开头开始
    this.limit = lim;    // cap，初始限制等于容量
```

**第 115-117 行：页对齐计算**
```java
boolean pa = VM.isDirectMemoryPageAligned();  // 是否强制页对齐（-XX:+PageAlignDirectMemory）
int ps = Bits.pageSize();                      // 页大小（通常是 4KB）
long size = Math.max(1L, (long)cap + (pa ? ps : 0));
```

**为什么需要页对齐？**
```
场景：使用 DirectBuffer 进行内存映射文件操作

非对齐地址：
  address = 0x7f123456789A  （不在页边界上）
  mmap() 要求地址必须页对齐
  → 需要额外的拷贝或调整

对齐地址：
  address = 0x7f1234567000  （4KB 对齐）
  mmap() 可以直接使用
  → 零拷贝优化
```

**第 118 行**：`Bits.reserveMemory(size, cap)`
```java
// 检查 MaxDirectMemorySize 限制
// 如果即将超过限制：
//   1. 触发 System.gc() 尝试回收已弃用的 DirectBuffer
//   2. 等待 ReferenceHandler 线程处理 Cleaner
//   3. 如果仍然不足，抛出 OutOfMemoryError("Direct buffer memory")
```

**第 120-126 行：分配内存**
```java
long base = 0;
try {
    base = UNSAFE.allocateMemory(size);  // 调用 malloc
} catch (OutOfMemoryError x) {
    Bits.unreserveMemory(size, cap);      // 回滚预留
    throw x;
}
```

**为什么用 try-catch？**
- `allocateMemory` 调用底层 `malloc`，可能失败
- 如果失败，必须回滚 `reserveMemory`，否则计数器不一致
- 这种"先预留再分配"模式防止内存超限

**第 127 行**：`UNSAFE.setMemory(base, size, (byte) 0)`
- 将分配的内存清零
- **为什么需要？** 防止读取到之前使用者的敏感数据（安全考虑）
- **性能代价：** 大 Buffer 的初始化会变慢

**第 128-133 行：页对齐调整**
```java
if (pa && (base % ps != 0)) {
    // base & (ps - 1) 计算 offset（ps 是 2 的幂）
    // ps - offset 是需要跳过的字节数
    address = base + ps - (base & (ps - 1));
} else {
    address = base;
}
```

**位运算解释**：
```
假设 ps = 4096 (0x1000)，base = 0x7f123456789A

base & (ps - 1) = 0x7f123456789A & 0xFFF = 0x89A (offset)
ps - offset = 4096 - 2202 = 1894
address = base + 1894 = 0x7f1234568000 (4KB 对齐)

Deallocator 保存的是 base（原始地址）
Buffer 使用的是 address（对齐后的地址）
```

**第 134 行**：`Cleaner.create(this, new Deallocator(base, size, cap))`
```
参数 1：this（DirectByteBuffer）- 被监控的对象
参数 2：Deallocator - 清理任务

逻辑：
1. 创建 PhantomReference，引用 this
2. 当 this 被 GC 回收后，PhantomReference 进入 ReferenceQueue
3. ReferenceHandler 线程检测到，调用 Deallocator.run()
4. Deallocator 释放堆外内存
```

## 第 2 部分：Cleaner 机制深度分析

### 2.1 Cleaner 类定义

```java
59: public class Cleaner
60:     extends PhantomReference<Object>
61: {
```

**为什么继承 PhantomReference？**
```
Java 四种引用类型：

1. StrongReference（强引用）
   Object obj = new Object();  // 只要有强引用，GC 不会回收

2. SoftReference（软引用）
   内存不足时回收，适合缓存

3. WeakReference（弱引用）
   下次 GC 时回收，不管内存是否充足

4. PhantomReference（虚引用）
   不影响对象生命周期，对象被回收后通知

Cleaner 用 PhantomReference 的原因：
- 不阻止 DirectByteBuffer 被回收
- 回收后得到通知，释放堆外内存
```

### 2.2 虚拟队列（第 66-67 行）

```java
66:     // Dummy reference queue, needed because the PhantomReference constructor
67:     // insists that we pass a queue.  Nothing will ever be placed on this queue
68:     // since the reference handler invokes cleaners explicitly.
69:     //
70:     private static final ReferenceQueue<Object> dummyQueue = new ReferenceQueue<>();
```

**为什么需要 dummyQueue？**
- `PhantomReference` 构造函数强制要求传入 `ReferenceQueue`
- 但 Cleaner 不走标准队列流程，而是被 ReferenceHandler 显式调用
- 所以传一个 dummy，实际上不会往里面放任何东西

### 2.3 双向链表（第 71-110 行）

```java
71:     // Doubly-linked list of live cleaners, which prevents the cleaners
72:     // themselves from being GC'd before their referents
73:     //
74:     private static Cleaner first = null;
75:
76:     private Cleaner
77:         next = null,
78:         prev = null;
```

**为什么需要链表？**
```
问题：PhantomReference 本身也是对象，如果没有强引用指向它，
      它自己会被 GC 回收，导致无法执行清理！

解决方案：
1. 创建静态链表 first
2. 所有活跃的 Cleaner 都加入链表
3. 链表有强引用指向 Cleaner，防止 Cleaner 被 GC
4. 清理完成后，从链表移除
```

**add 方法（第 78-85 行）**：
```java
78:     private static synchronized Cleaner add(Cleaner cl) {
79:         if (first != null) {
80:             cl.next = first;
81:             first.prev = cl;
82:         }
83:         first = cl;
84:         return cl;
85:     }
```

**为什么用头插法？**
- 简单高效，O(1) 时间复杂度
- 不需要遍历链表
- 顺序不重要

**remove 方法（第 87-110 行）**：
```java
87:     private static synchronized boolean remove(Cleaner cl) {
88:
89:         // If already removed, do nothing
90:         if (cl.next == cl)
91:             return false;
92:
93:         // Update list
94:         if (first == cl) {
95:             if (cl.next != null)
96:             first = cl.next;
97:         else
98:             first = cl.prev;
99:         }
100:        if (cl.next != null)
101:            cl.next.prev = cl.prev;
102:        if (cl.prev != null)
103:            cl.prev.next = cl.next;
104:
105:        // Indicate removal by pointing the cleaner to itself
106:        cl.next = cl;
107:        cl.prev = cl;
108:        return true;
109:
110:    }
```

**第 90-91 行**：`if (cl.next == cl)`
- 用 next 指向自己表示"已移除"
- 防止重复清理（clean() 可能被多次调用）

**第 106-107 行**：`cl.next = cl; cl.prev = cl;`
- 标记为已移除
- 形成自环，便于检测

### 2.4 create 方法（第 130-134 行）

```java

131:         if (thunk == null)
132:             return null;
```

**为什么静态方法？**
- 工厂模式，控制 Cleaner 创建

## 第 4 部分：面试高频问题

### Q1: 为什么 DirectBuffer 比 HeapBuffer 快？
**答案**：
1. **零拷贝**：DirectBuffer 可以直接传给 Native 代码（如 read/write 系统调用），不需要从堆拷贝到 native 内存
2. **避免 GC 移动**：堆外内存不受 GC 影响，地址固定
3. **页对齐**：可以利用 DMA 等硬件优化

### Q2: Cleaner vs finalize() 的区别？
**答案**：

| 特性 | Cleaner | finalize() |
|------|---------|------------|
| 性能 | 高（PhantomReference，无 JNI upcall） | 低（需要 JNI upcall） |
| 延迟 | 低（ReferenceHandler 线程） | 高（Finalizer 线程单线程） |
| 安全性 | 高（PhantomReference 保证对象已不可达） | 低（可能访问已释放资源） |
| 使用场景 | 简单清理（如释放内存） | 复杂清理（已不推荐） |

### Q3: 为什么需要 `Bits.reserveMemory`？
**答案**：
1. **限制 DirectBuffer 总大小**：防止无限制分配导致物理内存耗尽
2. **触发 GC**：如果即将超过限制，先尝试 GC 回收已弃用的 DirectBuffer
3. **提前失败**：在分配前就检查，避免分配后才发现超限

### Q4: 页对齐的作用？
**答案**：
1. **mmap 要求**：内存映射文件需要页对齐地址
2. **DMA 优化**：硬件 DMA 通常需要页对齐
3. **系统调用优化**：某些系统调用（如 read/write）在页对齐时性能更好
